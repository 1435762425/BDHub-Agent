# BDHub-Agent 项目文档

状态：当前项目与产品真相源。最后整理：2026-09-19。

本文回答“系统要解决什么问题、为谁服务、业务如何运行、什么算完成”。后续开发必须先符合本文；实现方式见 [技术文档](TECHNICAL.md)，当前开发进度见 [Codex 接管状态](handoff/codex-takeover-20260919.md)。

## 1. 项目目标

BDHub-Agent 是面向 TikTok 达人经营的独立系统，目标是在 1–2 人运营团队下，持续完成商品准备、达人发现、触达、回复服务和合作结果跟踪，并逐步替代旧 BDHub。

系统的核心不是“生成文案”或“导出名单”，而是形成可恢复、可核验的经营闭环：

```text
货盘发现
  → 商品资格与方案确认
  → TapLink 准备
  → 达人线索发现
  → 稳定身份与关系校验
  → 指定数量备料
  → 分批触达与逐项回查
  → 收信、服务与人工接管
  → 合作结果和经营证据
```

## 2. 用户与运营方式

- 主要用户是 BJN 的 1–2 名达人运营人员。
- 用户负责市场、商品范围、商业条件、预算、优先级和超出规则的业务决定。
- 系统自动完成有明确规则、可查询事实和可验证结果的步骤。
- 页面只重点展示：已处理结果、等待条件、异常阻塞和需要人决定的事项。
- 同一达人由一个关系上下文统一协调；商品、样品、佣金和渠道是该关系下的不同事项，不建立互相冲突的多个负责人。

## 3. 分阶段范围

### V1：意大利二发闭环

V1 首先完成意大利 TikTok IM 二发：找到曾推广相同 PID 的正销量达人，为其提供当前有效、佣金更高的商品卡，邀请再次制作短视频或 LIVE，并跟进回复和合作结果。

V1 必须覆盖从货盘准备到结果证据的完整闭环，不能停在名单、草稿或人工逐条建议。

### V2：一发与更多市场

- 一发主动推品作为 V2 独立流程，不与二发的历史同品证据混用。
- 墨西哥、巴西按各自能力和商业规则逐市场验收。
- 首期渠道是 TikTok IM；WhatsApp 在身份、授权和执行链完成后接入。
- IT 的单点成功不能自动开放其他市场、账号或渠道。

### 当前不自动扩展的范围

- 样品审批、付费投放、赔偿、MCN 签约和素材制作不是 V1 默认自主动作。
- 不因页面出现入口或只读接口成功，就宣称真实写能力已开放。
- 旧 BDHub 只作为协议和历史事实参考，不继续在旧系统叠加新产品能力。

## 4. 核心业务对象

| 对象 | 业务含义 |
| --- | --- |
| 市场/机构 | 经营、额度、账号、语言和授权的隔离边界 |
| 商品方案 | 同一 PID 下具体来源、活动、期限、佣金和资格的完整组合 |
| TapLink | 与商品方案绑定、经核验可发送的商品卡材料 |
| 达人 | 同市场以 OECID 为稳定主键；handle 是带时间的别名 |
| 线索 | 某达人曾推广某 PID 的来源证据，不等于已具备发送资格 |
| 位置 | 达人×商品的可经营机会；冷却、拒联和额度仍按达人统一判断 |
| 批次 | 用户确认的一次指定人数经营任务，含正式目标、候补和冻结规则 |
| 发送意图 | 一次不可变外部写入意图及其回执、回查和结果状态 |
| 合作事项 | 达人的当前诉求、负责人、下一步、等待条件和关闭证据 |

## 5. V1 完整业务流程

PID 维度的来源、选入、建链、刷新、核验与清理统一按 [PID 生命周期树](architecture/pid-lifecycle-v1.md) 执行；后续达人和发送只能消费其中的 `material_ready` PID。

### 5.1 创建任务

用户以自然语言或表单说明市场、目标人数、商品范围、开始日期、北京时间窗口和商业条件。系统生成一张可审阅任务卡；用户确认一次后，任务内部的正常准备步骤不逐项反复确认。

- 目标必须是明确正整数 `N`。
- 默认准备 `N + ceil(N × 10%)` 候补；候补不增加目标。
- 可以先立即备料、稍后再填写发送窗口；未设置窗口不阻塞准备，但不能开始发送。
- 修改目标、范围或规则形成新版本，只重算未提交部分；历史证据不可改写。
- 数量不足默认等待并显示缺口。只有用户明确“部分放行”时，才先发送已就绪项，原目标不缩小。

### 5.2 货盘采集与筛分

全托主来源固定为“高机会商品 → 仅全球销售商品”。默认入池条件：

- 累计销量 `>= 300`；
- 有评分时评分 `>= 4.0`，无评分允许；评分值 `0` 的语义未核实时不自行解释；
- 总佣金率减公开佣金率 `>= 2` 个百分点；
- 全托商品不要求库存数量；库存缺失、0 或低于 100 不因数量被拦截；
- 平台明确下架、治理、失效仍然拦截。

Campaign 非全托是独立来源：必须核对 ACTIVE、剩余期限、普通商品库存和额外条款，不能套用全托的无库存例外。评分大于 4 是二发偏好；剩余期限默认要求大于 45 天。期限是动态资格：加入 Campaign 时大于 45 天不产生永久资格；后续刷新发现剩余期限 `<=45` 天时，该 PID 的未发送位置退出严格发送池，历史线索、已发送记录和旧卡保留。若同 PID 另有合格 Offer，可重新选择该 Offer 后回归。

筛分门槛只控制新商品进入，不自动移除历史已选池商品。资格变化影响新的搜索和发送资格，但不删除历史证据。

### 5.3 TapLink 准备

必须先备链，再查询达人线索。链接准备不等待达人名单凑齐。

新建链接统一使用以下分佣原则：

- 机构收益至少 1 个百分点、优先 2 个百分点；
- 达人佣金至少比当前公开佣金高 1 个百分点；
- `机构收益 = min(2, 总佣金 - 公开佣金 - 1)`；
- `达人佣金 = 总佣金 - 机构收益`；
- 所有比例使用精确数值计算。

有效旧链优先复用，但必须同时满足：当前商品资格合格、机构收益 `>=1`、达人佣金高于当前公开佣金、账号/市场可见且 PID/活动/佣金绑定一致。多条旧链先选达人佣金最高，同佣金优先已有使用记录。

“旧卡佣金不一致”指旧卡创建时冻结的达人佣金与当前选中 Offer 的达人佣金不同。例如旧卡创建时为 12%，后来平台 Offer 或分佣规则重算为 13%；旧卡本身没有被篡改，只是它不再代表当前方案。此时旧卡继续保留，该位置进入待重建；新卡按当前方案创建并核验后，新的发送批次冻结到新 `listId`。

创建、复用、清理和移除已选商品是不同动作。未知创建或删除保留原意图核验，不生成替代意图。暂时缺货、混合有效列表和未知状态不作为删除依据。

旧卡采用统一 A 规则：主流程不根据“是否已被达人使用”区分删除权限，也不自动删除任何旧卡。当前方案需要新卡时创建并核验新卡，后续新发送冻结到新 `listId`；旧卡只进入独立清理流程，清理必须有明确范围、健康判定、删除意图和删除后回读。

TapLink 采用允许短期误差的快照规则：当前活跃材料每 48 小时批量刷新一次，全部链接库存每周完整刷新一次。两次刷新之间、刷新任务失败或延迟时，以上一次成功快照为准，不因“已到期但尚未刷新”阻塞达人查询、组批或发送；页面必须显示最后成功刷新时间和是否逾期。新建链接仍须在创建后立即回读一次，以取得确定的 `listId` 并结算原写入意图。

正式组批和逐条发送不再额外远程复读 TapLink。用户接受刷新窗口内偶尔出现旧链接失效：若平台在发送时明确拒绝该卡，只将对应 PID 转为等待刷新并继续处理其他成员；若发送结果本身未知，仍按发送意图的未知结果规则核验，不能把它当成普通链接失效自动重发。

### 5.4 达人线索与身份

- 只使用同 PID 的正销量达人证据；销量为 0 的线索过滤。
- 未查 PID 优先，按累计销量降序；已查 PID 默认 7 天后进入刷新队列。
- Kalodata 额度耗尽后停止并保留断点，不用未到期 PID 凑批次数字。
- 达人身份按 handle 去重查询一次。Find 精确匹配后取得 OECID；已明确搜索不到的 handle 保留记录但不自动重复查询。
- OECID 是同市场稳定主键。改名不能丢人、重名不能串配；一个已确认身份可以承载该达人名下多个商品位置。
- 无 OECID 的线索不能进入发送池，不伪造身份。

### 5.5 发送池与选择

发送池位置是“达人×商品”，但以下状态按达人共享：身份、冷却、新联系额度、人工接管、拒联和当前关系案件。

- 达人之间按经营优先级排序；达人内部优先达人佣金更高的合格商品，再按稳定排序与来源定序。
- 达人优先级与商品选择分成两步：先用该达人所有当前有效位置里的最佳线索强度（最小 rank）决定“这个达人排第几”；再在该达人内部按达人佣金最高 → rank 更小 → 全托优先 → PID 定序选择“这次发哪个商品”。换商品不改变该达人的队列位置。
- 同一达人一次只选择一个最优位置进入当前发送批次，其他位置保留等待。
- 商品失效会将相关位置移出可发层，但不删除位置、达人关系或历史链接；商品恢复并重新核验后可回归。
- 已发送、冷却、等待回复、人工接管、拒联和结果未知必须分层显示，不能用一个“不可发”数字混在一起。
- 未解决回复和人工接管属于达人级冻结：该达人名下所有 PID 位置暂停；同一 PID 对其他达人仍可正常排序和发送。案件解决并交还后，该达人全部位置重新计算。

### 5.6 发送与结果

- 本地保护性新联系额度以机构×市场共享，当前实现为滚动 24 小时 500 人；它是保守门禁，不等于平台公布额度，也不是任务目标上限。
- 单达人无回复前最多 5 条我方消息，商品卡计 1 条；达人回复或有有效采用证据后按当前关系规则解锁。
- 商品卡和文字均精确回查成功，才计 1 个完整触达达人。
- `flight ∈ {3,4}` 且有 `serverId` 是已知成功口径；`flight < 0` 是单达人限制，只结束该达人，不停止整个账号。
- 超时、回执缺失或 `unknown/result_unknown` 必须暂停并核验原意图，禁止盲目重发。
- 发送窗口结束、本批数量到顶、本地额度到顶、平台账号级额度、单达人限制和 unknown 是不同结果，页面必须分别说明。

当前真实发送保持暂停；新执行器第一次真实发送必须由用户在页面明确点击启动。历史授权或只读预检不能自动恢复发送。

### 5.7 收信、回复与人工接管

- 收信监控与外发分离；只读监控运行不等于允许自动回复。
- 同一达人最后一条文本消息后等待 60 秒再合并判断。
- 图片/截图默认转人工，直到多模态能力和业务案例完成单独验收。
- 普通事实查询和可验证标准诉求可自动准备答案；超出商业条件、样品费、Boost、补寄、赔偿或信息不足时转人工。
- 人工接管、拒联、待回复、冷却和事项完成是不同状态。人工明确交还后，Agent 从最新事实继续，不重复旧动作。
- AI 自动回复当前由用户暂停，必须保持关闭，直到用户明确恢复并完成案例验收。

## 6. 页面与信息架构

| 页面 | 主要任务 |
| --- | --- |
| 货盘 `/catalog` | 采集、筛分、入池、备链、线索队列和 OECID 阶段 |
| 流程演示 `/flow-demo` | 使用完全虚构数据解释 PID→发送池流程、筛选、刷新、门禁和锁；不连接后端 |
| 合作工作台 `/workspace?mode=second-live` | 发送池、监控与回复、回复预演、统计和系统状态 |
| 匹配研究 `/opportunities` | 一发 V2 与结构匹配研究 |
| 达人库 `/creators` | 稳定身份、别名、画像、人工资料与来源证据 |
| 运行页 `/ops` | 手动作业、可选定时、账号/身份就绪与异常 |

页面设计原则：

- 主页面不铺满逐行明细；先给漏斗、覆盖、缺口、阻塞和动作，明细按需展开。
- 每个外部动作显示账号、范围、是否平台写入、当前进度、停止原因和最后证据。
- 所有数量必须能对账；恒等式不成立时拒绝展示“看起来合理”的结果。
- 准备完成、进程存活、平台受理、完整送达和业务合作结果分别展示。

## 7. 完成标准

V1 完成必须同时满足：

1. 用户可以创建明确人数的 IT 二发任务并确认一次；
2. 系统按当前货盘和商业规则准备足量正式成员与候补；
3. 每位成员有稳定 OECID、同 PID 正销量证据、当前合格商品方案、可用 TapLink 和固定模板；
4. 暂停/重启/跨日可以从持久断点继续，不重复外部写入；
5. 发送按窗口、额度和账号能力执行，卡＋文字逐项回查；
6. unknown、平台拒绝、单达人限额和账号级额度分别处理；
7. 收信、加橱窗、人工事项和回复预演可从真实事件核对；
8. 页面数字能回到台账和原始证据；
9. 真实发送与自动回复均经过独立用户启动和验收；
10. 离线测试、服务运行、平台回执和业务结果分开报告。

## 8. 当前路线图

1. 稳定 V1 货盘、身份、发送池和监控读侧；
2. 将发送预检接入持久批次、start/stop 和现有执行器；
3. 取得账号级平台额度信号并固化自动停止语义；
4. 建立“真实回复 → 用户判定 → 正反例 → 可审计规则”的回复预演；
5. 完成 IT V1 端到端验收；
6. 再推进一发 V2、MX/BR 和 WhatsApp。
