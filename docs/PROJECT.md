# BDHub-Agent 项目文档

状态：当前项目与产品真相源。最后整理：2026-09-20。

本文回答“系统要解决什么问题、为谁服务、业务如何运行、什么算完成”。后续开发必须先符合本文；实现方式见 [技术文档](TECHNICAL.md)，当前开发进度见 [Codex 接管状态](handoff/codex-takeover-20260919.md)。

## 1. 项目目标

BDHub-Agent 是面向 TikTok 达人经营的独立系统，目标是在 1–2 人运营团队下，持续完成商品准备、达人发现、触达、回复服务和合作结果跟踪，并逐步替代旧 BDHub。

系统的核心不是“生成文案”或“导出名单”，而是形成可恢复、可核验的经营闭环：

```text
货盘发现
  → 商品资格与方案确认
  → TapLink 准备
  → 达人线索发现
  → 稳定身份与关系校验
  → 指定数量备料
  → 分批触达与逐项回查
  → 收信、服务与人工接管
  → 合作结果和经营证据
```

## 2. 用户与运营方式

- 主要用户是 BJN 的 1–2 名达人运营人员。
- 用户负责市场、商品范围、商业条件、预算、优先级和超出规则的业务决定。
- 系统自动完成有明确规则、可查询事实和可验证结果的步骤。
- 页面只重点展示：已处理结果、等待条件、异常阻塞和需要人决定的事项。
- 同一达人由一个关系控制统一协调；商品、样品、佣金和渠道按带时间的事件与事项保存，不用一段会过期的“关系摘要”覆盖多 PID 事实，也不建立互相冲突的多个负责人。

## 3. 分阶段范围

### V1：意大利二发闭环

V1 首先完成意大利 TikTok IM 二发：找到曾推广相同 PID 的正销量达人，为其提供当前有效、佣金更高的商品卡，邀请再次制作短视频或 LIVE，并跟进回复和合作结果。

V1 必须覆盖从货盘准备到结果证据的完整闭环，不能停在名单、草稿或人工逐条建议。

### V2：一发与更多市场

- 一发主动推品作为 V2 独立流程，不与二发的历史同品证据混用。
- 意大利 V1 是后续市场的参考标准，但不是自动授权。目标市场为比利时、巴西、德国、日本、马来西亚、墨西哥、荷兰、菲律宾、新加坡、泰国、英国、美国和越南；每个市场按[多市场接入标准](architecture/market-rollout-standard-v1.md)逐项验收。
- IT、BR、MY、UK 使用同一套市场页面、双账号身份、Campaign 与独立市场 plan；其余目标市场先使用同一页面结构展示未验收状态。实际开关、进程和业务数量以当前交接页及本机台账为准，不从页面上线推断执行授权。
- 达人可见内容按市场固定语言：IT=`it-IT`、BR=`pt-BR`、MY=`ms-MY`、UK=`en-GB`。二发正文、Agent 固定回复、TapLink 商品短名和卡名都必须来自当前 market；中文只作运营辅助翻译，不得作为发送正文，也不得从 IT 或其他市场回退模板、短名或命名配置。
- 支持全托的市场必须执行“采集 → 本地筛选 → 选入平台已选商品 → 标准 TapLink”链路；采集完成不能替代选入，选入完成也不能替代建链。采集策略统一为首次/月度一级类目完整读取、其余周更普通读取。IT/UK 支持全托，BR/MY 只走 Campaign；实际启停状态以当前台账为准。
- Kalodata 请求必须显式绑定市场区域和币种：IT=`IT/EUR`、BR=`BR/BRL`、MY=`MY/MYR`、UK=`GB/GBP`；任何新市场不得沿用 IT 的 header、referer、队列时钟或线索台账。
- 首期渠道是 TikTok IM；WhatsApp 在身份、授权和执行链完成后接入。
- IT 的单点成功不能自动开放其他市场、账号或渠道。

### 当前不自动扩展的范围

- 样品审批、付费投放、赔偿、MCN 签约和素材制作不是 V1 默认自主动作。
- 不因页面出现入口或只读接口成功，就宣称真实写能力已开放。
- 旧 BDHub 只作为协议和历史事实参考，不继续在旧系统叠加新产品能力。

## 4. 核心业务对象

| 对象 | 业务含义 |
| --- | --- |
| 市场/机构 | 经营、额度、账号、语言和授权的隔离边界 |
| 商品方案 | 同一 PID 下具体来源、活动、期限、佣金和资格的完整组合 |
| TapLink | 与商品方案绑定、经核验可发送的商品卡材料 |
| 达人 | 同市场以 OECID 为稳定主键；handle 是带时间的别名 |
| 线索 | 某达人曾推广某 PID 的来源证据，不等于已具备发送资格 |
| 位置 | 达人×商品的可经营机会；冷却、拒联和额度仍按达人统一判断 |
| 工作流运行 | 一次每日、每周或人工触发的后台审计范围，含阶段 generation 与断点 |
| 发送意图 | 一次不可变外部写入意图及其回执、回查和结果状态 |
| 合作事项 | 达人的当前诉求、负责人、下一步、等待条件和关闭证据 |

## 5. V1 完整业务流程

PID 维度的来源、选入、建链、刷新、核验与清理统一按 [PID 生命周期树](architecture/pid-lifecycle-v1.md) 执行；后续达人和发送只能消费其中的 `material_ready` PID。

### 5.1 自动运营工作流

各启用市场以不可变 `workflow run` 推进货盘、TapLink、Kalodata、OECID 和发送池；该 run 只作后台审计，业务页面不再要求运营创建批次或逐步确认。

- 自动运营总开关默认关闭；开启后按到期来源统一运行 Campaign、TapLink、Kalodata、OECID、发送池与收信。关闭后不启动新主链，收信已有 checkpoint 保留。
- Campaign 默认每 2 天完整刷新一次；全托每周普通刷新一次。支持全托的新市场首次采集使用一级类目完整刷新，此后每 30 天再做一次一级类目完整刷新；未到月度时的周更不传类目。
- 全托类目快照是已核实的覆盖基线；普通周更受接口结果窗口限制，只更新与该基线重叠的 PID。普通周更独有的 PID 保留为读取证据，不自动扩充类目覆盖，也不能用较窄的普通查询替换覆盖 head。只有新一轮类目完整发布或用户明确接受其部分覆盖，才能更换覆盖基线；已提交或结果未知的选入意图仍只按原意图核验。
- 货盘来源必须完成本轮完整读取、筛分和恒等式核对，才原子发布 generation；半成品不进入下游，上次完整版本继续提供业务数据。
- 只有用户对一轮已停止采集作出明确决定时，系统才可把现有商品冻结为 `accepted_partial/operator_accepted_partial` 并发布给下游；页面必须永久显示实际覆盖和“用户接受的部分快照”，不得称为完整覆盖。2026-09-21 的 UK 首轮快照为 64,089 个唯一商品、4,280 页、13/30 个一级类目完整。
- 全托首次/月度完整刷新按平台实时返回的一级类目树分片读取；每个一级类目必须独立到达 endpoint 末页并满足去重数＝该类目 reported total，全部分区完成后再跨类目按 PID 去重发布。类目间重复不重复计商品，单一类目若仍触及平台 10,000 结果窗口则如实记录该分区边界，不把分片总量冒充无上限全市场总量。
- IT 若某一级类目完整到达末页、返回行数精确等于 reported total，但行内存在重复 PID，先对重复页附近做带回执补洞；仍不足时完整复读该类目。只有完整复读新增为 0，或重复页精确复现，才能把差额记录为 `stableDuplicateRows` 并继续；商品数始终报告唯一 PID，不把重复行当商品。
- 普通周更在接口末页若返回行数精确等于 reported total，但唯一 PID 少于行数，同样先对重复页附近作带回执补洞。若找到缺失 PID，以补齐后的唯一数发布；若差额至多 `max(5, reported total/1000)`，且全部重复页精确复现、没有新增 PID，才单列稳定重复行并发布本轮普通查询。`reported total` 是平台行数，业务商品数始终是唯一 PID；未取得复读证据时保持 `partial`，不替换上次完整覆盖。
- TapLink、Kalodata 和 OECID 按同一 workflow generation 串联。Kalodata 以范围完成或真实额度耗尽作为阶段终点，正在读取的 PID 不发布部分结果；最多两个市场并行读取，各市场数据库、region、currency 和断点保持隔离。
- Campaign 每 2 天更新时先回查上次未知加入意图，再实时读取可加入列表并自动加入当前合格活动；只有加入结果全部明确后才重新采集已加入 Campaign、筛分商品并进入建链。任何未知加入只回查原意图并暂停主链。
- TapLink 准备先读卡并确认真实缺链范围，再为所有缺链 PID 补齐经验证的意大利语短名；短名仍有缺口时不得用截断商品标题继续创建。验证码只允许同账号求解后重放同一个冻结请求一次，再次挑战即暂停。
- 后台保存每阶段输入/输出 generation、断点、计数、平台写入数和停止原因；进程存活不等于业务完成。
- 首页只保留自动运营、全托周更新和持续自动发送三个高频控制；正常运营不需要逐项启用或“立即运行一次”。具体时间进入运行与设置，运行中的主链仍提供安全停止。

### 5.2 货盘采集与筛分

全托主来源固定为“高机会商品 → 仅全球销售商品”。默认入池条件：

- 累计销量 `>= 300`；
- 有评分时评分 `>= 4.0`，无评分允许；评分值 `0` 的语义未核实时不自行解释；
- 总佣金率减公开佣金率 `>= 2` 个百分点；
- 全托商品不要求库存数量；库存缺失、0 或低于 100 不因数量被拦截；
- 平台明确下架、治理、失效仍然拦截。

Campaign 非全托是独立来源：必须核对 ACTIVE、剩余期限、普通商品库存和额外条款，不能套用全托的无库存例外。评分大于 4 是二发偏好；剩余期限默认要求大于 45 天。期限是动态资格：加入 Campaign 时大于 45 天不产生永久资格；后续刷新发现剩余期限 `<=45` 天时，该 PID 的未发送位置退出严格发送池，`catalog_current_binding` 同步变为 `inactive`；同一 PID/Campaign 条款变化则变为 `waiting_refresh`。历史线索、已发送记录和旧卡保留。若同 PID 另有合格 Offer，可重新选择该 Offer 后回归。

筛分门槛只控制新商品进入，不自动移除历史已选池商品。资格变化影响新的搜索和发送资格，但不删除历史证据。

### 5.3 TapLink 准备

必须先备链，再查询达人线索。链接准备不等待达人名单凑齐。

新建链接统一使用以下分佣原则：

- 机构收益至少 1 个百分点、优先 2 个百分点；
- 达人佣金至少比当前公开佣金高 1 个百分点；
- `机构收益 = min(2, 总佣金 - 公开佣金 - 1)`；
- `达人佣金 = 总佣金 - 机构收益`；
- 所有比例使用精确数值计算。

从本规则生效起，发送材料只认“当前标准链接”：使用 `commission-1-to-2-v1` 计算分佣，使用该市场登记的 `link-naming-{market}-v1`（IT 兼容版本为 `link-naming-v1`）和模板 `🔥 BJN {short_name} {creator_percent}% {tail}` 命名，并精确绑定当前 market、PID、来源和 Campaign。`short_name` 必须是该市场 locale 的本地化商品短名；非 IT 市场缺少本地化短名时直接停止建链，不能读取 IT 缓存或截断原始标题。只有上述版本、语言、字段和平台回读完全一致的卡才能成为该商品的当前 `listId`。

历史链接不再参与复用判断，也不再形成“佣金不一致”状态。即使历史卡仍可用、佣金满足最低条件或曾被达人使用，也只作为历史记录保留；当前合格商品如果没有标准链接，就按统一规则新建一张。若完全相同的标准链接已经由本系统核验存在，则直接使用该标准 `listId`，不重复创建。

上线前执行一次标准链接补齐：遍历当前全部合格商品方案，为每个方案确认或创建唯一标准链接，并保存唯一的当前 `listId`。发送池只读取这个当前 `listId`，不再从平台历史卡中临时挑选或比较佣金。

创建、复用、清理、移出当前发送投影和平台删卡是不同动作。未知创建或删除保留原意图核验，不生成替代意图。暂时缺货、混合有效列表、未知状态以及“只是不符合当前内部佣金/期限门槛”都不作为平台删除依据。

旧卡不因“旧”、佣金变化或是否被达人使用而删除，但永远不再用于新发送。只有平台回读确认整张列表失效时才可进入删除候选，并在删除后完整回读确认；BR/UK 在各自单条删除 canary 验证前只做本地停用和只读扫描，不执行平台 DELETE。

TapLink 按商品来源使用两个简单周期：Campaign 商品每 2 天刷新来源时同时核验对应 TapLink；全托已选商品的 TapLink 每周统一核验一次。两次刷新之间、刷新任务失败或延迟时，以上一次成功结果为准，不阻塞达人查询或发送。新建链接仍须在创建后立即回读一次，以取得确定的 `listId` 并结算原写入意图。

材料作业在“运行与设置”展示共享北京时间。周一 04:30 可执行失效卡清洗，Campaign 每 2 天 07:00、全托按周形成完整货盘 generation；货盘发布后才进入标准链接准备。清洗、核验与创建使用不同持久意图，任何 unknown 都只回查原意图；失败期间最后一次成功且仍为当前 Offer 的绑定继续生效。

正式组批和逐条发送不再额外远程复读 TapLink。用户接受刷新窗口内偶尔出现旧链接失效：若平台在发送时明确拒绝该卡，只将对应 PID 转为等待刷新并继续处理其他成员；若发送结果本身未知，仍按发送意图的未知结果规则核验，不能把它当成普通链接失效自动重发。

### 5.4 达人线索与身份

- **A 类销售线索**：每个 PID 读取近 14 天、最多 20 条正销量达人线索；销量缺失或 handle 非法的记录过滤。
- **B 类内容线索**：不属于同一达人×PID A 类的记录，如果最近 30 天存在精确关联该 PID、当前累计播放量 `>=1,000` 的视频，也形成一条线索；不要求该视频出单。同一达人×PID 有多条达标视频时，只取当前累计播放量最高的一条作为代表视频，不求和、不计算播放速度；播放量并列时取发布时间较新的视频。
- B 类首次读取完整回溯 30 天，之后每 7 天重新读取该 PID 最近 30 天的视频列表，以发现原来低于 1,000、后来跨过门槛的视频；已经确认作者的视频不重复查作者。视频跨过门槛时仍在 30 天窗口内才进入，超过 30 天后按本地发布时间退出当前资格。
- 视频列表读取不设置人为的每日请求数或单 PID 视频数业务上限；平台返回真实额度耗尽时保存断点并停止，下次从断点继续。只有完整覆盖当前时间窗口的结果才能发布。
- Kalodata A 类请求按 `revenue DESC`，同时保存数值 GMV、市场币种、`sourceRank` 和原始字符串；只有同一市场当前采集口径的数值 GMV进入排序，原始金额字符串只作证据。
- PID 在查询 Kalodata 之前只有商品累计销量可用于排序，不使用或推测 PID GMV。未完成任务先从断点继续；其余首次 PID 按商品销量降序，到期刷新 PID 按最早成功时间优先、商品销量作为并列项；销量缺失按 0，最终以 PID 升序稳定排序。
- Kalodata 额度耗尽后停止并保留断点，不用未到期 PID 凑批次数字。
- 达人身份按 handle 去重查询一次。Find 精确匹配后取得 OECID；已明确搜索不到的 handle 保留记录但不自动重复查询。
- OECID 判定只有三种结果：精确 handle 返回稳定 OECID＝`resolved`；平台正常返回且没有精确 handle＝`unresolved/搜索不到`；验证码、签名、登录维护、共享退避、超时或请求失败＝`blocked`。`resolved` 与 `unresolved` 都是已判定终态，后续线索复用结果、不再搜索；`blocked` 不是搜索不到，账号恢复后从原断点重试。
- 页面主卡只显示 **已就位、待补充身份、搜索不到**；`blocked` 与尚未提交都归入“待补充身份”的后台待处理数，不再单独显示“被挡住”业务卡。技术原因只在任务异常时按需展开，不能把 blocked 改名或计入搜索不到。
- 平台要求验证时使用项目已有的同账号滑块验证与原业务请求重放；验证成功且重放仍为 HTTP 200/code0、无验证头后才能继续判定。验证失败不能落 OECID 或 unresolved。
- OECID 是同市场稳定主键，handle 只是带时间的别名。达人改名后，同一 OECID 归并到原 `creatorId`，并保留 PID、发送历史、冷却、拒联和未结事项；重名不能串配。
- 无 OECID 的线索不能进入发送池，不伪造身份。

### 5.5 发送池与选择

发送池位置是“达人×商品”，但以下状态按达人共享：身份、冷却、新联系额度、人工接管、拒联和当前关系案件。

- A 类整体排在 B 类之前。同一达人×PID 同时命中两类时合并为一条 A 类位置，并保留视频证据。
- A 类按同一市场、同一采集口径的达人×PID近 14 天 GMV 排序：`GMV DESC → 正销量 DESC → sourceRank ASC → PID ASC`；原始金额未能解析为当前市场数值时不得猜测或跨币种比较。
- B 类只按代表视频当前累计播放量排序：`代表视频播放量 DESC → 代表视频发布时间 DESC → PID ASC`；不计算多条视频播放量总和，也不计算播放速度。
- 先按上述统一位置顺序取每位达人的第一个当前有效位置作为发送槽位；同一达人的其他位置保留等待。因此达人同时有 A、B 类位置时先发 A 类，B 类不会挤占明确出单线索。
- 佣金只决定商品方案是否合格和标准卡内容，不再作为达人内部商品排序键；A/B 来源优先级仅按本节已确认的规则执行。
- 同一达人一次只领取一个最优位置进入持续发送，其他位置保留等待。
- 商品失效会将相关位置移出可发层，但不删除位置、达人关系或历史链接；商品恢复并重新核验后可回归。
- 业务层只显示三种结果：**可发送、等待中、暂不参与**。等链接、等身份、冷却、未结回复和同达人其他 PID 都是“等待中”的原因；商品失效和明确排除是“暂不参与”的原因；已发送属于历史而不是池状态。
- 未解决回复和人工接管属于达人级冻结：该达人名下所有 PID 位置暂停；同一 PID 对其他达人仍可正常排序和发送。案件解决并交还后，该达人全部位置重新计算。

### 5.6 持续发送与结果

- 本地保护性新联系额度以机构×市场共享，当前实现为滚动 24 小时 500 人；它是保守门禁，不等于平台公布额度，也不是任务目标上限。
- 单达人无回复前最多 5 条我方消息，商品卡计 1 条；达人回复或有有效采用证据后按当前关系规则解锁。
- 商品卡和文字均精确回查成功，才计 1 个完整触达达人。
- 二发模板使用 16 个跨市场一致的固定模板；IT 使用意大利语，BR 使用巴西葡萄牙语，MY 使用马来语，UK 使用英国英语，各市场只翻译、不改变语义。模板正文只允许 `{creator_handle}`、`{product_name}`、`{creator_commission}` 三个参数，其中商品名和达人佣金必填。
- 真实发送和持续发送开关必须先有至少 10 个当前 revision 的模板审核为 `approved`；模板任一市场正文或 IT revision 变化都会使对应审核回到 `pending`。同一市场、同一达人已经进入发送意图或文字已尝试的话术 ID 不再使用，后续触达按固定顺序选择下一个已批准且未使用的话术；全部用完时等待人工补充，不自动循环。
- 二发批量模板、人工回复模板和 Agent 场景固定模板是三个独立域，不能互相读取或覆盖。
- `flight ∈ {3,4}` 且有 `serverId` 是已知成功口径；`flight < 0` 是单达人限制，只结束该达人，不停止整个账号。
- 超时、回执缺失或 `unknown/result_unknown` 必须暂停并核验原意图，禁止盲目重发。
- 用户不再操作冻结批次；执行器领取每一位达人前，把 creator/OECID、PID、Offer、`currentListId`、模板 revision、最终正文、关系控制 revision 和去重键写入不可变 `cycle_delivery` 快照。
- 历史 `cycle_bulk/cycle_bulk_freeze/cycle_bulk_candidate` 只读保留，不构成当前授权；旧冻结入口固定退役。
- 窗口结束、本地额度到顶、平台账号级额度、单达人限制和 unknown 是不同结果，页面必须分别说明。持续发送开启时在下一日窗口继续，不重复 delivery。

16 条固定二发话术已按当前内容完成审批，后续正文或语义变化仍按新 revision 重新审批。当前真实发送保持暂停；审批通过、代码发布或只读预检均不能自动恢复发送，第一次新执行器真实发送仍须由用户在页面明确启动。

### 5.7 收信、回复与人工接管

- 意大利两个机构账号固定分工：ACC6 是通信账号，负责收信监控、IM 发送、Agent 回复、OECID 获取和达人画像；ACC9 是货盘账号，负责货盘读取、Campaign、商品选入和 TapLink 创建/核验。两者不自动换岗。页面必须把“固定职责”和“只读实测能力”分开，不能因两个账号通过相同探针就显示成相同职责。
- 两个账号每 72 小时分别在北京时间 14:30、14:40 进入串行维护。立即重登必须打开可见浏览器并自动填写已保存凭据；验证码或二次验证允许在该窗口人工完成。新浏览器、HTTP 与 IM 身份只写入本项目，三者共同验证后才原子发布；失败保留最后一代可用身份，不修改旧 BDHub 身份目录。
- 收信监控与外发分离；只读监控运行不等于允许自动回复。
- 新消息到达后立即冻结该达人名下全部 PID；删除固定 60 秒逐达人合并，改为集中批处理尚未分类的事件。
- Agent 自动外发与持续二发必须使用严格不重叠的北京时间窗口，不建立谁优先于谁的规则。当前默认 Agent 集中回复为 `15:00–16:00`，随后保留 30 分钟缓冲，二发为 `16:30–24:00`；保存设置时服务端拒绝重叠窗口。等待二发窗口的进程不能阻塞 Agent 窗口，真实正在 dispatch 的外发仍由同一账号写门禁串行化。
- 运营层只允许五种动作：`no_reply`、`sample_self_service`、`collaboration_ack`、`link_usage`、`human`。
- 不做事实型智能回复，不调用当前佣金、样品状态、物流、商品目录或链接状态等工具生成答案。模型只选择动作、意图和证据；回复正文只使用人工确认的固定模板。
- 样品/物流、合作确认和唯一 PID 的链接使用可以使用固定模板；付费、预算、目录、WhatsApp、Boost、投诉、拒联、链接打不开、佣金异常、多 PID 不明确、多意图、附件或无法理解时转人工。
- DeepSeek 是当前 Agent 分类器，已有人工 `turn_review` 时人工结论优先；Jev 保持同集 challenger。模型不能生成自由正文、修改达人/PID 状态或把自己的输出当训练真值，最终动作和发送仍受固定动作、确定性守卫、时间窗、持久意图和精确回查约束。
- 上下文按外发 episode、入站 turn 和案件保存，不把整段聊天每次全部交给模型，也不用会随商品和时间过期的自由“关系摘要”代替事件事实。
- 人工接管、拒联和事项完成是内部控制与历史，不增加主发送池的业务状态。会话工作台默认打开“需人工”；人工明确交还后，系统从最新事件继续，不重复旧动作。
- 达人合作状态固定为 `normal / collaborated / paid / rejected`。加橱窗只把系统默认 `normal` 自动升级为 `collaborated`；人工选择永远优先。`paid/rejected` 阻止该达人全部 PID，其他状态继续按原门禁计算。
- 会话按可用视口铺满三栏。每条达人入站正文可按需翻译成中文；“确认人工回复”直接结算当前 case/pending，本身不发送消息，也不要求先有人工发送记录或另写处理结果。合作状态用紧凑四态选择器管理；`paid/rejected` 按达人共享并阻止其全部 PID 后续进入发送池。
- 达人“添加到橱窗”事件作为明确的系统消息进入会话队列摘要和时间线。会话分类只保留“需人工 / Agent 回复 / 已完成 / 全部”；待 Agent 回复与 Agent 已处理统一在“Agent 回复”中，以“待回复”标记区分，不再设置含义模糊的“处理中”。
- “达人与事项”同时展示当前 GMV、视频/直播 GMV、粉丝、销量、视频均播、真实回复次数和加橱窗次数；来源时间必须可见，缺值显示未知而不是 0。
- Agent 执行器已经接入三条固定模板和 `no_reply` 本地结案；`human` 永不自动发送。开关默认关闭，只有用户在 Agent 设置页明确启用后才启动集中回复 worker，代码发布和服务重启都不能代替该动作。自动执行仍只在 `15:00–16:00` 窗口运行；用户明确要求立即处理当前合格队列时，可使用带 request ID 的一次性授权运行，每次仍只发送一个持久意图并精确回查，出现 unknown 立即停止。

### 5.7.1 下一版多轮 Agent 回复（2026-09-23 已确认）

当前五动作/三固定模板实现是历史 V1，不再作为下一版目标。新 Agent 依据同一达人已发生的双向消息、当前市场语言、关联商品事实和版本化回复指南，按上下文自然组织正文；参考答案约束处理方式和语气，不逐字重复发送。无新问题的感谢/表情可不回复；已尝试无效的方法不重复推荐；多个问题逐项回应。事实与执行状态由代码和台账核验，模型不自行改变身份、金额、资格、暂停或结果。

常见样品申请、物流、损坏/错货/补寄、佣金到账与结算、合作确认、内容形式、商品卡用法、原链接佣金较高、其他商品/目录与普通推广支持由 Agent 沟通。用户已明确：样品申请不到且没有产品可用时自然结束，不专门追问旧产品是否仍在；物流与售后不转人工、不承诺代查催发；佣金结算问题给可能原因和平台查询路径，不推断真实退款；内容形式由达人按自己的风格决定；要其他商品时解释二发范围和未来商品网站，不编造可申请的样品链接；推广支持只确认会反馈商家，不承诺投放，不另建提报待办。

商品卡打不开、无法加入橱窗、我方明确告知的比例与卡展示不符、固定费用/报价、提供真实外部联系方式、明确要求不再联系、针对我方合作条件或历史承诺的投诉，先用市场语言简短确认再转人工。仅请求换渠道而未提供联系方式时先索取一次，等对方补充后才转人工；不明确的图片/语音先请求一次文字说明，仍无法理解再转人工。多个问题同时出现时先完整回应，按其中需要人工的事项交接。转人工即暂停同达人全部 PID 的二发；首次确认发送后 AI 不再与人工并行回复。人工队列提供手动解除按钮：普通处理完成解除人工锁并重新按二发门禁判断；继续处理保持暂停；不再联系与付费合作即使人工事项完成仍排除普通二发。待达人补充期间也保持本轮冻结，不自动催问或超时放行。

页面展示实际 provider、model、API endpoint、完整编译提示词、当前生效指南版本、每次真实输入/输出、分流理由与发送结果；提供同合同的多轮试聊而不执行平台写入。按会话所属市场输出 IT=`it-IT`、BR=`pt-BR`、MY=`ms-MY`、UK=`en-GB`，入站偶尔换语言不改变发送语言。新代码、发布、试聊、影子评测和原有开关状态均不授权新执行器真实发送；首次真实发送须用户在 Agent 页面明确启动首条验证。首条送达后暂停，用户查看真实结果后再在页面选择继续自动回复。

完整动作边界、三条固定回复、上下文模型、DeepSeek/Jev 切换和真实数据评测见 [达人发送池与 AI 回复策略](architecture/creator-pool-and-reply-policy-v1.md)。

## 6. 页面与信息架构

| 页面 | 主要任务 |
| --- | --- |
| 运营首页 `/{market}` | 整条自动经营主链、异常与三个高频开关；正常日的默认入口 |
| 合作工作台 `/{market}/workspace/send`、`/history` | 当前市场发送池、16 条本地化模板与审核门禁、进程和结果历史 |
| 会话 `/{market}/conversations`、`/templates`、`/agent` | 同一三栏结构、严格市场隔离；空市场展示真实空队列，不回退意大利数据 |
| 货盘 `/{market}/catalog` | 四个固定 Tab：全托商品、非全托商品、达人线索、新建链接命名；不支持全托的市场保留全托 Tab 并显示明确空态，全托 API 与 worker 调用为 0 |
| 达人 `/{market}/creators` | 当前市场稳定身份、别名、画像与线索/结果统计 |
| 运行与设置 `/{market}/ops/kalodata`、`/jobs`、`/accounts` | Kalodata 身份、主链作业与时间、TikTok 账号身份代次；回复评测位于会话高级区域 |

页面设计原则：

- 主页面不铺满逐行明细；先给漏斗、覆盖、缺口、阻塞和唯一下一动作，明细按需展开。
- 货盘页的数量、口径和动作优先集中在表格中；大容器只用于区分业务阶段，不把每个数字都做成独立卡片。
- 不提供“全部市场”混合执行视图；14 个目标市场复用同一页面结构和组件。未验收市场显示状态但动作关闭；所有市场级 API 必须显式携带 market，空数据不得回退其他市场。
- 市场切换器分为“正式接入”和“待接入”：BR、MY、UK、IT 集中展示于正式接入组，其余市场进入待接入组。MY 当前暂停不改变其已接入分类，也不因切换页面获得执行授权。
- 达人详情把平台 Profile 经营画像与 Kalodata 当前商品线索分开展示。Profile 未取得时，GMV、粉丝等字段保持未知；可按 PID、币种和查询窗口展示已有的近 14 天商品线索 GMV，但不能把它称为达人全店成交额。顶部身份数只统计当前市场、当前线索范围内已判定的去重达人。
- 每个外部动作显示账号、范围、是否平台写入、当前进度、停止原因和最后证据。
- 所有数量必须能对账；恒等式不成立时拒绝展示“看起来合理”的结果。
- 准备完成、进程存活、平台受理、完整送达和业务合作结果分别展示。

## 7. 完成标准

V1 完成必须同时满足：

1. 正常日无需逐项操作，运营首页能核对同一 run/generation 的完整主链；
2. 货盘只发布完整 generation，Kalodata 在范围完成或额度耗尽后统一交给 OECID；
3. 每个被持续发送领取的位置有稳定 OECID、符合 A 类或 B 类规则的精确 PID 证据、当前合格商品方案、标准 TapLink，以及已冻结 revision 与最终正文的版本化模板；
4. 暂停/重启/跨日可以从持久断点继续，不重复外部写入；
5. 发送按窗口、额度和账号能力执行，卡＋文字逐项回查；
6. unknown、平台拒绝、单达人限额和账号级额度分别处理；
7. 收信、加橱窗、五动作回复分类、固定模板和人工事项可从真实事件与关联 episode 核对；
8. 页面数字能回到台账和原始证据；
9. 真实发送、自动清洗、自动建链与自动回复均经过独立用户启动和验收；
10. 离线测试、服务运行、平台回执和业务结果分开报告。
