## 2. 固定市场归属，弹性业务分工

每个账号在新系统中只属于一个市场，一市场恰好两个不同账号，Profile/设备身份也必须独立。不会自动给墨西哥、巴西或其他市场占用ACC1/8/11；后续按产品经理分配登记。

| 工作 | 默认主账号 | 备用条件 |
| --- | --- | --- |
| IM收信、二发发送、后续AI回复 | ACC6 | ACC9须先验证真实IM读取/回执和发送能力，并确认共享sender协调后才可接管未提交工作 |
| 货盘发现、刷新、已选对账 | ACC9 | ACC6空闲且相应能力有效，可在短任务边界临时承接 |
| 商品选入、Campaign加入、TapLink创建/维护 | ACC9 | 按动作逐项验收后启用，不从catalog_read推导写权限 |
| OEC身份与画像补全 | ACC9优先的目标分工 | 迁移前仍遵守已验路径；ACC6的12 QPS验收不迁移到ACC9，ACC9单独测量 |
| 本地筛选、统计、名称生成 | 不占平台账号 | 控制CPU/数据库资源，独立于平台租约 |

当前货盘读取、Campaign、商品选入和TapLink固定ACC9；通信、OECID与发送固定ACC6。历史断点保留原账号但不决定新任务路由，自动角色切换关闭。见[货盘读取迁移实测](../implementation/catalog-read-acc9-migration.md)。

## 3. 资源层与唯一归属

| 资源键 | 管理内容 |
| --- | --- |
| account/profile | 一个会话负责人、一个会话版本、账号内统一请求预算、验证与维护屏障 |
| institution＋market | 新联系额度、拒联关系、达人OEC去重、市场级暂停和平台级退避 |
| IM sender | 发送队列、请求节拍、投递去重、在途确认；ACC6/ACC9本轮证实需要共享此键 |
| conversation＋creator | 同一关系负责人，收信去重、接管状态、60秒合并窗口 |
| operation intent | 商品选入/建链/消息各自持久记录，固定参数、原执行账号、结果与核验证据 |

统一调度器先取得账号资源，再授权某项已验证能力。每个模块不能自行打开账号并独立叠加QPS。身份查询12 QPS、选入8 QPS是已有特定场景记录，不能相加，也不能套用给第二账号、IM或别的市场。

每个账号的会话负责人可管理多个本账号HTTP连接，保持单连接无并发重用，统一更新本账号验证状态。连接池、签名输入、Cookie和IM令牌不能从ACC6复制给ACC9。

## 4. 状态与调度

账号状态：`unassigned → validating → ready → leased → draining → refreshing/maintenance → validating → ready`。异常进入`cooldown/attention`；人工停用进入`disabled`。能力状态独立于账号健康：一个账号可读取货盘，不代表可以发送或建链。

1. 任务声明市场、机构、能力、优先级、到期时间、账号亲和与是否已有外部写入。
2. 两号均正常时按分工并行。没有匹配资源时进入明确的等待原因，不将busy记作平台失败。
3. 收信与在途核验及时处理；发送前定向商品核验属于发送阶段。普通后台扫描按页/批次保存断点，不能无限占用通信资源。
4. 每批结束检查维护、暂停、高优先级任务和账号健康；允许让出账号，不强杀在途请求。
5. 已提交写入保存原账号和意图。故障切换只接未提交任务；未知结果先核验。人工暂停新发送不阻止必要的只读结果核验；人工明确停用整个账号时等待人工处理。
6. 账号身份变化增加`session_epoch`，新任务只使用新版本；迟到回执可追加原意图证据，但旧持有者不能领取新任务。

03:00货盘日任务以市场＋业务日期＋类型形成唯一日意图，进入队列后由账号分配决定实际启动。断网或Mac休眠后补跑一次缺失作业，续用原断点。PID线索7天刷新是另一类任务，不能把每日货盘刷新解释为每日重新查询全部Kalodata PID。

## 5. 身份维护：两个周期任务

产品经理最新确认：无感身份更新每48小时、登录维护每72小时；取消5分钟周期巡检和6小时深度检查，也不再提前2小时维护备用账号。这覆盖本页旧版5/6/24/48周期设计。

| 层级 | 周期/触发 | 行为与完成证据 |
| --- | --- | --- |
| 无感身份更新 | 每48小时 | 从该账号自身已登录环境更新认证材料，验证后原子切换新版本；不先清空健康凭证 |
| 登录维护 | 每72小时，全天可排空执行 | 先排空实际在途请求；需要登录时使用本账号凭据，完成后独立记录last_login_success_at |
| 按需认证恢复 | 正常业务明确返回认证异常，或平台明确令牌过期 | 同账号有界恢复、验证机构市场与sender；不作为额外的周期巡检 |

调度器根据各账号最近一次对应动作的真实成功时间计算next_due，直接安排到期事件，不每5分钟主动巡检、不额外运行6小时探针。管理页面读取本地状态只用于展示，不发起TikTok健康探测。

已成功的业务读取可更新业务健康时间，但不得重置48/72小时维护基线。Cookie文件mtime只作观察，不能当作登录成功时间或有效期。刷新失败不得覆盖最后可用身份；取得新Cookie但机构/市场不符时拒绝发布。若登录维护同时完成身份更新且两者均有成功证据，可同步推进两种成功时间，取消重复到期的无感更新任务。

### 双号维护互斥

每号按自己的成功时间到期，不提前到70小时。全局同时只允许一个账号维护；同组另一号健康、且相应接管能力已验收时才交接未提交任务。两号同时到期时依次维护。若两号均不可用，保存队列等待恢复，不承诺两号失效时仍不停机。

有结果未知但已经没有HTTP请求在途时，先保存意图和核验任务；如果身份失效阻止核验，可维护原账号后再核验。不能让未知记录与身份维护互相等待形成死锁。

### 过渡期的实际执行状态

当前凭证及维护权仍属于旧版身份服务，新版只读引用现有账号资料与维护状态。`maintenanceExecutor=legacy_lifecycle`、`enableNewMaintenanceWorker=false`。本轮只更新新项目配置、策略和页面，未改旧服务实际周期；页面必须分别标注新版72小时计划和旧服务实际维护到期时间，不把新计划展示成已生效的运行状态。

移交时不只替换定时器：必须同步改为新策略的任务准入、maintenance_due检查、排空与重试，避免旧48小时门禁继续阻塞新版72小时计划。停止旧服务对指定账号的业务分配和维护调度，排空在途，建立新系统独立凭据提供器/存储，继承核实后的成功时间，再启用唯一的新维护执行器。当前不执行该交接，也不静默复制凭据。

由于不同登录账号共享IM sender，发送交接还必须覆盖整个“机构＋意大利市场”的旧发送入口，不能只把ACC6/ACC9移出旧账号池。切换时选择单一外发系统；若确需两个系统同时参与，必须先实现跨系统原子的sender写入门禁和共同额度事实源，现有只读冲突快照不足以完成这项保证。

## 6. 验证、故障与退避

| 情况 | 调度处理 |
| --- | --- |
| 普通网络超时 | 只读操作有界重试；写入超时进入原意图核验，不换号重做 |
| 账号验证挑战 | 复用现有同账号HTTP验证方案；暂停补入、收齐在途后统一验证并更新本账号会话 |
| 验证失败/权限拒绝 | 停本账号相关能力，记录原因与退避；不能循环切号掩盖错误 |
| 单账号失效 | 备用仅承接它已通过验收的未提交工作；没有能力证据时等待 |
| 机构/市场额度或限流 | 两号共享限额/退避，增加账号不增加每日500新联系额度 |
| 单商品失效 | 只暂停该商品的后续搜索/二发，按已确认规则保留历史链接 |
| 原账号返回迟到结果 | 追加到原意图并检查版本，不覆盖新账号任务、不重复确认计数 |
| 手动暂停发送/回复 | 最高业务开关，不因定时任务、账号恢复、主备切换或重启撤销 |

只读失败退避建议10秒、30秒、2分钟，连续异常进入能力冷却并告警；明确401/403/429不能作为普通网络错误反复重读。登录维护沿现有忙碌10分钟再检查、失败至少1小时再试的基线，主动故障恢复与周期作业共用意图和退避，避免两边重复登录。

## 7. 持久状态与接口合同

已实现登记：`config/market-accounts.json`只放账号别名、分工、证据位置与维护执行方，不保存Cookie/密码/令牌。`GET /api/market-accounts`返回脱敏登记和当前维护观察，不启动平台请求或刷新。

运行期需要的表：

- `account_binding`：市场、两号、角色、版本、启停及交接状态。
- `account_capability_evidence`：账号、机构市场、动作、会话版本、核验时间、证据和结果。
- `account_lease`：账号/Profile、任务、owner、epoch、心跳、期限。数据库租约与实际进程锁共同检查，超时不直接证明进程死亡。
- `account_session`：认证材料引用、epoch、健康时间、IM sender绑定；秘密留在凭据提供器，不进入业务表或模型上下文。
- `account_maintenance_intent`：动作、计划/硬期限、原基线、排空状态、结果、重试时间；成功时间只有真实成功后推进。
- `market_quota`与`sender_outbox`：前者按机构市场，后者按实际sender协调。

后续命令接口分开：绑定、暂停/停用、申请检查、申请身份更新、申请登录维护、验证备用能力、任务交接。每个命令返回持久意图和状态，不以HTTP200或Worker启动当作业务完成。管理页面只展示具体原因、下一次动作和需要人工处理的项目。
