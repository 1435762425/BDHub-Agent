### 3.2 唯一的结构性改动

现在批量发送的选人顺序由 `choose_candidates()` 自己排（windowEnd/units/creatorId）。改为：

> **池子的 `ready` 顺序决定"发谁、发哪个商品、什么顺序"；`choose_candidates()` 退化为发送前的安全复检**——不合格的带原因跳过（`cycle_bulk_item.reason`），不回写池子。

这样"页面上看到的就是将要发的"，同时一条安全闸门都没松。

### 3.3 页面显示

- 六层读数（复用 `lead-pool` 桥接）：可发 / 池中等待 / 冷却中 / 等回复 / 已排除 / 已发送
- **本次授信**：`500`（默认）/ `1000`（单选）
- **窗口**：开/关 + 起止时间输入 + 下次可发时间
- **样例 2–3 条** + 一行"本批共 N 条，按池子顺序取，完整名单不下发到页面"
- `确认并开始本批` / `停止`（跑完当前这一条就停）
- 本批进度：已确认 / 进行中 / 待核验 / 需处理，以及**停下来的原因**（额度到顶、窗口结束、结果未知、平台拒绝、你要停）

### 3.4 额度事实

现有实现的闸门是 `lib/cycle_delivery.reserve_contact()`：

- 只对 **`relationship.unlocked=0`**（从未互动过）的达人计数；**已解锁的达人不占这个额度**（现 62 人）
- 口径是 **滚动 24 小时**：`reserved > now-86400` 的预留 ∪ 近 24h 已发卡片，去重后 `>= 500` 即 `new_contact_capacity_reached`
- 当前实测：**近 24h 已发卡片 0、有效预留 0** → 这 500 额度今天是空的；池子里可发槽位 **1,593**，取 500 或 1000 都够

### 3.5 取得平台原生上限信号（用户的真实意图，也是 B.13 未完成的那一步）

用户原话：每天尽量发到上限，"今天后面就可以尝试发 500 个以上，这样子的话你就可以拿到发送上限的那个平台传来的那个接口信息是什么，然后后续你只要触碰到这样的信息，你就自动停止发送就可以了"。

**先查过旧版，平台信号不是完全未知——一半已知**（这就是"不要重复造轮子"）：

| 信号 | 含义 | 旧版口径（`01-BDSystem-V2/docs/current-system-truth.md:367`、`bdhub/send/dispatch.py:305,465`） |
| --- | --- | --- |
| `flight ∈ {3,4}` + `serverId` | 发送成功 | 判定成功的唯一口径 |
| **`flight < 0`**（如 -2） | **单达人触达上限**（"5 条无回复上限"：达人没回过就发不进去） | `outcome="send_limit"`；**是单达人终态，不暂停整个账号**，不重试，原始响应进 `raw_json` |
| `send timeout` | 平台写入**结果未知** | 必须写 `unknown`、暂停、人工核验，**禁止自动重试** |
| 账号/机构**每日新触达上限** | 尚未取得 | 新版 `second-cycle-speed-and-limit-test-v1.md:28` 明确："当前尚未观测到每日新触达上限返回，**不能提前编造错误码**，也不能认定所有拒绝都是日额度；本地 500 计数不作为平台信号" |

所以"探测"要探的是**账号级那一个**，而单达人那个已有结论：

1. 本地 500 闸门加一个**显式放宽档**（默认 500 自动停；可选"越界探测"），越界逐条发送；
2. 每条真实回执都落 `cycle_platform_signal`（已有 `outcome/native_status/check_code/check_message/response_ref` 字段）——**原始响应必须存下来**，否则下一次还是不知道；
3. 遇到**账号级**额度拒绝 → 固化成"平台上限信号"，之后所有批次默认认它、自动停整批；
4. 遇到 **`flight<0`（单达人）** → 只把该条标 `send_limit` 终态，**继续下一条**，绝不停整批、绝不重试；
5. 遇到 `unknown` → 停整批等核验（现有）。

### 3.6 到上限自动暂停（四种，都写进页面，并写清是哪一个）

1. **本批条数到顶**（500/1000）→ 正常结束
2. **本地 24h 500 新联系闸门** → `local_capacity_reached`（现有），写明"这是本地保守闸门，不是平台信号"、什么时候恢复
3. **平台账号级上限** → 探测到之后自动停，并显示平台原话
4. **单达人 `flight<0`** → **不停整批**，只标该达人（旧版口径）

另外：窗口结束 → 停在下一条、写明下次可发时间、断点保留跨日续发；结果未知 → 停整批等回查，**绝不从头重发**。

  → 先按缓存键、miss 再**按 pid** 兜一次。

## 5. ③ 回复预演与训练闭环

**这不是"打开自动回复开关"，而是"你教我"**：用真实回复反复出题，把你的判定沉淀成 Agent 的知识。

| 环节 | 内容 |
| --- | --- |
| 出题 | 一条真实回复（意语原文）＋背景：我们发过的商品/佣金/卡片、关系状态（是否已解锁、历史消息数）、是否有未结事项 |
| Agent 作答 | ①**该不该自动答**（分类：佣金/链接/样品费/Boost/目录/拒绝/其他）②候选回复（意语＋中文对照）③**引用的事实**（来自 `cycle_reply_facts`，不许编） |
| 你判 | 「OK」/「不 OK」＋**应该怎么答**（自由文本） |
| 沉淀 | OK → 正例；不 OK → 反例＋你的修正。你的修正再提炼成**规则**（如"样品费一律不承诺、转人工"），你过目后启用 |
| 下一轮 | prompt ＝ 固定模板 ＋ 事实 ＋ **该分类已启用的规则** ＋ 最近的正/反例 |

数据（`var/second-cycle.sqlite`，新增，不改既有表）：

- `reply_draft(id, plan_id, creator_id, pending_revision, category, text_it, translation_zh, facts, state, created, decided_at, operator_note, corrected_text_it)`
  - `state ∈ draft | approved | rejected | human_required`
  - **draft 表本身就是案例库**：`approved` 是正例，`rejected` 是反例（带 `corrected_text_it` 与 `operator_note`）
- `reply_rule(id, category, instruction, source_draft_ids, active, created, revision)`——每条规则**必须能说出它是从哪几条判定提炼的**

纪律：

- **只从你的判定学习**，不从模型自己的输出学习（不自我强化）
- 预演阶段 `realSends 0`，与真发通道物理隔开（不进入 `service_reply` 的 ready 队列）
- "这类不能自动答" → 永久进人工，不让模型硬答
- 规则可停用、可改、可审计
- 样本诚实：现在只有 26 条真实回复，靠监控持续攒；不造假样本

## 6. ④ 统计日历

按天（**北京时间**分天）一行：

| 指标 | 来源 | 口径 |
| --- | --- | --- |
| 发送条数 | `cycle_delivery_part`（`kind='card'` 与 `'text'` 分开） | 按 `started`，只算 `confirmed` |
| 触达达人数 | 同上，去重 `creator_id` | **只算回查确认**；发出但未确认另列"未确认" |
| 收到回复 | `inbox_event`（`kind='creatorReplies'`） | **排除 `historical=1`**（历史补录不算今天） |
| 加橱窗 | `inbox_event`（`kind='showcaseNotifications'`） | 同上 |
| 自动回复 | `service_reply`（`state='confirmed'`） | 本轮不做真发，先显示 0 |
| 待人工 | `service_case`（`state='open'`） | 当日新增/当日未结 |

### 3.10 用户问"为什么这么多发不了"——三个根因，两个是我的口径错（2026-09-15）

用户的原话是："我的逻辑都是要先建完链接之后再去找线索，所以这些线索都应该是已经有链接才找到的线索
才对啊。为什么会没有可用的 taplink 卡呢？"——**用户是对的**。查完台账后，三件事都定住了：

**① 备链缺口 797 里绝大多数不是"没有链接"，是我的台账读卡口径错。**
建链台账把"可复用的已有卡"写在**三处**，而 `ledger_card()` 只读了第一处：

| 位置 | 内容 | 行数 |
|---|---|---|
| `catalog_prepare_item.card` | 自己建出来并核验的卡（`verified_read_only`，带 listId） | 1518 |
| `catalog_prepare_readback`（`kind='reusedLink'`） | **复用已有链接**时的完整卡读回（`reconcile_from_inventory` 只写这里，**不写** `item.card`） | 1239 |
| `catalog_prepare_reuse`（`reusable=1`） | 同一份观察，只剩 listId 与佣金原始值（`1300`=13%） | 1393 |

另外两处小坑：`catalog_prepare_item` 里同一 pid 有多行时 `ledger_card` 只取**最新一行**（那一行常常
只是摘要）；读卡那一步（`step_read`）会把 `classify_pid` 算好的复用事实**覆盖**成
`{'state':'existing_links_observed','total':N}`——一个**没有 listId 的摘要**，等于把已经花掉一次平台读
才拿到的东西扔掉。三处读全之后 `missing_card` 从 797 降到 756（其余被上一轮 mislabel 的
`offer_not_in_current_catalog` 吸收），并且拆成**有名字的原因**：

- `card_not_read`（449）——台账有行、没卡。**只读复读一次就有**，不是建链。
- `card_rate_changed`（301）——台账那张卡记的是另一个佣金（平台/货盘改过）。话术里的佣金必须与平台一致，所以也要复读确认。
- `card_campaign_changed`（1）——卡挂在别的活动上，**这才是要平台写入**的那种。
- `no_link_in_ledger`（6）——台账里连一行都没有，要核实它凭什么进的池子。
- `card_unverified`——有定位信息但状态不是可用核验卡。

**② 读卡队列以前永远不会再读这些行。** `claim_read()` 只领 `pending/read_incomplete`，`review`/`reuse`
的行一旦被判过就**永久钉住**——哪怕平台上卡就在那里。新增只读入口
`catalog-link-prepare.py reread --route selected|--route campaign`：先把"有行但没卡"的行重新排队，
再走既有的 `step_read`（**只读卡，不建链**），并把复用事实按卡片契约 `reused_card()` 转好存下来
（不再存摘要）。**实测 5 条**（`--limit 5`）：读到 2 张真卡（listId `8650227744673078038` /
`8650747538196765462`，佣金 13%），1 条瞬时读失败，2 条还在飞；**平台写入 0**。同一次 requeue 把
2352 行（review 1161 ＋ reuse 1191）排回了队列——这是本地队列状态，读卡仍是只读；建链仍要显式给
`--max-creates`。

**③ `offer_not_in_current_catalog` 218 里 182 条也不是"商品不在货盘"。** `choose_candidates` 用
`select_offers()` 建 offer 表，而那个函数**无条件**要求"这个 pid 在 `opportunity` 表里有行"。那是
**准备/估算**用的需求表（`_edges` 只在来源边自带 `creatorId` 时写它，Kalodata 线索边没有 creatorId），
**发送位置来自池子，池位本身就是需求**。改成 `select_offers(..., scoped_pids=池位集合)` 之后这一档
**218 → 25**，剩下的 25 条是真规则（佣金无优势、剩余不足 45 天、库存不够）。

**④ 页面上出现中文商品名，是样例取错了字段。** `_sample()` 先取 `shortNameZh`（AI 生成给操作者看的
中文备注），而真正发出去的话术用的是意语 `mentionIt`。现在样例**逐字渲染既有模板**（
`cycle_materials.render`，v4 `standard`）：`Ciao @handle! Abbiamo una commissione migliorata al {rate}% per te su {mention} 👏 …`，
中文只作为**标注了"中文对照"**的翻译出现。顺带修掉卡名解析：模板是 `🔥 BJN {短名} {佣金}% {tail}`，
以前只认以 `BJN ` 开头的名字，遇到 emoji 前缀就把整条名字当短名塞进话术。

**⑤ 附带发现（未改口径，先记着）**：`ready` 商品的卡名里的短名是**建链时截断的标题**
（例：`Rubinetto portatile per`），因为短名生成当时只覆盖了 879 个**待建链**商品。要让话术里的商品名
好看，得把 `catalog-names` 的作用域扩到 ready 商品（那是模型调用，成本 ¥0.1 量级）。

### 3.11 只读复读跑完后的真实账（2026-09-16 凌晨，用户说"开始修复"后实测）

`reread --route selected|--route campaign` 跑满 14 批（9 通道 / 12 QPS），**平台写入 0、创建 0**：

- `catalog_prepare_item` 里 `state='reuse'` 从 **2 → 1193**：**1193 个商品拿到了可定位的真卡**
  （listId ＋ 平台实际佣金），全部来自只读复读——证明"先建链再找线索"这条链是通的，
  之前那批"备链缺口"确实是我们台账没读全。
- `card_not_read`（台账没存下卡）在发送池里 **449 → 0**。
- 剩下的是**两种非台账问题**：

| 卡点 | 池位 | 性质 | 实测证据 |
|---|---|---|---|
| `no_card_needs_link` | 495 | **要建链（平台写入）** | 抽 30 个行状态为 `missing/reading/pending` 的 pid，用**发送时同一个卡搜索**（CARD 端点按 pid）去问：19 个返回 `total=0`、11 个响应形状异常，**有卡的是 0 个** |
| `card_rate_changed` | 344 | **业务决定** | 台账里的旧卡（卡名 `🚀 Incentivo Boost disponibile \| BJN`）达人佣金比当前计划**低 1 个点**：`rateGap = {same:618, lower:230, lowerByOne:212, higher:0, noCard:399}` |
| `offer_not_in_current_catalog` | 26 | 规则（不合格） | 佣金无优势 / 剩余<45天 / 库存不够 |
| `relationship_blocked` | 7 | 规则（关系被挡） | 拒联或人工中 |
| `no_link_in_ledger` | 6 | 要核实 | 台账里完全没有这个商品 |
| `card_campaign_changed` | 1 | 平台写入 | 卡挂在别的活动 |

**为什么"卡佣金低 1 点"不能由代码自己决定**：发送时读卡走的是 `inspect_card()`（CARD 端点按 pid 搜卡），
它要求"卡上的佣金 == 我们声明的佣金"。实测同一个商品：**发送读卡端返回 `1200`（12%），而计划是 `1300`（13%）**。
所以声明计划佣金会被它挡下（`commission_advantage_unverified`），而按卡上的 12% 发又与"计划说 13%"不一致。
两条路都成立，选哪条是**对达人承诺多少钱**的事，只能用户定：
① 按卡上的佣金发（话术说 12%，**不写平台**，立刻可发）；② 按计划的佣金**重建链**（话术说 13%，平台写入）。

**顺带验证了窗口闸门**：默认 9:00–24:00（北京时间）。凌晨 02:12 实测 `可发 0`、`outside_send_window 1094`
——不是坏了，是窗口关着，到 09:00 自动开。页面顶部会显示「窗口 关着」。

**下一步（都等用户点头）**：①495 条要不要建链（`--max-creates`，平台写入）；②344 条按卡佣金发还是重建链。
