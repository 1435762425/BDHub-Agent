# 非全托（Campaign）商品：设计口径与实施方案（2026-09-15）

> 历史 Campaign 设计。当前冷却为 72 小时、额度/消息上限及渠道范围以 PROJECT 为准；本文旧 24/48h、5 条/月及待定渠道设想不构成现行规则。 参见[项目文档](../PROJECT.md)和[技术文档](../TECHNICAL.md)。

> 历史设计与实施证据：同一 PID 内选择 Campaign Offer 的规则仍可参考；跨 PID 的达人内部“佣金优先”已失效。当前发送选择在达人之间和达人内部均按 Kalodata `sourceRank → units DESC → PID`，见 [达人发送池与 AI 回复策略](creator-pool-and-reply-policy-v1.md)。

## 一、已经确认的口径

| # | 事项 | 结论 |
|---|---|---|
| 1 | IT 的 campaign 读取 | **算已验证**（新版已实读 3 次：`live-it-campaign` 3,622 个 offer；旧库把 IT 的 `campaign` 标为 `unsupported` 是历史口径，不沿用） |
| 2 | 加入活动的自动边界 | 沿用旧版：ACTIVE + **剩余 > 45 天** + 无额外条款/资料要求 → 可自动加入，否则转人工；`apply` 要显式确认 + contact_email；逐项记账、**原意图回查不重复提交** |
| 3 | 池子形态 | **一个池子 + 渠道标签/筛选**，不做两张卡 |
| 4 | 佣金 | 用**已确认的新规则重算**（`catalog_links.new_commission`），不用快照里的旧"平均分佣"结果 |
| 5 | 跨渠道重叠 | 实测只有 1 个 PID；**位置只出一条、全托优先** |

## 二、为什么不会和全托混掉：三层归属

**渠道属于「商品/线索/链接」，属于「达人」的东西一律共享。**

| 层 | 带渠道？ | 事实源 |
|---|---|---|
| 商品目录 | ✅ `catalog(plan_id, **source**)` + `catalog_head(plan_id, **source**)` | 已有，按 source 各一份快照 |
| offer | ✅ `catalogSource` + `offerKey = source:pid:cid` | 已有（`cycle_catalog.normalize`） |
| 链接台账 | ✅ `catalog_prepare_item.catalog_source`；intent `route` | 已有字段，目前只允许 `selected` |
| 线索边 | 应带（`offerKey` 已有渠道前缀） | `source_edge.payload.offerKey` |
| 发送池位置 | ✅ 要带（现在被折叠掉） | join 链接台账取渠道 |
| 达人身份 / 冷却 / 500 额度 / 拒联 | ❌ **共享** | `cycle_identity_*`、`relationship`、`cycle_contact_reservation` |

**绝不按渠道拆 plan 或拆身份库**：拆了同一个达人会被两个渠道各碰一次，那是事故不是隔离。

## 三、非全托的闸门（全部用已有判据）

| 顺序 | 闸门 | 判据 | 现状 |
|---|---|---|---|
| 1 | 可推资格（商品级） | creator>公开、库存>100（非全托）、available、剩余>45天；评分>4 仅偏好 | **已实现** `second_cycle.assess_offer` |
| 2 | 佣金规则成立 | 总−公开 ≥ 2 个点（= `new_commission` 的 `insufficient_commission_gap`） | **已实现** `catalog_links.new_commission` |
| 3 | 挑活动 | 达人佣金最高 → 截止更晚 → 活动ID最小（确定性）；**不合格不硬挑** | 待实现 |

注意：闸门 2 不是另配的门槛，它**就是佣金规则本身**（机构最少 1 点 + 达人至少比公开高 1 点 → gap≥2）。所以非全托不需要像全托那样单独配"佣金差下限"。

## 四、真实数据实测（`live-it-campaign`，2026-09-15）

```
3,622 offer / 2,668 PID / 43 活动
 → 合格 offer 925（闸门 1+2）
 → 至少一个合格活动的 PID = 420        ← 非全托候选池
 → 其中 223 个要在多个活动里挑一个
 → 最终池来自 12 个活动
被挡原因：佣金差<2点 2,223｜达人≤公开 1,990｜不可用 1,233｜库存≤100 1,049｜剩余≤45天 374
```

**非全托池不是 3,622 个商品，而是约 420 个**——主要卡在佣金（多数 campaign 的佣金差不到 2 个点）。

挑活动的裁决分布（223 个）：**截止更晚 140 / 靠活动ID定序 80 / 佣金更高 3**。
「佣金优先」与「截止优先」两种排序挑出不同结果：**0 个**——所以排序细则现在不敏感，固定下来是为了**确定性**（否则同一批商品每次算可能换活动）。

佣金重算的效果举例（PID 1729589042485762870）：

| 活动 | 总 | 公开 | 旧"平均分佣"给的达人 | **新规则后**（机构=min(2,总−公开−1)） |
|---|---|---|---|---|
| 7666370360582260502 | 15% | 12% | 13% | 13%（机构2） |
| 7683821197913540374 | 17% | 12% | 14% | **15%**（机构2） |

→ 重算不只是换个数字，它可能改变"哪个活动更好"的排序。

## 七、验收点

- **离线**：挑活动规则用真实快照钉住（223 个多活动 PID 的裁决、确定性、不合格不硬挑）；佣金重算等于 `new_commission` 输出；`assess_offer` 的拒绝原因可枚举；渠道不混的恒等式（pool 位置按渠道分组之和 = 总数）。
- **真实**：读 campaign 快照（只读）；挑活动（只本地记账）；**加入活动与建链是平台写入**，逐次显式确认后才执行。

## 八、明确不做

- 不拆 plan / 不拆身份库 / 不按渠道复制额度与冷却。
- 不为非全托另建一套佣金规则。
- 不把非全托套进全托的 300 件门槛。

## 九、池子分配：渠道不参与配额（已确认，B 方案）

**分配单位是「达人」，不是「渠道」。** 池内 4,158 个位置（全托 3,648／campaign 510）里，只有
**224 个达人**同时拥有两个渠道的位置——渠道之争只发生在他们身上，其余 1,396 个达人只涉及一个渠道。
达人级约束（冷却 24/48h、机构 500、达人 5 条/月）本来就与渠道无关，所以**不设渠道配额**。

现状排序（`lead_pool.py`）把两件事压在一个键上：

```python
layers['ready'].sort(key=lambda r: (r['rank'], r['creatorId'], r['pid']))   # 然后每达人取第一条进槽位
```

**改成两段**（B 方案）：

| 段 | 规则 |
| --- | --- |
| 达人之间（谁先发） | 按线索强度 `rank`——**与现状完全一致，队列顺序不变** |
| 达人内部（发哪个商品） | 达人佣金最高 → `rank` 更小 → **全托优先** → `pid` |

实测（真实 ready 层 1,162 个槽位）：

| | 数量 |
| --- | ---: |
| 换商品 | **131（11.3%）**（同渠道换商品 114、跨渠道 17） |
| 不变 | 1,031 |
| 换商品带来的达人佣金 | 平均 **+2.06 点**（+1.0 ~ +8.0） |

裁决依据分布（多位置达人）：佣金最高直接决定 193｜佣金相同→rank 决胜 178｜佣金+rank 都相同且同渠道→pid 决胜 77｜
**佣金+rank 都相同且跨渠道→全托优先：0**（这批数据里没触发；它实际是确定性保险 + 覆盖"同一 PID 跨渠道"那种情形）。

代价要说清：换商品的槽位里 `rank` 平均会变差（例：rank 4→8），是**回复率（佣金）与线索强度（rank）之间的取舍**。

## 十、商品失效即排除（已确认口径）

campaign 商品会失效（下架/治理/不可用、活动结束或退出、库存≤100、剩余期不足）。

| # | 边界 | 确认结论 |
| --- | --- | --- |
| a | 可逆性 | 排除＝不进可发范围，**记录保留**；商品恢复有效自动回归（池子每次读取重算，无后台任务） |
| b | 涉及哪些层 | 可发／池中等待／冷却中／**等达人回复**都排除；但**达人级的案件、关系、冷却不动** |
| c | 影响范围 | 只影响该 PID；同一达人的其他商品位置不受影响 |
| d | 查询队列 | 该 PID 移出待查队列且不再刷新（死商品查达人是白花 Kalodata 额度）；已查到的线索保留 |
| e | 链接 | 不为失效商品新建链接；已有有效链接不删，但该位置不发 |

落点：池子新增**商品级**层 `product_invalid`，**优先级高于冷却**（商品死了跟时间无关），与达人级
`excluded`（拒联）**分开显示**、原因码分开；排除每次读取重算。

**现状缺口（实测）**：`lead_pool` 只 join `relationship`／`cycle_delivery`／`service_case`，
**完全不 join 商品状态**，所以失效商品的位置现在照样被算成"可发"。
按最新快照逐条判：4,158 个位置里**已有 27 个不合格**（全在 campaign 侧，全是库存≤100；selected 侧 3,648 个全部有效）。
日刷决定"池子状态"，**发送前再核一次**是最后一道门——两道都要。

## 十一、P1 第一步已完成：佣金迁到新规则（2026-09-15）

**改了什么**：新增 `cycle_catalog.commission_rule()` / `commission_calculator()`，把三处还在读旧
`bdhub.research.catalog_rules.link_rules_for`（默认 `MX_AVERAGE`「平均分佣」）的调用统一迁到已确认规则
（`catalog_links.new_commission`：机构 `min(2, 总−公开−1)`、达人 `= 总−机构`、要求差≥2点）：
`sync-cycle-catalog.py`、`enrich-global-opportunity.py`、`create-cycle-card.py`。

**离线实测（拿现有快照的原始总/公开佣金重算）**：

| 渠道 | offer | 佣金变化 | 可推资格 |
| --- | ---: | --- | --- |
| selected | 3,451 | 3,384 同值 / **61 变化（全部升高）** | 3,383 → **3,444** |
| campaign | 3,622 | 1,174 同值 / **225 变化（222 升高、3 降低）** | **925 → 925（不变）** |

**影响与注意**：

- 规则指纹变了，所以**旧目录快照里的 offer 会被判 `commission_rule_changed`**（`create-cycle-card.py` 的守卫）——

  `config/catalog-link-policy.json`（本次没改）。而且链接侧本来就已在用新规则（`new_offer` → `new_commission`）。
- 这一刀**没有平台写入**，也没有发布新快照；只是让下一次读取按新规则算。

## 十二、P1 完成：非全托筛分账本（2026-09-15）

新增 `lib/campaign_screen.py` + `scripts/campaign-screen.py status|record`，账本落在
`var/campaign-screen.sqlite`（`campaign_screen_run` + `campaign_screen`，主键 `(run_id,pid,campaign_id)`）。

**单位是 offer（PID × 活动），不是 PID** —— 因为同一个 PID 可能落在多个已加入活动里，筛分先按 offer 判，
「一个 PID 用哪个活动」是 P2 的挑选步骤。

**筛分口径（全部复用既有判据，没有新造门槛）**：

```
原始总/公开佣金 + 当前规则(commission_calculator) → 达人佣金
  → assess_offer：达人>公开、非全托库存>100、available、剩余>45天（评分>4 仅偏好）
```

**为什么筛分时重算佣金**：快照可能是旧规则算的（历史快照就是）。把「原始事实 + 当前规则」当输入，
筛分结果才与规则一致，不会因为快照新旧给出两套答案。

**一个商品只算一次原因**：达人佣金是我们自己算的，所以 `assess_offer` 的 `missing_creatorPercent`
在本模块里**被抑制**——佣金不足就报 `insufficient_commission_gap`，不再同时报一次「平台没给达人佣金」
（否则 2,057 个商品会被计成两条原因，原因总数虚高）。同理 `missing_total_commission` 只在总佣金缺失时出现。

**实测（当前快照，`status` 实时算）**：

| 渠道 | offer | 合格 / 不合格 | 合格 PID | 需要挑活动的 PID | 主要原因 |
| --- | ---: | --- | ---: | ---: | --- |
| campaign | 3,622 | **925 / 2,697** | **420** | **223** | 佣金差<2点 2,057｜不可用 1,233｜库存≤100 1,049｜差166缺公开佣金｜剩余≤45天 374 |
| selected | 3,451 | **3,444 / 7** | 3,444 | 0 | 差不足 3｜缺公开佣金 3｜不可用 1 |

全托侧一个 PID 只在一个活动里（multiCampaignPids = 0）；campaign 侧 643 个 PID 落在多个活动里，
其中 223 个在合格范围内——这就是 P2 要挑的对象。库存那一条对全托自动失效（`require_stock` 对全托为假），
所以 selected 侧的原因里没有 `stock_not_over_100`——一个函数同时管两个渠道，渠道差异由已有判据表达。

**`status` 实时算、`record` 才落库**：池子那套是"每次读取重算"，筛分同理；落库只用于审计与下游批次号，
并且 `recorded()` 会带出「这条记录还是不是当前快照」的对照信息，避免页面拿旧账本当现状。

## 十三、P2 前半：挑活动 + 入池账本（2026-09-15）

**挑活动规则**（已确认口径，纯函数 `campaign_screen.pick`）：

```
达人佣金最高 → 截止更晚 → 活动ID最小（确定性）；不合格的候选根本不参与
```

**入池投影**（`campaign_screen.pool`）：一个 PID 一条，只带被选中的活动；落选活动留在 `alternatives` 里
不删除、可人工改选；一个合格活动都没有的 PID 记为 `held` 并带上原因——**不硬挑**。

**踩到并修掉的 bug（值得记）**：第一版按 **offer 的状态**分桶，结果 **65 个 PID 同时有合格和不合格的活动**，
于是它们在"已入池"和"未入池"里各出现一次，池子总数变成 2,733（正确是 2,668）。
改为**先按 PID 分组、再看这个 PID 有没有合格活动**，并加了恒等式 `reconciled`：
`chosen + held == distinct PID`，没有 PID 出现两次。测试里专门钉住这个回归场景。

**实测（`live-it-campaign`，当前快照）**：

| | 数量 |
| --- | ---: |
| 快照 offer（PID×活动） | 3,622 |
| 筛分合格 / 不合格 | 925 / 2,697 |
| **入池（一个 PID 一个活动）** | **420** |
| 未入池（有商品但无合格活动） | 2,248 |
| 有备选活动可改选 | 223 |
| 恒等式 `chosen+held == distinct PID(2,668)` | ✅ |

落库在同一个 `var/campaign-screen.sqlite`：`campaign_screen_run` / `campaign_screen`（offer 级）
+ `campaign_pool_run` / `campaign_pool_item`（PID 级）。**只落库、不写平台、不动全托任何行。**

还修了一个 CLI 缺陷：`campaign-screen.py status` 原本调 `build()` 而不是 `status()`，所以少了
「上次落库是否还是当前快照」的对照；现在会带出来（实测一致）。

**还没做的（P2 后半）**：加入活动的状态机（preview → 显式确认 → apply → verify、逐项记账、原意图回查）。
它含**平台写入**，所以单独一片做，并且做完停在"可预览、待确认"。

### 传输层：写入必须先被声明

### 状态机纪律

| 纪律 | 做法 |
| --- | --- |
| **写入前先落盘** | 条目先记 `writing` + `write_attempted=1` 再发 POST；崩溃也不会看起来"从没提过" |
| **结果未知绝不重试** | 再点 apply → `campaign_write_requires_verification`，只能去 `verify` |
| **回查结算** | `verify` 重读已加入列表，把 `writing`/`result_unknown` 结算成 `joined`（只读，`platformWrites` 必为 0） |

* **读卡**：非全托**没有账号级卡清单**，所以按活动分组、每个活动读一次

* **唯一键保持按 PID**（不是 PID×渠道）：一个商品永远只允许一份未结意图，跨渠道也不例外。

## 十八、第一次点「预览可加入活动」像没反应：两个 bug 叠在一起（2026-09-15）

用户点了一次预览，页面毫无变化。查下来预览**其实成功了**（账本 `var/campaign-join.sqlite`
里 18 条 `eligible`、已加入 43），是两处各自的缺陷把结果吞掉了：

1. **桥接把 `error:""` 当成失败。** `server/campaign/bridge.ts` 的 `run()` 判据是
   「有 `error` 字段且是 string 就 reject」——**空字符串也是 string**。而 `campaign-join.py`
   **成功时也带 `error: ""`**（job 行的 error 列），于是 `/api/campaign-join` 在第一次预览**之后**
   永久 503。预览之前没有 job、返回的是 `{available:false,reason:...}`（不带 error 字段），
   所以接口那时是好的——这个缺陷只在第一次预览后出现。已把判据改成**非空**错误码，
   并同步修掉其它 4 处同样的写法（`catalog-jobs`/`identity-queue`×2/`catalog-names`）。
2. **`preview` 的输出少了 `status` 那层封装。** 桥接的校验器要求 `available===true`，
   而 `preview` 只返回 `{jobId,campaigns,joined,eligible,items}`——没有 `available`，
   于是被当成"不可用"，`if(value?.available)` 不成立，**连成功提示都不显示**。
   桥接本来就把 `campaigns/joined/eligible` 标成「preview 才带的三个字段」，说明两者本来就该同形，
   所以改成 `preview` 复用 `status()` 的封装再补这三个字段（`items` 也顺带带上
   `write_attempted`/`joined_campaign_id` 等页面需要的列）。

修完实测：`preview` → `available:true, state:previewed, campaigns:18, joined:43, eligible:18,
platformWrites:0`；`GET status` → 200、18 条可加入。两条路径各加了回归测试
（Python 端 `preview` 必须带 `available`；Web 端 `readCampaignJoin()` 必须接受 `error:""`）。

**顺带确认的事实**：这个账号**已加入 43 个活动**，与 campaign 快照里的 43 个活动数一致——
所以 `campaign-inventory.py` 里"没有加入记录就退回整个快照"的兜底，覆盖的正是这批已加入活动。

## 十九、「一键加入」替代逐个勾选（2026-09-15）

要求：不要让人一个个勾。于是把「加入选中（N）」换成 **「一键加入全部可加入（N）」**，
活动列表保留下来但**只读**（仍然要能看到会加入什么、以及不加入的原因）。

三个设计点：

1. **目标集合由服务端重新预览得出，页面不传活动名单。** 一键动作 = `join_all()`：先跑一次
   只读预览，再把当前**全部合格**的活动一次提交。不拿页面上的旧列表去写平台——那份列表可能已经过期，
   拿它去写会把"已经不可加入"的活动也提交一遍。请求层也**不接受** `campaignIds`：多带这个字段直接 400。
2. **安全纪律一条没松**：只接受预览判定为 eligible 的活动、每个活动一次会话只写一次、
   结果未知立刻停下并留给 `verify` 回查——因为 `join_all` 只是把「预览」和「提交」串成一次调用。
3. **邮箱预填**，否则"一键"每次都要手打。优先级：这个 job 实际提交过的邮箱（账本里的证据）
   > `config/campaign-join.json` 的默认值 > 空。默认值取自旧版 `config.yaml` 的

## 二十、第一次点「一键加入」失败：一个只在该路径才存在的 NameError（2026-09-15）

现象：点「一键加入」→ 页面显示 `暂时无法提交加入。（campaign_unavailable）`。

**账本证明一条都没写**：18 条全是 `eligible`、`write_attempted=0`；job 停在
`blocked`，错误是 `name 'CAMPAIGNS' is not defined`。

### 根因（我自己的 bug，而且只在真正写入时才会现形）

`global_source_transport.opportunity_campaign_joiner` 里用了 `CAMPAIGNS` 来声明"允许的只读端点"，
但**这个模块从来没有定义或导入过它**。这行代码在 `_opportunity_transport` 被调用之前执行，
所以它在**任何一次写入之前**就抛出了 `NameError`——产品上表现为"点了没反应"，实际上是根本没走到写。

为什么一直没被发现：这个函数在 P2 写完就从没被真正执行过（当时的备注就是"未对平台跑过任何加入"），
而**所有既有测试都注入假传输**，真实的 scope 构造函数一行都没跑过。用户这一下正好是它的第一次。

修：在常量区定义 `CAMPAIGNS`，并把 `allowed_extra` 里那份重复的字面量换成它，免得两处走样。

### 一起加固的三件事

1. **新增 `tests/test_transport_scopes.py`**：把 `_opportunity_transport` 打桩，让**五个**写入作用域
   构造函数（selector / creator / creator_batch / deleter_batch / campaign_joiner）真正跑完自己的
   校验、冻结与"允许的端点"那几行。未定义的名字会当场失败，不必等到动平台那一刻。
   **验证过这道防线有效**：把 `CAMPAIGNS` 去掉，3 个测试立刻变红；恢复即全绿。
2. **CLI 对任何异常都以 JSON 回答**：`campaign-join.py` 原来只 `except ValueError`，
   `NameError` 直接崩到 stderr、stdout 空白，桥接只能报 `campaign_unavailable`——真正的原因一个字都
   传不到操作者眼前。现在非预期异常也回 `{"error": "campaign_join_internal:<类型>:<摘要>"}`（exit 2），
   traceback 仍进 stderr 供排查。
3. **桥接在拿到非 JSON 输出时带上 stderr 的最后一行**（`campaign_unavailable:<原因>`），
   免得以后再有崩溃变成一句无信息量的"服务不可用"。

### 顺带修掉同一类判据的另一半

上一轮为了修「`error:""` 被当失败」，我把判据改成了"有非空 `error` 就是失败"——**太粗暴**：
`status` 里的 `error` 是 **job 的历史错误**（给人看的记录），于是"只要这个 job 存过一次错误，
状态接口就再也读不出来"（实测正是如此：那条 `blocked` 记录让 `/api/campaign-join` 又变成 500/503）。

正确判据是**只有 `error` 一个键的裸信封**——各 CLI 的失败输出都是 `json.dumps({"error": code})`，
而成功的 status 一定还带 `available`/`jobId`。5 处桥接统一改成这个判据，并加了两个方向的回归测试：
带历史错误的 status 必须 resolve（且把错误当数据如实显示），裸信封仍必须 reject 出它自己的错误码。

### 现在的状态

`/api/campaign-join` → 200、可用、可加入 18、已加入 43、邮箱已预填、`write_attempted=0`。
那条历史错误仍如实显示在页面上（"上次运行停在…"），**下一次成功提交会把它清掉**——不手改数据库。
修复后 **938 Python 测试 + 271 subtests、336 Web 测试全绿**，`tsc` clean。

## 二十一、第二次点「一键加入」：`allow_write` 漏了 campaign_scope（2026-09-15）

现象：job 停在 `needs_verification`，**1 个活动**被记成 `result_unknown`
（`write_uncertain:TapLinkError`），其余 17 个一次没碰——停下的时机是对的，但原因不在平台。

### 根因：写入许可漏了一条渠道

`_opportunity_transport` 建传输时：

```python
transport=Scoped(identity,account,allow_write=selection_scope is not None or creation_scope is not None or deletion_scope is not None)
```

**漏了 `campaign_scope`**（同一个文件里 `fork_lane` 反而带上了它）。旧版
`bdhub/send/taplink/transport.py:61` 的判据是
`if write and (not self.allow_write or (path, method) not in writes): raise TapLinkError('taplink_endpoint_not_allowed')`
——**在任何 HTTP 请求之前**就抛。所以：

* 那条活动**根本没到平台**（平台侧已加入仍是 43、它仍在"可加入"列表里）；
* 账本上显示"平台写入 0"也解释得通：计数写在发送**之后**，抛异常就没加。

修法不是补一个 `or`，而是**把推导收成一处**：新增 `write_enabled(...)`，`fork_lane` 与建传输
都用它。分散写正是漏掉一条渠道的原因。

### 顺带发现并修掉的三个 bug（其中一个是危险的自相矛盾）

1. **`preview` 会抹掉「已提交」记录**（危险）。它原来整表替换条目，`write_attempted` 一并归零；
   而"一键加入"的第一步就是 `preview`——于是每次点击都会**清掉禁重试保护**，下一次提交就会
   重复写平台。现在只保留**未结算**（`writing`/`result_unknown`）的提交；已结算的（joined/skipped）
   按平台这次的回答刷新（否则一条结算成"平台说没加入"的记录会永远卡住、再点也进不去）。
2. **`verify` 把「已加入总数」写成「本 job 里 joined 的条目数」**：一次回查就把平台的 **43 改成 0**，
   页面上是一个凭空的假数字。现在以平台这次读回来的为准。
3. **结果未知时只记了异常类型名**：`write_uncertain:TapLinkError` 把真正的原因
   （`taplink_endpoint_not_allowed`）丢了，只能靠读代码定位。现在记消息。
4. `verify` 之前对"平台说没加入"的条目**无法结算**（两条路都不匹配），现在用平台**两个独立列表**
   的回答给出结论：不在"已加入"里、却在"可加入"里 → `skipped` +
   `not_joined_platform_lists_it_joinable`（原因码把依据写清楚，让人看出是平台说的、不是我们放弃确认）。

### 实测与现状

* 结算后账本自洽：job `completed`、`joined_count 43`（平台口径）、17 待加入、1 条按平台回答结算为未加入。
* 再预览一次（只读）：`campaigns 18 / joined 43 / eligible 18 / writes 0`——那条回到可加入，
  所以下一次点击会尝试全部 18 个。
* **新增 6 条测试**，并且逐条做过**反向验证**（把 bug 退回 → 测试变红，恢复 → 全绿）：
  `allow_write` 必须覆盖全部四个作用域、预览绝不抹掉未结算的提交、已结算的 skipped 能回到可加入、
  回查写平台口径的总数、未知必须带消息、结算依据是平台的两个列表。
* 全量：**944 Python 测试 + 271 subtests 全绿**。

**注意**：到现在为止，非全托**一条链接都没建**、加入活动**一次都没真正写出去**。
下一次点击才是这条写入路径第一次真的发出请求。

**用户观察**：非全托已经有 400 多条可用链接、对应 400 多个商品，但查询队列里的 PID 没增加。

**根因**：队列作用域＝`合格商品 ∩ 有可用链接的商品`，而 `eligible_products()` **只读全托的筛分账本**

`linked_products()` 本来就读两条渠道，但交集把它们全挡掉了。

修法与实测：

* `eligible_products()` 现在返回**两条渠道的并集**：全托来自筛分账本、非全托来自已入池账本

  没有把平台活动商品行里的 `product_sales` 接出来。已接出（连带 `reviewCount`），并重跑了一次采集
  让快照带上它。实测 **444 个非全托商品全部有销量数据**（`unitsUnknown: 0`）。

* 队列载荷新增 `byChannel` 与 `unitsUnknown`，页面据此写明渠道构成；没有销量数据的会**如实标记**
  （按 0 参与排序，但绝不假装有数据）。
  ★ 这里踩了一个小坑：`build()` 加了字段，但页面读的 `status()` 是**逐字段列出**的，

## 二十八、补 OECID 的进度条 + 你那次线索查询的结果（2026-09-15）
