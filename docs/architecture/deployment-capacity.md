# 部署与容量研究

部署位置尚未选定。当前已知运行方式是一台持续开机的 Mac；本文件给出可验证的容量判断方法和候选配置，不承诺某台服务器一定支持特定日发送量。

## 1. 当前设备的只读快照

| --- | --- | --- |

| 物理内存 | 16 GiB | 同时供 macOS、浏览器、数据库、开发及其他应用使用 |

磁盘空间应在正式安装、复制大数据和负载测试前规划。旧项目三个大型检查转储仅列为约570MiB清理候选，是否删除另行确认，不能把它们当作已经释放空间。初次研究时新项目只保存精简文档与选择目录；后续已增加本地 Web 原型和独立 SQLite 运行验证，没有复制旧输出或原始业务数据。后续安装前再次读取磁盘可用空间约34GiB，该变化不是本项目清理成果。

## 2. 承载量由什么决定

如果推理调用外部模型 API，通常不需要在应用主机上配置 GPU。主机主要承担连接器、浏览器/签名环境、数据库、事件队列、检索和并发网络任务。如果未来要求本地运行大模型，则是另一套硬件与质量研究，不能用本表配置替代。

影响容量的因素按实际工作拆开：

1. **平台容量**：账号/机构限额、动作能力、QPS、验证和维护。资料查询3QPS不能推导消息发送也允许3QPS。
2. **浏览器与会话**：是否必须常驻浏览器，每账号/页面内存，活跃页面与认证周期，是否能在Linux稳定运行。
3. **模型资源**：API请求与token限制、响应时间、模型/工具费用。增加CPU不一定提高云模型并发额度。
4. **数据与索引**：历史消息量、商品/Offer更新、去重范围、查询索引和事实保存周期。
5. **服务承载**：触达带来的有效回复、在途样品/内容、人工决定和维护时间。

因此“十万达人”不能直接换算成十万个Agent进程；有限worker按事件处理。日发送量也不能仅凭CPU核心数预测。

## 3. 三种部署路径

| 路径 | 优点 | 成本与限制 | 适用条件 |
| --- | --- | --- | --- |
| A 继续本机 | 已有平台环境接近现状；改动少，适合首轮验证 | Mac维护/网络/重启影响运行；与日常工作共享资源；远程使用与备份需独立方案 | 单机服务可接受，先验证闭环和实际负载 |
| B Mac执行节点＋自控云端管理 | 浏览器/平台操作留在已验证环境；管理、状态和多人访问可独立运行 | 增加安全连接、离线队列与双端故障处理；不是免费获得高可用 | Linux平台环境存在困难，且确有远程管理或隔离计算需求 |
| C 全部迁到服务器 | 常驻环境独立，监测与多人服务较集中 | 新环境认证、Linux/架构/网络与浏览器恢复需逐项验收；要承担运维或托管费用 | 连接器在服务器通过稳定性与恢复验收，运行成本更合适 |

不能仅因“服务器一直开着”就判定C最好。先验证现Mac上新系统能正确恢复，再对真实连接器做服务器兼容验证。A到C可分阶段迁，不要求同时换所有账号和数据。

## 4. 候选服务器规格——仅作为测量起点

| 工作负载 | 可比较起点 | 尚不能推导的结果 |
| --- | --- | --- |
| 只运行Web/API与轻量调度，模型外调，数据库另放 | 2–4 vCPU、4–8GB RAM | 不代表可同时运行多个浏览器会话 |
| Web/API、PostgreSQL与有限后台任务同机，浏览器在Mac | 4 vCPU、8GB RAM、至少80–100GB SSD | 不代表当前数据规模下查询和备份一定达标 |
| 同时运行少量常驻浏览器与新系统核心 | 8 vCPU、16–32GB RAM、至少150–200GB SSD | 不是账号数或日触达保证，须按每会话实测调整 |

以上是工程候选范围，不是云供应商报价或经过本项目压测的推荐订单。不先购买。CPU架构和操作系统选择取决于签名/浏览器/依赖兼容性；不能把Mac ARM运行成功直接等同于Linux x86成功。

## 5. 如何量化

```text
峰值内存预算 = 基础系统 + DB/索引 + 实测单浏览器会话×并发会话数
             + worker工作集 + 缓存/峰值余量
日存储增量 = 原消息/事件 + 业务快照 + 必需trace + 模型输出与媒体
存储规划 = 活跃数据 + 索引 + 临时工作空间 + 备份/恢复空间 + 增长余量
预计新增人工分钟 = 新触达量 × 咨询率 × 需人工比例 × 单项处理分钟
```

测试先使用模拟/历史隔离数据：1k、10k、100k关系索引，有限候选检索、重复消息与工作队列；不构造全部商品×达人组合。测p50/p95查询、队列年龄、内存峰值、磁盘增长和恢复耗时。

平台阶段只在明确范围、账号和动作授权后做有限真实验证。观察至少包括空闲与活跃浏览器、认证维护、入站洪峰、模型延迟、数据库暂不可用、Mac重启、网络中断和unknown核验。不用内部队列吞吐外推平台发送速度。

稳定阶段应观察完整经营周期的资源曲线，而非一次 `ps`。阈值按实际服务时效和费用设定；达到积压高水位先减少新获客，继续已有服务。模型/平台限制优先于worker扩容。

## 6. 混合部署需要额外解决的合同

云端保存经营意图和控制版本；Mac执行节点保存已接受的稳定action_id及本地执行尝试。双方通过受限业务协议交互，不能暴露任意shell或浏览器控制给公网。

候选B默认在失去控制端连接时停止新的平台提交，只收口或只读核验已经提交的动作；不能凭旧control_revision继续发信。云端人工接管在执行节点确认前显示“接管待确认”，不承诺跨断网立即取消；节点确认后才显示控制已生效。若未来确需离线外发，必须另行设计有限授权租约和明确的接管延迟语义并重新确认，本方案不默认支持。云端重发投递只用于找回同一个action_id，不创建新的平台写入。平台已提交但结果不明时，本地保留unknown并核验，云端不能因节点离线再分配另一机器重复执行。

这条路径多一层分布式一致性成本，因此必须与单机/全云方案实测比较，不因听起来灵活就直接采用。

## 7. 目前可下的结论

目前证据不足以判定必须换服务器，也不足以承诺现Mac能够无限增加账号。M2/16GB可以作为首轮验证环境；磁盘余量和长期会话稳定性应先测。正式部署由连接器兼容、资源、服务时效、恢复与运维责任共同决定。

需要后续确认的值是：实际同时使用的账号/浏览器数、可接受停机时间、远程访问需求、模型/主机预算及备份保留周期。这些不会阻止当前PRD和离线合同完成，也不等于已经同意服务器采购或迁移。
