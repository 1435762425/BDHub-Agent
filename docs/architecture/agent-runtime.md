# Agent 运行合同与已确认协作基线

设计稿 v0.2，2026-09-11。本文定义可实现、可测试且与具体框架无关的运行合同，不是生产实现或选型结论。研究依据为[公开 Agent 案例与框架评审](../research/agent-cases-review.md)，其中原始资料、日期与能力边界已经分别登记。

## 1. 已确认背景与待比较边界

系统最终独立运行并替代旧 BDHub。首期覆盖 MX/BR/IT TikTok IM 的一发、二发、回复和合作结果，后接 WhatsApp；范围内自动经营，超出商业条件交人。团队 1–2 人，不设固定业务日触达硬上限。当前有持续开机的 Mac M2/16GB；这不是并发容量、故障恢复或本机部署优于服务器的证据，部署另行比较。

**已确认协作基线：**一个关系 Agent 负责当前达人，程序负责调度与执行；只有独立研究任务才按需委派专家，评估使用流水线。增加 Agent 要先验证效果，不预设固定三个自主角色。具体框架仍通过小闭环比较，必须实现以下合同。

**已确认数据基线：**长期关系、原消息和业务状态保留在自控数据库，模型只接收本次必要上下文；托管长期会话不作为当前默认方案。自控数据与本机/服务器部署是两个不同问题，部署仍另行比较。供应商 session、图 checkpoint、SDK run 不直接等同于业务关系或合作事项。以上最新决定覆盖研究报告中当时未决的对应问题，不改写其历史记录。

按次提供必要上下文不等于供应商零留存。接入前须按实际供应商、接口、账户和配置核实日志、留存、训练使用与可用数据控制能力；未核实不能承诺零留存，也不能假定 API 会话结束即删除。

## 2. 运行职责，不预设三个自主角色

| 职责 | 输入与产出 | 权限边界 |
|---|---|---|
| 事件接入与协调 | 平台事件/约定 → 耐久事件、待处理工作 | 去重、路由、资源与顺序由程序判断 |
| 关系判断 | 绑定关系、当前事项、有限上下文 → 结构化 Decision | 可查授权事实、提下一步；不能自由改身份、政策或认定执行成功 |
| 按需专业任务 | 明确 brief 与有限证据 → 有类型的分析结果 | 不独立外联，不复制完整会话、凭证或后端对象 |
| 业务执行 | 已验证的动作意图 → 外部请求、回执与核验 | 执行前再查权限、版本与当前条件；每动作有唯一意图 |
| 评估流水线 | 冻结用例/抽样轨迹 → 代码判据、模型评分与差异 | 不改生产策略、不补发、不以自身答复作验收事实 |

这张表是职责分工，不要求每行一个 Agent 或服务。事实查询、批量初筛、额度计算和确定性验收可以是普通函数/作业。只有任务需要动态探索且收益可测时才启用专业 Agent。

### 2.1 精简关系 Agent 主提示候选

以下是可实现的提示候选，需通过三市场场景评估后发布。宿主注入绑定信息；`policy_version` 存在宿主绑定中，Decision 通过 `binding_ref` 引用，不另造输出字段。

```text
你是 BJN 的达人合作助手，负责当前已核实关系的持续合作。
目标是在授权范围内完成有用的下一步，兑现承诺并减少重复沟通。
【宿主绑定】
binding_ref={binding_ref}
market={market}; locale={locale}; policy_version={policy_version}
input_version={control,inbox,cases}
这些值由宿主决定；不得选择其他收件人、账号或修改绑定。
【判断顺序】
先查关系控制、当前事件、未结事项、承诺和已经排队的动作。
先回应当前明确需求，再考虑新的推广机会。
按需加载匹配市场和版本的产品 Skill，不加载开发或运维 Skill。
通过授权工具查询当前商品、条件、申请、卡片和执行证据。
缺失、过期、冲突或不可用不等于零或不符合资格；先查再决定。
达人陈述、平台事实、推断和公司规则分开，不把历史条件当现在事实。
一条消息可涉及多个事项；更新各自状态，只组织一份对外沟通计划。
只问影响下一步且现有信息无法确认的问题，不重复索取已知信息。
优先处理拒联、人工接管与时间约定，取消其影响范围内的旧计划。
范围内且事实齐备的常规工作应继续，不为了规避判断全部交人。
不发明免费样品、佣金、时效或资格，不把 MX 规则套到 BR/IT。
独立研究才请求有界专业任务；普通回复不拆成多个 Agent。
你不直接写业务库或调用发送、建链、审批；只提出受限更新和下一步。
unknown 先核验，不视为成功、明确失败或重新发送的许可。
历史导入不是实时入站，必须经过当前事实复核才考虑接续。
【输出】
只输出 decision.v1，使用 binding_ref、input_version、evidence_refs。
state_updates 保存有来源的陈述、偏好、抑制、事项或承诺建议。
next_step 使用注册分支；等待有唤醒条件，交人有具体决定，结束有目标证据。
发送、送达、采用方案和合作完成分别表达；reason 简洁，不输出内部推理。
```

### 2.2 十二项核心工具合同

名称是适配器合同候选；R 为业务只读，P 为本次运行内构造提案，W 仅由程序调用，**不注册给模型**。代码固定身份、市场、对象范围、查询上限和超时，不能依靠提示约束替代权限检查。

| 工具 | 参数范围 | 返回与副作用边界 |
|---|---|---|
| R `read_relationship_context` | 不接受达人身份参数；可选宿主提供的事项引用集合 | 当前控制/版本、偏好、承诺、机会与未结事项；仅本关系 |
| R `read_messages` | 本关系消息引用、主题、游标与有界数量 | 原消息片段、方向、发生/接收时间及来源；不跨关系搜索 |
| R `read_active_policy` | 本市场动作/商品范围，规则引用必须来自宿主 | 生效政策、版本与缺项；不修改规则或补造数值 |
| R `load_product_skill` | 注册表允许的 ID/版本 | 已筛市场/权限的指令正文与 hash；不执行脚本 |
| R `search_offers` | 已知需求、筛选条件、允许货盘集合与有界页码 | 程序过滤的候选引用、适用原因和待准备事实；不自动选入或建链 |
| R `read_offer_evidence` | 允许的 offer 引用与字段集合 | 精确商品/活动、当前条件、样品路线及事实时间；不拼接不同方案 |
| R `read_creator_evidence` | 本达人字段集合、明确统计窗口 | 画像、带货信号和来源；不推断当前仍有实物 |
| R `read_cooperation_evidence` | 本关系关联的事项/申请/卡片/执行引用及类型 | 对应业务状态、有效路径、回执与可观测范围；不审批、创建或发送 |
| P `build_content_plan` | 有界正文/固定字段、允许 offer 与证据引用 | run 内的 `content_plan_ref`、组件及校验问题；不建发送任务、不变业务状态 |
| W `commit_decision` | 网关已验证的 decision.v1 与宿主绑定 | 原子保存受限 state_updates、提案、Wake/后续工作；失配返回冲突 |
| W `dispatch_intent` | 已持久冻结的动作意图引用 | 再次门禁校验并调用指定执行器；不接受自由 receiver/账号参数 |
| W `verify_execution` | 待核验意图/组件引用 | 只读查外部结果并更新本系统核验记录；不以补发取得证据 |

R 工具可调用已经授权的远端读接口，证据落盘由程序统一记录，不因此获得商业写权限。`build_content_plan` 生成的引用绑定本次 run；提交时复制并冻结完整内容，重启后不依赖内存引用。所需工具缺失时返回明确能力缺口。专业委派通过 `next_step.kind="request_delegate"` 进入宿主任务流程，不额外暴露无限递归工具。

## 3. 单次关系事件的完整合同

1. **先收事件。** 保存来源 ID、发生/接收时间、市场、消息方向、事件类型与 payload 引用，再确认接收成功。历史导入和评估事件不订阅真实外发。
2. **定位与合并。** 由程序解析稳定身份、相关事项和已有工作。无法确认身份留在待解析区；不能让模型用近似昵称选择收件人。同一关系的重复触发可以合并，但保留各原事件。
3. **领取工作。** worker 取得有期限的租约、单调 fencing token 和输入版本，随后释放短事务再调用模型。账号通道资源与关系规划租约分开。
4. **组装上下文。** 注入生效策略、当前事件、未结事项/承诺、近期相关消息及必要证据；工具凭证留在服务端。模型只能查询授权对象范围。
5. **工具与判断。** 工具返回有来源和时间的事实；模型在预算内选择查询，产出 Decision、必要 Wake 或 Delegate 请求，不能通过查询工具暗中发送。
6. **验证并提交。** 验证结构、引用、字段权限、市场口径、当前控制/事项/收件水位。输入过时则取消提案并合并一次新判断。有效的内部更新与后续意图可靠提交。
7. **执行前复核。** 执行器重新检查账号、联系限制、动态条件与动作依赖；冻结外发内容和组件参数，先记提交意图，再调用平台。
8. **回执驱动结果。** 保存组件级结果；用可支持该阶段结论的证据更新事项。平台接收、送达、已读、采用方案和合作完成分别表达。
9. **结束本次调用。** 有下一事件或到期条件则保存 Wake，释放 worker。模型调用完成不代表事项完成，等待不需要常驻模型。

调用失败由当前步骤的合同决定恢复方式；不得把整段过程包进可重复执行外部动作的通用 retry。

## 4. 最小 Decision 与 Wake

下列 JSON 都是 **synthetic 合同样例**，不对应真实达人、日期约定或可发内容。字段采用严格 schema；模型不能增加任意数据库字段或未提供的引用。宿主从 run 绑定恢复真实身份，模型回显的 `binding_ref` 不构成授权。

```json
{
  "schema_version": "decision.v1",
  "binding_ref": "binding_demo_01",
  "input_version": {
    "control": 7,
    "inbox": 12,
    "cases": {"case_demo_a": 3, "case_demo_b": 2}
  },
  "evidence_refs": ["message_demo_12", "offer_demo_3"],
  "state_updates": [
    {
      "kind": "record_statement",
      "scope": {"product_ref": "product_demo_a"},
      "value": {"usable_item_possession": "creator_says_no"},
      "source_ref": "message_demo_12"
    },
    {
      "kind": "update_case",
      "case_ref": "case_demo_a",
      "expected_revision": 3,
      "change": {"blocker": "physical_item_unavailable"}
    }
  ],
  "next_step": {
    "kind": "propose_message",
    "purpose": "answer_current_product_request",
    "case_refs": ["case_demo_a", "case_demo_b"],
    "content_plan_ref": "content_demo_01"
  },
  "reason": "更新实物障碍，并回答同一消息中的其他商品需求。"
}
```

`state_updates` 只允许注册的操作：记录带证据的达人陈述、偏好/纠正，增删明确范围的触达抑制，更新本关系事项，登记承诺建议。实物持有是有时间的陈述，不存成永久偏好。不允许模型修改商业规则、远端身份、平台结果或任意 JSON path。一个事件可以更新多个事项，但只组织一份对外沟通计划；每个被改事项均有版本约束，事务冲突不能落下一半相互依赖的更新。

`next_step.kind` 候选为 `propose_message / wait / request_delegate / transfer_owner / request_human / finish_case / record_only`。每个分支只有自己的字段：`propose_message` 如上例；`wait` 携带 `wake_plan`；`request_delegate` 携带 `delegate_plan`；`transfer_owner` 携带 `handoff_plan`；`request_human` 携带 `decision_needed/options/blocked_scope`；`finish_case` 携带 `case_ref/outcome/completion_evidence_refs`；`record_only` 只记录 state_updates，不强行发消息。暂不具备跨 Agent 转移时关闭 `transfer_owner` 分支，不假装已接通。

达人已经表达的事实/拒联立即保存并影响未发动作；草稿中“我明天帮你处理”的承诺先是待发承诺，随对应发送结果激活或进入结果待核验，不能把未发草稿当已对外许诺。既有真实承诺不得被新摘要或新策略静默覆盖。

```json
{
  "schema_version": "wake.v1",
  "wake_ref": "wake_demo_01",
  "relationship_ref": "rel_demo_01",
  "case_ref": "case_demo_a",
  "condition": {
    "any_of": [
      {"event_type": "sample.state_changed", "subject_ref": "sample_demo_01"},
      {"event_type": "message.received", "subject_ref": "rel_demo_01"}
    ]
  },
  "review_at": "2026-09-18T12:00:00Z",
  "on_wake": "recheck_current_facts",
  "dedupe_key": "case_demo_a:sample_observation:v1"
}
```

Wake 只描述白名单事件条件和检查时间，不接受任意代码/cron。真实时间来自明确约定或生效策略，保留当地时间与 IANA 时区；复查不是自动催促。事件已满足时直接接续；事项结束、人工控制或新事实改变安排时，旧 Wake 失效。触发只产生一次待处理工作，处理前再检查条件。

## 5. 1:N 关系、有限 worker 与控制权

一个 Agent 定义可以服务大量达人。关系以核实的平台身份及市场关联；联系人、昵称、共享经纪人号码不是唯一键。未来跨渠道的确认/撤销绑定需要版本，撤销错误关联后派生上下文也重建。

关系控制至少记录 `mode(auto/human/paused)`、owner、control revision、入站水位、当前 lease/fencing token。不同关系并发处理，同一关系只有一个有效外联决策归属；只读专业分析可以并行。租约到期后旧 worker 即使返回，也不能提交或绑定执行器。

人工接管与外发的最后本地提交通过同一关系临界区协调。接管先改变控制版本、阻止尚未提交的动作；已在途请求不能物理撤回，界面须显示哪些仍在核验。交还时读取人工处理结论、最新消息和状态，再规划；不恢复暂停前旧文案。

控制版本、条件提交与幂等事实由自控业务状态维护，不能仅相信供应商 session ID。框架 checkpoint 只保存明确需要的运行信息，不成为另一份全量会话真值；任何涉及外部托管的运行信息都要核实其数据边界，不能以框架默认行为扩大长期状态托管范围。

## 6. 专业委派合同与真实权限隔离

```json
{
  "schema_version": "delegate.v1",
  "task_ref": "delegate_demo_01",
  "parent_run_ref": "run_demo_01",
  "mode": "as_tool",
  "objective": "独立核对候选商品的多来源证据并比较适配，返回可追溯结论",
  "allowed_subject_refs": ["candidate_demo_a", "candidate_demo_b"],
  "evidence_refs": ["profile_demo_4", "preference_demo_2"],
  "tool_scope_ref": "readonly_candidate_analysis.v1",
  "output_schema_ref": "candidate_comparison.v1",
  "budget_profile_ref": "bounded_analysis_poc.v1",
  "completion_rule": "各结论有证据引用，缺失资料明确返回未知",
  "deadline_at": "2026-09-11T12:05:00Z"
}
```

brief 明确目标、边界、可用资料、交付结构、截止与预算。子任务只拿可序列化的必要字段和受限工具客户端；不拿完整聊天、共享可变状态、数据库连接或 `backend` 对象。服务端按任务身份逐次校验工具、对象范围和操作类型，子任务不能继承父任务写权限，不能凭自己返回的 scope 扩权。

同进程的受信任代码隔离不是 OS 沙箱。若未来允许第三方可执行插件，必须增加实际进程/权限边界；产品 Skill 默认只含指令与注册引用，不执行夹带脚本。子任务产出存为有版本工件，父任务取引用与必要摘要；结果有效不代表父输入仍新鲜。

`as_tool` 是已确认的按需协作基线：只有构成独立研究的比较、检索等任务才交专家，完成后返回关系负责人；普通选品或回复不因名称不同就拆 Agent。`handoff` 保留为后续扩展候选，用于专家确需负责下一段协商的情况，须先验证收益。启用时必须有交接原因、目标角色、事项范围、上下文引用、控制版本与返回条件，并原子切换归属；它不等于转人工。委派深度与资源预算通过小闭环确定，不默认任意递归创建 Agent。

## 7. 上下文、记忆、压缩与矛盾

| 层 | 内容 | 更新与使用 |
|---|---|---|
| 稳定指令 | 角色、权限、输出合同、通用事实原则 | 固定版本，消息与网页不能覆盖 |
| 当前策略 | 该市场/活动的已授权动作与商业规则 | 引用生效版本；缺规则只阻断依赖动作 |
| 当前工作集 | 新事件、未结事项、承诺、相关近期消息 | 每次按任务取少量高相关信息，多事项并存 |
| 可检索证据 | 原消息、商品/申请/执行记录、字段时间 | 按需读取；引用包含来源版本和观测时间 |
| 派生记忆 | 偏好、摘要、模型推断、纠正关系 | 可重建；推断与明确事实分开，不升级成政策 |

工具证据至少包含 `ref/subject/status/observed_at/valid_until/facts/source_ref`，必要时保留发生时间与本系统首次获知时间。`missing/stale/unavailable/conflict` 都不等于零或不符合资格；查无记录只有在范围完整时才支持限定结论。

压缩先移除冗余工具正文，保留关键引用、未兑现承诺、拒联范围、人工决定和未解问题。涉及“上次那款”时能回查原文。冲突保留双方来源，按业务事实源和时间核查；人工修正也需来源，不能用任意聊天覆盖平台回执。上下文预算不足可拆只读调查，不能为了装得下把未结事项丢掉。

## 8. 产品 Skills 与 Codex 开发 Skills 分开

Codex Skills 服务开发者编程、研究和运维；产品 Skills 服务达人业务运行。两者使用独立目录、注册表、加载权限和版本，不把开发机器 `.codex/skills` 挂进产品，不把里面的 shell、部署或插件安装权授予产品 Agent。

```json
{
  "id": "product.existing-item-link",
  "version": "0.1.0-draft",
  "status": "staged",
  "markets": ["mx", "br", "it"],
  "locales": ["es-MX", "pt-BR", "it-IT"],
  "trigger": "已有实物并请求对应商品方案",
  "required_tools": ["resolve_product", "read_offer", "read_asset_state"],
  "policy_keys": ["offer_terms", "message_actions"],
  "output_schema_ref": "decision.v1",
  "valid_until": null,
  "content_hash": "sha256:synthetic",
  "eval_suite_ref": "existing-item-link.v1",
  "owner": "business-policy-owner"
}
```

市场列举表示设计覆盖，不表示三市场已开放；运行注册表还要检查当地已验证的工具与政策。主提示只加载 Skill 索引，宿主筛版本/权限后按需读取正文。工具暂不可用与业务根本不提供分别处理；未接通技能保持 staged，不靠文字承诺能力。

参考案例先提炼诉求、事实需求、允许动作、等待与完成标准，再由业务负责人确认规则；语言风格可以学习，历史免费样品、佣金与期限不能直接生效。MX 规则不套用 BR/IT。发布流水线检查 metadata、引用、schema、工具权限和正反评估；固定策略/提示/Skill/工具/模型版本组合做差异回放。评估者是流水线中的代码或有界 judge 调用，不是常驻人格。

回滚产生可审计的版本切换，只影响新判断和未提交提案；在途/未知动作保留原版本核验，已发内容和真实承诺不重写。

## 9. 可靠工作合同

| 情况 | 必须实现的结果 |
|---|---|
| 重复或乱序入站 | 稳定远端键去重；保存发生与接收时间，不因晚到旧事件覆盖新业务状态；缺口可追查 |
| 模型期间收到新回复 | 旧输入水位失效；合并后重新判断，已取得且仍有效的证据可复用 |
| 提交前重启 | 从持久工作重新领取；按同一幂等键找既有意图，不重复建立外部动作 |
| 外部已提交但本地未收到结果 | 进入 unknown；先查远端/执行记录，不靠换号或重发取证 |
| 人工接管或明确拒联 | 立即影响相应未发动作；记录范围，不能误关所有主动服务或自行恢复 |
| 多组件部分成功 | 文本、各商品卡分别记结果；只对确定未执行且仍允许的组件考虑重试，不重发已成功文本/卡片 |
| 组件结果未知 | 该组件及依赖它的后续进入核验；无关且已授权的服务可继续，但不能声称整份交付成功 |
| 方案在排队时过期 | 重新查询并规划，原提案失效；不能把另一活动条件拼进冻结消息 |
| 事项结束 | 区分达成、拒绝、取消、过期、不适用；完成需相应目标证据，沉默不算合作成功 |
| 恢复服务 | 先检查水位、租约和在途意图，再恢复新领取；不清库或批改成功来消除异常 |

外发 bundle 有逻辑联系 ID、组件顺序、各组件幂等键和依赖。平台接收不等于达人送达；“已交付”使用哪一级证据由场景合同明确。模型可以解释未知，不能替执行器宣布成功。所选框架的 checkpoint/replay 必须通过这些例子；托管 session 也不提供外部动作只执行一次的保证，且不在当前长期状态默认方案中。原理见[研究报告第 7 节](../research/agent-cases-review.md#7-持久执行不等于外部-exactly-once)。

## 10. 有限预算与小团队负载

每个工作项和整条委派树都有模型请求、tokens、工具调用、并发、成本、墙钟时间与深度预算。消耗由程序聚合，子任务不能通过重新创建任务重置额度。费用耗尽明确进入等待或停止，不把未处理全部转给运营。

新机会队列按有效增量持续补充；当前咨询与到期承诺优先。账号容量、真实平台额度、模型费用、工具健康与服务积压形成 backpressure，不暗设固定业务日总人数。队列超出阈值先减少新获客，恢复设置低水位与稳定窗口，避免反复开停。

同根因故障聚合成一项可处理问题，同时保留每位达人的事实；不同商业条件不能批量冒充同一批准。运营卡片只呈现具体决定、证据、选项、影响、负责人和时限，正常等待由系统管理。模型任务预算、队列阈值和 worker 数需通过当前设备及接口压测确定，不由 M2/16GB 直接推导。

## 11. 必须比较的 PoC

在已确认协作与自控数据基线内，用相同三市场模拟/脱敏场景比较框架实现；对独立研究任务比较直接处理与按需委派的实际收益。至少覆盖多需求消息、拒联、过期事实、重启、乱序、接管、未知发送和多组件部分成功。首轮不把长期会话托管或广泛 handoff 当成默认实施前提，后续有明确价值再作为扩展评估。

记录业务判据、错误动作、人工分钟、P95 延迟、每事项成本、上下文恢复和版本升级行为。框架选择取决于这些差异及维护工作量；供应商文档存在、示例能跑或一次模型正确回答，都不是选择结论。
