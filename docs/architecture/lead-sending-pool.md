# 达人线索统计与发送池（设计）

2026-09-15，用户要求：在「达人线索查询队列」下方增加一个大卡片，展示**找到了多少线索、发了多少**，并设计一个**随冷却时间动态变化排序的发送池**；同时在顶部漏斗条下方增加几个统计卡（选出多少 / 发了多少 / 还有多少没发）。

**本页是设计，尚未实现。** 发送仍为暂停状态，本设计不包含启用发送。

## 一、实测现状（2026-09-15）

线索来源：`source_edge` 中 `sourceKind='kalodata_http'` 的边。

```
线索边（达人×商品）        7,225
覆盖商品                   1,468
去重达人 handle            2,334
```

归并（`cycle_identity_outcome`，合计 7,225）：

| 状态 | 数量 | 含义 |
| --- | ---: | --- |
| completed | **5,314** | 已归并到达人档案 |
| unresolved | 1,711 | 找不到对应达人 |
| queued | 125 | 待查 |
| blocked | 75 | 受阻 |

关系与发送：

| 项 | 数量 |
| --- | ---: |
| 已归并到达人的**去重达人** | **1,606** |
| 已建档关系（`relationship`） | 1,607 |
| ├ 已解锁 | 61 |
| └ 拒联 | 1 |
| 已发送过的达人 | **495** |
| ├ 冷却中 | **446** |
| └ 冷却结束可再发 | 49 |
| 从未发送过的达人 | **1,111** |
| 累计发货（`cycle_delivery` confirmed） | 495 |
| 发出商品卡（`cycle_delivery_part` card） | 504 |

**可发送 1,160 / 冷却中 446**，两项互斥且合计等于 1,606。

## 二、顶部第二行统计

顶部现有产品链漏斗（采集 → 筛出 → 已备链 → 待查线索）。下方加一条**达人线索链**，单位是**线索条数（达人×商品）**，不是达人数。

```
线索 5,314  →  已发送 504  →  未发送 4,810
共 1,606 个达人 · 搜索不到 1,711 条
```

| 位置 | 口径 |
| --- | --- |
| **线索**（主） | 已归并到达人的**达人×商品**条数 = 5,314 |
| **已发送**（主） | 已成功发出的达人×商品条数 = 504 |
| **未发送**（主） | 线索 − 已发送 = **4,810** |
| 共 N 个达人（小字） | 已建档关系的去重达人数 = 1,606 |
| 搜索不到（小字） | 归并失败的线索条数 = 1,711 |

**为什么主数字用"条"不用"个达人"**：要发的东西是「某个达人的某个商品」，所以池子、已发、未发都以这个为单位。达人数和"搜索不到"是背景信息，放小字。

口径必须写清：

- 线索条数 5,314 是**已归并到达人的**部分；全部线索边是 7,225，其中 1,711 条找不到达人、200 条待查或受阻。这 1,911 条进不了池子，但要在小字里看得见，否则"7,225 条线索怎么只剩 5,314"就说不通。
- **已发送是累计**，**冷却中是当前瞬时**，两者不在同一条轴上，不放在同一个减法里。
- 全部线索里的去重 handle 有 2,334 个，其中 1,606 个已归并到达人档案。页面上以 1,606 为准（能发的部分）。

## 三、发送池：派生视图，不是新表

**关键设计决定：池子不落库。**

池子的顺序依赖"现在几点"——任何存下来的顺序在几分钟后就过期了。所以池子是由四张已有表**实时算出**的只读视图：

```
关系（relationship）  ∪  线索（source_edge + cycle_identity_resolution）
                      ∪  发送历史（cycle_delivery + cycle_delivery_part）
                      ∪  额度（cycle_contact_reservation）
```

1,606 条规模，每次读取重算的成本可以忽略。不新增表，也就没有"池子表和真实状态不一致"这类问题。

## 四、排序规则（本设计的核心）

排序是**分层的**，因为"能不能发"比"先发谁"更硬：

```
第 1 层  现在能不能发        可发在前，冷却中在后
第 2 层  可发的：线索强度      Kalodata GMV 排名靠前 / 窗口内销量高
         冷却的：解冻时间      先解冻的排前面
第 3 层  同强度：最久没联系的优先
第 4 层  兜底：creator_id 升序（保证顺序确定、可复现）
```

**为什么第 2 层对两类用不同键**：可发的那批要比出"先联系谁"；冷却中的那批此刻发不了，唯一有意义的顺序就是"谁先被解冻"。用同一个键排这两批是没有意义的。

**动态性从哪来**：冷却到期不是事件，是时间的函数。所以池子每次读取都重算，某个达人一到点就自动从"冷却"层升到"可发"层，无需任何后台任务。

## 五、冷却与额度口径（复用既有规则，不新造）

| 规则 | 现值 | 来源 |
| --- | --- | --- |
| 已解锁达人冷却 | 24 小时 | `cycle_delivery.py`（对应用户说的"一天最多发一次"） |
| 未解锁达人冷却 | 48 小时 | 已确认策略 |
| 未回复/未加橱窗前我方上限 | 5 条（商品卡占 1 条） | 已确认策略 |
| 月度刷新 | 到上限后过一个月可再发 | 已确认策略（按自然月/滚动窗口未核实） |
| 排除项 | 拒联、人工接管、正在处理咨询 | 已确认策略 |

**池子里要能看到"为什么现在不能发"**：冷却中显示解冻时间；额度用完显示等待刷新；被排除的显示原因。不把"不能发"笼统显示成"不可用"。

## 六、卡片内容

放在「达人线索查询队列」下方的大卡片：

1. **四个数字**：今日可发 / 冷却中 / 未发送 / 已发送（累计）
2. **排序规则一行说明**（就是上面第四节，让人一眼知道池子怎么排）
3. **池子列表**（前 20 行，可展开）：达人 handle、来源商品、达人佣金、线索强度、**可发送时间**、当前状态
4. **待确认项**：额度受限数量、被排除数量

## 七、明确不做的事

- **不加发送按钮**：发送仍为暂停状态（`service_reply_config.enabled=0`）。本卡片只做统计与排序展示。
- **不存池子顺序**：见第三节。
- **不改冷却与额度规则**：复用既有实现，只在页面上如实展示。

## 八、已确认的三项（2026-09-15）

1. **排序主键**：线索强度用 **Kalodata GMV 排名**（`sourceRank`，越小越强），与线索来源口径一致。
2. **池子粒度：达人×商品**。同一达人可因不同商品出现多次；先发最好的那条，等冷却结束再发其次的。**线索池一直留存，不因发过一次就消失。**
3. **未解决的 1,711 条**在页面上单独显示，文案用 **「搜索不到」**（不用"待补身份"）。

### 粒度决定的一个关键区别：池子的单位是「达人×商品」，冷却的约束在「达人」上

用户的要求「一天最多给达人发一次」是**针对达人**的，不是针对某个商品。所以：

- **位置（池子的一行）** = 达人 × 商品
- **冷却** = 按达人算。一个达人在冷却中，他所有的商品行**同时不可发**
- 冷却一结束，他**排名最靠前的那条还没发过的商品**自动升到可发层

这也正好和「未回复/未加橱窗前最多我方 5 条，商品卡占 1 条」相合：一个达人一个月内可以收到最多 5 个不同商品，但**任何一天最多一条**。

于是第 2 层排序要按达人分组看：

```
位置 = (creator, product)
creator 冷却中  -> 该达人的全部位置都排在冷却层，按解冻时间
creator 可发    -> 只取该达人排名最好的那条未发位置，参与可发层排序
                   其余位置留在池中等待（不是删除，也不是丢弃）
```

**这就是"池子不会丢失"的实现方式**：发过的位置标记为已发但保留，同一个达人的次优位置一直在池中，等冷却结束自然上位。

### 由此带来的一个页面要求

池子列表需要能按**达人**折叠：一行是达人，展开后是他名下的多条商品位置（已发 / 待发 / 冷却），否则同一达人会重复出现很多行，反而看不清。

## 九、滚动模型与「达人回复未解决就不发下一条」

用户确认（2026-09-15）：发完一个达人的一个商品就滚动到下一个，是**持续滚动的过程**，好不容易找来的线索不丢。同时新增一条硬规则：

> 后续接入 AI 回复后，达人回复**没有解决**的，就先不发第 2 个给他；有些回复 AI 判断**不需要再回复**的，那种没关系，可以继续发；遇到达人有问题的那部分，就要停在那里，等把问题解决了才能继续进入发送池。

### 这条规则现有状态机已经实现，不需要新造

`lib/cycle_service.py` 的决策动作与 `relationship` 状态正好一一对应：

| AI 判定 | 动作 | 落到状态 | 对发送池的影响 |
| --- | --- | --- | --- |
| 致谢等无需回复 | `review_no_followup` → `resolved_no_reply` | 无 open 案件，`mode` 保持 `auto` | **放行** ← 用户说的"没关系，可以继续发" |
| 佣金问题 / 样品申请 / 商家替换 / 其他 | `human` | `service_case` 插入 `state='open'`，`relationship.mode='human'` | **阻断** ← 用户说的"停在那里" |
| 明确拒联 | `suppress_marketing` → `suppressed_no_reply` | `relationship.rejected=1` | **永久阻断** |
| 人工处理完毕 | `resolve_case()` | `case.state='resolved'`，`mode` 回 `auto`，`inbox_until=0` | **恢复放行** ← 用户说的"解决了才能继续" |

所以池子的阻断条件就是这三条，全部是既有字段：

```
阻断发送 = 有 open 的 service_case
        OR relationship.mode = 'human'
        OR relationship.rejected = 1
```

`resolve_case()` 会把 `mode` 改回 `auto` 并清空 `inbox_until`，所以**人工一解决，该达人自动回到池子**，不需要任何额外动作。`open` 案件作为第二重信号保留，即使 `mode` 因某种原因不同步，也不会误发。

数据现状：`service_case` 里 open 1 条、resolved 1 条；`relationship` 中 `mode='human'` 1 条、`rejected` 1 条。AI 回复本身仍是暂停状态。

### 对排序的影响：加一个第 0 层

原来的四层排序前面再加一层，因为"能不能发"里最硬的是这一条：

```
第 0 层  是否被阻断      被阻断的移出可发层，进入「等达人回复」层
第 1 层  现在能不能发    可发在前，冷却中在后
第 2 层  可发的：线索强度  Kalodata GMV 排名
         冷却的：解冻时间  先解冻的排前面
第 3 层  同强度：最久没联系的优先
第 4 层  creator_id 兜底
```

### 池子因此有四个层，而不是两个

| 层 | 含义 | 是否参与发送 |
| --- | --- | --- |
| 可发 | 冷却已过、未被阻断 | 现在就能发 |
| 冷却中 | 距上次发送未满 24h/48h | 到点自动上位 |
| **等达人回复** | 有未解决案件或人工接管 | **解决后自动上位** |
| 已排除 | 明确拒联 | 不再发送 |

页面上这四层要分开显示。把「等达人回复」混进「冷却中」会让人以为是时间问题，而它其实是要人去处理的事情——**这两种"发不了"性质完全不同**。

## 十、实现（2026-09-15）

`scripts/lib/lead_pool.py` 计算，`scripts/lead-pool.py status` 是 CLI，`/api/lead-pool` 是接口，页面两处消费：顶部第二行统计 + 队列下方的「发送池」大卡片。

**实测分层**（位置合计 4,144，与 `ready + queued + cooling + awaiting_reply + excluded + sent` 完全相等，有测试钉住这条恒等式）：

| 层 | 数量 |
| --- | ---: |
| 可发（每达人一个位置） | **1,148** |
| 池中等待 | 1,083 |
| 冷却中 | 1,417 |
| 等达人回复 | 1 |
| 已排除 | 0 |
| 已发送 | 495 |

**冷却 1,417 > 已发送 495** 正是"达人级冷却"在起作用的证据：495 个达人被冷却，他们名下的 1,417 条位置一起等。

### 数字口径（最终）

顶部第二行主数字用**条（达人×商品）**：

```
线索 4,144  →  已发送 495  →  未发送 3,649
共 1,606 个达人 · 搜索不到 1,711
```

注意 4,144 是**去重后的位置数**：已归并的线索边是 5,314，同一达人对同一商品可能有多条边（不同来源 handle 拼写），去重后 4,144。全部线索边 7,225 = 已归并 5,314 + 搜索不到 1,711 + 待查受阻 200。

### 桥接层强制校验

接口校验里有两条硬约束，违反即判为不可用：

1. **各层之和必须等于位置总数**——池子是一个划分，任何位置都不能漏也不能重。
2. PID 必须是 19 位数字，层名必须在已知集合内。

### 页面卡片（2026-09-15 精简）

卡片只保留「四层拆开＋一条进度」：4 个数字 + 发送进度条 + 6 层小卡 + 口径说明。
原来铺在下面的「可发前 20 行」表和「池中等待与冷却明细」折叠区**已按用户要求删除**——池子不提供发送入口，也没有逐行动作，罗列只会把状态淹没。

### 测试

11 项：排序按 Kalodata 排名、每达人只占一个位置、冷却按达人波及全部位置、已解锁 24h 快于未解锁 48h、open 案件进入「等达人回复」而非「冷却中」、案件解决后回到池子、拒联是永久排除而非等待、已发位置保留不删除、分层恒等式、库缺失不抛异常、limit 只限制行数不限计数。
