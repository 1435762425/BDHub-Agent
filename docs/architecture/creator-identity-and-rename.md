# 达人身份、handle 发现与 OEC 刷新

2026-09-12。用户明确要求允许不同渠道不断输入 handle 扩大达人池，同时已获得 OECID 的达人不能因改名而丢失。**handle 是发现入口和可变名字；市场 + OECID 是平台身份，内部 creatorId 是业务关联键。** 同一达人改名不新建关系，不重置拒联、接管、联系频次、去重或 Agent 上下文。

## 两条入口

| 输入和任务 | 请求路径 | 入库规则 |
| --- | --- | --- |
| 新来源只有 handle | 该市场精确 Find → 取得 OEC → Profile | 先记发现线索；精确匹配后按市场/OEC 复用或新建身份 |
| 已有 OEC，需要刷新 | 直接 Profile(OEC)，不执行 Find | 仍是原 creatorId；返回新 handle 时更新名字并留历史 |
| 同时有 OEC 和旧 handle | OEC 优先，旧 handle 仅审计 | 不把旧名字放进请求，不要求响应还叫旧名字 |
| 当前 OEC Profile 没返回名字 | 同 OEC 补身份分型；仍缺则保留历史名字 | 保留原名字的核验时间，不宣称本次返回过它 |
| Find 找不到新输入 handle | 保留待解析线索 | 不伪造 OEC，不把待解析线索算作已核验达人 |
| OEC 请求超时或失败 | 记录失败，按错误类型调度核验/有界重试 | 不删达人，不退回用旧 handle 搜另一个人 |

因此“每个输入 handle 最终都有 OEC”是解析成功后的目标，不是可以强制成立的事实。本轮意大利名单仍有 17 个未解析 handle，应留在线索区，等后续新来源、正确名字或平台 OEC 证据补齐。

## 改名与名字复用

例如 OEC 111 曾叫 alice，后来改为 alice.new：从原档案生成刷新请求时只取 111。返回同 OEC 的 alice.new 后，保持原 creatorId，当前名字更新为 alice.new，alice 留作历史别名。

如果新的 OEC 222 后来使用 alice，新导入的当前 alice 必须经过一次当前精确 Find，解析为 222 后形成另一身份。111 的合作、拒联、消息与去重不能转给 222。历史别名搜索可以显示两条候选及观察时间，但不能自动决定一条新名单或历史第三方记录属于谁。

同理，多个来源输入同一人时，精确返回同市场同 OEC 就复用同一身份，保留各来源线索。Kalodata ID、样品 creator_id、平台 OEC 分属不同命名空间；当前 handle 对上 OEC 不能证明更早的第三方交易记录归属。后续真正的跨来源绑定应保存独立证据，撤销时也不删除原始记录。

## 存储与顺序

- creator_identity：唯一键 `(market, oec_id)`，内部不可变 creatorId，最近一次实际返回的 handle 及其核验时间，最近一次成功观察时间。
- identity_observation：不可修改/删除的 Profile/Find/失败事件，含来源引用、时区时间、内容指纹和允许字段；名字历史来自这些实际观察。
- handle_lead：尚未确认身份的输入及来源，与正式达人身份分开。
- handle_lead_resolution：一次当前精确 Find 的归属证明；已解析线索不能因名字后来被复用而改绑。

同事件同内容重复执行幂等；同事件键出现不同内容报冲突。较早快照晚到只追加历史，不能回退当前名字。同一时刻两个名字冲突保留证据并标注冲突，后续更新观察可解决。没有名字的成功响应只更新画像观察时间，不能刷新历史名字的核验时间。失败也不修改最后成功观察时间。

OEC 以原始十进制字符串保存，拒绝数字类型输入造成的精度损失。首期按市场隔离，不因相同 OEC、昵称或 handle 自动跨市场合并。业务表和关系 Agent 的持久上下文应引用 creatorId；刷新任务保存 market/OEC，不保存“下次再按 handle 找人”的指令。

## 实现和当前边界

本轮已在新项目实现：

1. `scripts/probe-italy-profile.py` v3 支持 handle 与 OEC 两种输入。OEC 明确存在时优先直查，首个返回即检查同 OEC，防止错 OEC 被用于补抓；沿用现成 EU HTTP、验证、节拍器与清理。
2. `scripts/lib/creator_identity.py` 提供独立持久身份库、发现线索、精确解析、别名历史、幂等、迟到保护和失败保留；可从已有身份生成 OEC 刷新输入。
3. `scripts/import-creator-identities.py` 验证已保存探针证据，导入新项目 `var/creator-identities.sqlite`。只导入允许字段，不读取旧业务库或联网。

真实数据已导入 31 个稳定身份、48 条发现线索，其中 31 条已解析、17 条待解析；65 条观察包括 31 次 Find 解析、31 次完整画像和 3 次 OEC 刷新。重复导入全部输入，五项计数都不变。

该事实库是后续身份入口，不是另起一套发送或匹配规则。现有 matching/second-pilot 试点库与页面尚未迁接；迁接时以显式旧 ID → creatorId 引用表接入，保留完成/未知/暂停状态，不能重建业务记录来获得“新身份”。尚未启动全量定时刷新、真实消息发送或生产迁移。

## 本次验证

仅给 3 个现有意大利达人提供 OECID，不提供 handle：3/3 返回同 OEC 和当前 handle，Find 请求 0，Profile 请求 8（2 人需要 `[1,6]` 身份补抓）。账号身份文件未修改，旧库写入和真实发送为 0。

Profile-only 本轮可用字段数为 20、17、5，少于此前 Find+Profile 的 22、19、6；这不影响本次稳定身份验证，也不能把 Profile-only 称为全字段等价。字段观察独立留痕，历史值仍是历史值，不用旧值伪造本轮远端响应。本轮没有遇到真实平台改名样本；改名、名字复用、无名字响应、错误 OEC、迟到快照和重放用隔离自动测试验证。

可复现的真实汇总在 `var/italy-oec-only-validation-20260912/`，公开证据见 [身份与改名验证](../research/creator-identity-validation-20260912.json)。相关离线检查仅需 Python，不涉及 Next 构建或旧库迁移。
