## 1. 结论与完成目标

**话术顺序选择已经接通并能识别历史使用；四市场全功能运行仍有必须先修复的缺口。** 当前不能只打开四市场开关就宣称发送、收信、AI 回复和恢复都正常。

本轮用户要求先检查并写计划，随后再让模型执行。本轮不启动发送、不启用 AI、不改变现有采集/收信/调度器状态。后续执行应完成下述修复、验收、正式全量运行与观察，不停在一两条测试成功。

正式经营目标：持续处理四市场**全部当前合格且在已授权范围内**的发送池，可能跨多个发送窗口、自然日及额度周期；不把 10、100 或 500 人当作本轮总任务终点。不能为追求清零而绕过冷却、拒联、未结回复、素材资格、模板耗尽或平台真实额度，也不能向同一达人连续倾倒全部话术。

完成标准分两层：

1. **可以正式上线**：四市场 sender/inbox/Agent 全链已接通，下文 P0 缺口关闭，当前身份及数据可用，必要真实能力验证完成，用户在页面完成正式启动。
2. **完成本轮闭环**：已冻结的启动范围全部进入“确认触达、明确等待或明确排除”之一；确认数可回查，所有不确定结果有原意图处置；新入站被及时处理或交给人工；跨日和下一轮 Campaign 刷新能够续跑。仍有真实未知或待人工事项时如实保留，不写成全部成功。

## 2. 话术轮转核查

### 2.1 当前真实行为

- 按市场 plan 和稳定 `creatorId` 识别同一达人，不按每个 PID 重新从第一条开始。
- 使用固定 `SEND_IDS` 顺序，从**当前审核有效且该达人未使用**的模板中选下一条。首次默认 `standard`（利益直击型），再次合格触达默认 `brief`（利润最大化）。第一条未获批准时会跳过，不保证每个人第一次一定是编号 1。

### 4.2 统一账号调度的方案

有必要加强，但不新建平行账号池。继续使用固定8账号、现有 identity generation、resource slot、lease/fence、IM write gate 和持久意图。

- 通信账号协调收信、OECID/Profile、持续发送、AI；货盘账号协调 Campaign、全托、选入、TapLink。
- Kalodata 保持最多2市场并行；账号维护全局1个；同账号真实外发串行。初期大体积 catalog 同时最多2个、模型生成最多2个为待实测调参起点，未验吞吐前不加速。
- 账号资源采用短持有、可观察等待、合理公平性；长 OECID cohort 不应饿死收信。保持当前非重叠外发窗口，不自行引入 AI 与二发争抢优先级。
- refresh/relogin 只由明确认证失败或既定维护触发；Profile 的 HTTP200/code100000/systemError3 不能当作账号失效。Find 已确证 OECID 不因 Profile 失败重查或改成 unresolved。
- 代次必须绑定 market/account/institution/能力。新代次失败保留原发布代次；能力继承仅限相同身份，失败观察优先。只验通信不能推定 sender/AI可用。
- 维护时停止新领取、等待已提交意图回查、释放相应资源，再发布新代次；恢复收信并确认 checkpoint 向前后，按仍有效的页面授权恢复任务。unknown 不转号、不换意图。
- supervisor 至少每30秒检查一次独立 worker，不能被14,400秒的 `_call` 卡住；采用有界退避，连续失败显示原因，不无限快速重启。

## 9. 性能优化顺序

1. **先修调度与正确性**：解除失败run/残留collecting阻塞；补齐收信与外发恢复。错误流程跑得快没有业务收益。
2. **再减重复工作**：sender候选用分页/索引/短期投影，领取时重新验证；每个PID每周期只抓到期源，Find复用resolved/unresolved；同generation标准卡精确复用，未知卡不重复创建。
3. **长作业拆可恢复小步**：Campaign列表、详情、筛分、发布分开计时，已有断点先继续；筛分/发布用短事务，禁止网络I/O期间持SQLite写事务。大响应只留必要证据索引，避免常驻重复解析全量JSON。
4. **合理错峰**：保持现有业务频率，供给作业低峰排队；不在发送/AI窗口集中开8个浏览器重登或Web build。窗口冲突由共用调度合同决定，而不是加多个隐藏定时器。
5. **再测并发**：每次只调整一个并发参数，对比确认吞吐、P95、验证码率、收信延迟、内存/网络错误；稳定后再提高，平台挑战/限流不靠扩号规避。
6. **最后做页面细节**：布局/文案/折叠、键盘和移动宽度，保持业务状态准确可见。无需为本轮引入新服务框架或重写数据库。

## 10. 范围核算、交接与最终报告

每市场保存启动时范围的只读manifest（现有position/source/generation ID），新进入的量单列。资格在执行前变化时记录退出原因，不偷偷从分母消失。建议报告以下恒等式并说明口径：

```text
启动范围 + 本轮新增 = 已确认触达 + 仍待执行 + 等待条件 + 明确排除 + 待核验
每个已领取delivery = ready/running/confirmed/partial_delivery/failed/cancelled/unknown中的一个
完整触达 = 卡confirmed 且文字confirmed；只有卡成功不计完整触达
达人数量与达人×PID位置数量分别核算，不跨表直接相减
```

第一条为运营范围投影：各组必须互斥，同一位置只能进入一个结果；同一达人其他PID作为等待原因。不能直接把不同历史/current head表的总量凑等式。AI的no_reply也是明确处理结果，但不能计为已发回复。

最终执行报告分开交付：

- 代码与测试：提交、版本、关闭的F项、实际测试与仍未覆盖场景。
- 本机服务：worker身份、心跳、跨日恢复、主链进度与资源趋势。
- 只读数据：四市场漏斗、范围、身份、unknown和收信覆盖。
- 真实平台写入：加入/选入/建链/删卡/建会话/卡/文字/AI逐域计数，原意图与回执证据。
- 业务结果：确认触达、有效入站、已回复/待达人/人工、采用与合作；不把进程启动或请求200当成经营完成。
- 未完成项：具体市场/原因/数量/下一动作/下一时间；等待真实达人回复不能伪装已完成AI闭环。
