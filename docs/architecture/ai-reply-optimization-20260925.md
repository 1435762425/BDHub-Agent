2026-09-25 实施进展：Jev 可执行依赖已移除，F6 的交接/回复原子准备和 F4 的首份准备后立即发送已修复并加载；详细测试与授权保持证据见[交付报告](../implementation/continuity-agent-runtime-20260925.md)。下文 F1–F10 保留原审查基线，其余上下文、业务范围和隔离改造仍待后续批次。

## 1. 结论与范围

保留 V2 的基本方向：**一个 DeepSeek 模型读取真实上下文，一次同时决定处理动作和组织正文；确定性代码负责授权、事实引用、状态、水位、去重及发送。** 不恢复五动作固定模板分类器，不增加 Jev challenger、双模型投票或每条回复的第二模型审批。

最值得优先改的是：

1. 明确当前待回复的消息范围，并给模型完整的未结问题与必要历史，避免最近 24 条截断造成漏答和重复提醒。
2. 生产与历史回放分别建立时间边界，让生产回复看见来信后实际已发送的配套邀请文字，同时不把它误当成已回答来信。
3. 从“最多生成 20 份再发一份”改为“领取一位 → 生成 → 复检 → 发出或结算 → 下一位”，缩短等待和草稿陈旧时间。
4. 把模型失败、上下文变化、平台回复未知、商业转人工分开处理；补齐 handoff 原子落账与中断恢复。
5. 清除 Jev 的可执行入口和配置依赖，保留历史事实，并用已确认案例验证单模型质量。

已确认业务政策不重写：固定报价、联系方式、卡异常等人工交接照旧；纯感谢、样品/物流/售后/结算等照既有指南。技术隔离“不转人工”不能覆盖这些商业政策。现有持久授权、四市场语言与独立回复窗口不因优化重置。

## 3. 逐项审查发现

### F1：队列并未表达“这一轮尚未处理的全部消息”（高）

`run-agent-replies.py:73–96` 按 pending.due_at 排序，随后取最新一个 turn；`cycle_inbox.py:49–54` 新来信会覆盖 due_at。`production_context` 又把历史入站混入最近消息，没有明确未处理范围。结果是新消息可能改变排队年龄，模型也难区分历史已答和当前待答。当前代码不一定每次漏答，但没有满足已确认 §9.14 的完整处理范围合同。

**改进：** 使用最早未处理入站时刻作为排队依据；领取时固定本次 coveredMessageIds/水位与 pending/control revision。新消息继续落账，不覆盖此次范围；提交前发现新入站则让未提交候选失效、重新组合。确认/no_reply 只结算被覆盖的范围，未被本次覆盖的消息保留。

### F2：生产上下文时间截断与当前邀请收口不一致（高）

`agent_reply_v2.py:122–198` 以目标来信发生时间为截止点，排除该时刻后的已确认外发。这个规则适合历史回放，却被生产 worker 同样调用（`run-agent-replies.py:138`）。按新规则“卡已确认→达人来信→原配套文字发完”时，生产模型看不到后发的配套文字，可能误解完整邀请。

**改进：** 分出 production/replay 两种上下文模式，共用证据选择器。生产在领取时建立最新本地消息快照，包含真实已确认的后续配套文字并标明用途；历史回放限定当时可观察到的消息、事实和指南。发送前再对照水位，已提交候选保持原正文。不能用当前关系状态冒充历史时刻状态，无法重建的历史字段明确 unavailable。

`observed_messages.py:6–53` 已会按精确 messageId 排除本系统已记录外发，因此不能笼统断言“所有配套文字都会误判成人工回复”。仍需覆盖缺失回执/观测先到等情形，并将真实人工客服回答与 outreach_followup 分开，避免 `replied_after` 单纯按最后外发时间跳过未答问题。

### F3：固定最近 24 条不保证业务记忆，字节预算也未前置处理（高）

`agent_reply_v2.py:15、131–175` 从各来源取消息后再裁成最后 24 条；用户已定规则要求识别“提醒过一次”“已请求联系方式/澄清”“对方已经尝试无效的方法”。这些证据可能在 24 条之前。`previousWaitFor` 只从最后已确认 service_reply 推导，不能替代完整未结事项。`historyTruncated=len(messages)>=24` 也无法准确区分恰好 24 条和真的遗漏。

`draft_provider.py:24、267–295` 总输入限制 24,000 UTF-8 字节；当前仓库指南约 7,935 字节，另有输出合同与上下文。24 条长消息或页面允许保存的长指南可能直接超过限制；`generate` 会把本地输入过长也写成 unknown，继续消耗尝试（273–320）。

**改进：** 按必要证据优先和实际序列化字节分配预算，保留全部当轮待处理诉求、关联真实邀请、当前商品事实、当前等待/人工状态及相关历史证据；先裁无关已结历史。确有超长未结内容时明确分段覆盖与剩余范围，不能静默删掉问题或整件结案。必需内容仍超预算则返回稳定 context_too_large，不向 provider 发送相同失败输入。事实摘要必须带原消息引用，不新增模型生成的自由摘要作为状态真相。

### F4：先生成一批，再每轮只发一条，增加等待与过期（高）

`run-agent-replies.py:95、128–153` 最多取 20 位，串行生成全部候选后只执行最早一条 ready；`main:159–179` 默认每轮再等待 60 秒。只要存在任意 ready 就暂不生成新候选。即使模型/发送很快，也有固定空等；若每次模型慢，第一位要等后面所有生成结束。生成循环中也没有逐项重查 stop/窗口/剩余时间，可能跨窗口继续花费模型调用（逐写门禁仍会阻止窗外发送，不能说已经越窗外发）。

**改进：** 首版按每市场一位一位即时准备与发送，成功后不固定睡 60 秒，有任务且窗口允许就继续下一位；等待/失败时才退避。逐项调用前重读授权、窗口与实际二发缓冲，预留有界生成/发送时间。暂不并发生成 20 位，也不增加多 Agent。只有测量后确认模型成为瓶颈，再考虑极小预取，且 ready 队列有上限、可失效、不可长期囤积。

### F5：一个回复 unknown 仍可阻塞整个市场（高，涉及新业务取舍）

`run-agent-replies.py:102–110` 先查最早 unresolved reply，核验后直接返回；`cycle_auto_reply.reply_blocker:14–21` 在同 plan 任一 service_reply inflight/accepted/unknown 时拒绝全部新回复。对真正正在发出的消息串行互斥合理；对长期结果未知，单项可能占据整个市场窗口。

**改进方向已确认：** 新方案把“同账号当前真实写入互斥”与“某历史意图等待核验”分开。用户已在模块方案 §9.18 确认 AI 回复有限原意图核验后自动技术隔离、不转人工，其他合格达人继续；该达人自动回复与主动推品暂缓，新来信继续保存。具体核验参数尚须评估，未上线前不解除现有门禁。AI unknown 不允许重新生成一份同义回复绕过，交接确认消息 unknown 也不能撤销原商业人工接管。

### F6：转人工锁与确认消息之间存在中断缺口（高）

`agent_reply_v2.py:391–417` 在事务内创建 case、置 pending=human、relationship=human；退出事务后才调用 `prepare_generated` 并关联 decision。后者可因 context/revision 不符失败，或者进程恰好退出。`pending_rows` 排除 human，恢复路径只认已有 service_reply，所以可能留下没有可继续确认消息的人工锁。`tests/test_agent_reply_v2.py:146–153` 只覆盖成功路径，未证明中断点恢复。

**改进：** case、状态变更、确认消息意图及 decision 关联在同一原子操作中落账；复用内部无嵌套事务的准备函数，或保存明确可恢复的中间阶段。先锁后发的业务合同不变，消息已提交只核验。故障注入要覆盖每个落账边界，不能用回滚人工控制或删案件掩盖缺口。

### F7：技术失败状态和重试依据过于混合（中高）

`generate:306–321` 把 provider 超时、本地超预算、JSON/字段校验错误统一标 unknown、对外统一 agent_decision_unresolved；`decision_retry_ready:54–61` 按 turn 计数，而 generate 按 input_hash 计数，存在 ready 就允许继续尝试。窗口内一旦上下文持续变化，旧 ready、失效草稿与新输入的重试不能靠这两个不同口径解释清楚。

**改进：** 模型调用未成功与平台消息送达未知分别命名、分别预算。对于同一明确输入保留有界尝试；本地确定性校验失败先修输入或配置，不重复调用；上下文变化转 superseded，不消耗“平台发送重试”。新输入可以有新版本，但必须保留累计成本/失败记录，不能因无关时间字段变化无限获得新预算。模型失败耗尽处置已在模块方案 §9.17 确认：同一输入总尝试最多 3 次，耗尽自动跳过、不转人工，保留未回答问题；新来信形成的新上下文可重新判断。

### F8：可核对的商品事实与语义检查应加强（中高）

`production_context` 明确提供 pid/listId 与历史消息，但未建立带来源、观测时间及当前有效性的商品事实包。`validate_decision:229–270` 校验字段、路线和引用必须来自输入，且至少一条入站；它不保证引用属于本次未处理诉求，也不验证正文数字/承诺与当前事实一致。不能把 JSON 合法当作语义正确。

**改进：** 提供只读本地事实包，区分“当时卡片显示”“当前已核实条件”“未知”；模型只使用给定事实。校验本次证据引用及路由互斥，已知 PID/比例/链接可以做确定性匹配，但自然语言语义仍由已确认指南及逐案例评测约束，不用几条关键词声称彻底防幻觉。无依据的实时承诺不通过再加一个 Jev judge 解决。

### F9：试聊与生产上下文并不完全同构（中）

`simulation_context:327–349` 只支持最多 20 条纯文本方向/正文及 previousWaitFor；页面同样以纯文本输入（`AgentReplySettings.tsx:30`）。它不能直接模拟真实商品卡、messageId、已处理范围、关系状态、提醒证据或在途意图。离线 `agent_evaluation` 可提供更丰富合成 context，但用户在页面试聊通过不等于生产上下文通过。

**改进：** 共用同一上下文 schema/编译器，试聊支持脱敏的真实上下文快照与受控合成卡片/事实；模拟状态和记录单独隔离、零平台发送。重放采用历史模式，绝不偷看未来消息/人工答案。保留简易纯文本入口，但明确能力范围。

### F10：模型调用成本与失败回执没有完整进入 V2 trace（中）

`draft_provider.call_model` 已返回 responseId、usage、估计成本和起止时间，异常也附 receipt；`generate:309–324` 仅提取 content/错误码，decision 表没有对应调用回执字段（`schema_migrations.py:1010–1032`），CLI trace 只展示输入/decision 与 serviceReplyId。应保留可用模型回执，不重复实现一套计费逻辑；缺 usage 显示未知，不能当 0。

另外两条 reply transport 的 ready 异常取消策略不同（`reply_transport.py:77–88` 与 `market_agent_reply.py:57–66`），最终 permit 主要核对 replyWindow，实际二发窗口缓冲检查在 worker 开始处。抽公共门禁时应重新检查两种窗口与最新控制，并对“尚未提交可取消”和“可能已提交只核验”做同合同测试；不能仅改模块名视为合并完成。

## 4. 推荐的新执行流程

```text
持续收信落账（参考旧版可靠接收机制）
  → 原待回复事项合并，保存最早未处理时间
  → 到独立回复窗口，领取一位可处理达人
  → 读取生产快照：未答问题＋必要对话＋材料/状态证据
  → 单次 DeepSeek：reply / no_reply / request_detail / handoff ＋正文
  → 校验结构、事实引用与最新消息/控制水位
  → no_reply：只结算覆盖范围；仍需等待资料的保留等待
  → handoff：原子保存商业案件、锁和唯一确认消息意图
  → reply/request_detail：保存唯一冻结正文和 requestRef
  → 发送前再复检 → 单次提交 → 精确回读
  → 确认后只推进已覆盖范围，继续下一位；异常走独立恢复
```

### 4.1 不增加平行状态源

继续使用 inbound_turn、inbox_pending、service_cursor、relationship、service_case、agent_reply_decision_v2、service_reply。以下是需表达的逻辑字段，不要求每项新建一张表：

| 对象 | 最小补充 |
| --- | --- |
| 待处理事项 | 最早未处理时间、当前入站范围/水位、现有 revision、到期/退避、必要 owner/lease/fence |
| 决策输入快照 | live/replay、context schema/version、快照截止时刻、消息覆盖范围、必要事实引用、历史裁剪范围、指南/连接版本 |
| 调用回执 | 原 provider receipt、尝试号、错误类、起止/usage/成本；与唯一 input_hash/decision 关联 |
| 执行关联 | decision → 唯一 service_reply；handoff 的 case/锁/确认消息原子关联；冻结覆盖范围 |

保留旧消息/意图 ID、当前未知和人工案件，迁移只增量且幂等。旧记录无法恢复处理范围或成本时标 legacy/unknown，不凭猜测回填。新旧 worker 混用新字段前要有兼容策略和明确切换时点。

### 4.2 业务记忆应来自事实

例如“这个商品已经提醒加橱窗”“已经向达人索取过联系方式”“目前等对方补充什么”，应从已确认发送、决策关联与等待状态提取，带证据 ID。未提交草稿和未知回复不能记成已经提醒过。可以持久化可重建的投影，但不让模型生成的摘要覆盖原消息或永久状态；不能以新投影绕过当前唯一台账。

### 4.3 模型与代码的分工

- 模型：理解多诉求、衔接上下文、按既有政策选 route、用市场语言组织自然回复。
- 代码：市场/身份、当前材料与数字事实、授权/窗口、处理范围与去重、人工控制、冻结意图、回执匹配、重试预算。
- 离线评测：验证语义与业务边界。不添加第二个在线模型分类/审批，不将模型自报 confidence 作为自动放行依据。

## 5. Jev 退出清单（用户明确要求）

**现状：正式 V2 已只使用 DeepSeek，Jev 是旧五动作影子路径的残留。** `agent_reply_v2` / worker 没有调用 Jev；不能把删 Jev 说成当前生产每条回复节省一次模型调用。

实施时移除或退役：

- `scripts/lib/typesafe_provider.py` 的可执行网络 adapter 与 `config/typesafe.example.json` 新配置入口；不读取或擅自删除本机私密 typesafe 配置/密钥。
- `reply_events.py:238–270` 的 JevClassifier，batch_classify 的 Jev provider 分支、status 中对 typesafe readiness 的依赖，以及新的双模型比较入口。
- 相应 Jev 调用测试、启用说明和“必须有 challenger 才能验收”的要求。替换为无 Jev 配置/依赖时生产、试聊、重放、状态和评测均正常的验证。

必须保留：

- `reply_events.backfill` 的真实 episode/turn 投影、必要 `load_policy` 兼容；收信、V2 worker、模板等仍调用它们，不能整文件删除。先将历史分类与当前消息投影职责分离。
- 历史 Jev 决策行、人工真值、审计报告与旧模型名称。它们是历史事实，可只读展示，不需要加载 Jev SDK/provider，更不允许历史分类授权当前发送。
- 旧评测报告标记为历史，不改写当年的准确率，不在新方案继续推荐 Jev。

代码扫描“Jev 零字符串”不是验收；正确标准是 **零可执行 Jev 请求路径、零启动/状态依赖，历史仍可追溯**。

## 6. 建议实施顺序

## 7. 验收重点

1. **既有场景不回退：** 固定报价/真实联系方式/卡异常按原规则交接；样品、物流、售后、结算按已确认含义回答；纯感谢不误当合作承诺；真实卡前提及同 PID 提醒去重；四市场固定语言。
2. **消息边界：** 两条问题＋最后一句感谢仍处理前两条；生成/发送/确认间新增入站不被清掉；人工已答旧问题不再答；配套邀请文字不吞待回复。
3. **上下文：** 关键提醒在第 25 条以前仍可追溯；已等待联系方式、对方只说谢谢保持等待；未知发送不作为已送达证据；live 看见已发生的新配套文字，replay 不看未来；必需上下文过长不循环调用同一无效输入。
4. **原子与恢复：** handoff 锁/case/意图各中断点、领取后崩溃、provider 超时、ready 过期、逐写前新人工动作、窗口关闭、迟到 fence 均覆盖；同 input/原 requestRef 不重复外发。
5. **吞吐：** 用可控假模型证明第一位生成完成即可进入执行，不等待后 19 位；任务持续可运行时没有固定每条 60 秒空等。实际吞吐另量测模型耗时、认证/平台耗时与窗口容量，不把代码推导当生产速度。
6. **隔离：** 模型技术失败不创建商业人工 case；账号故障不耗尽所有人的单项预算；拟议 AI unknown 策略获准后测试一位失败不拖全市场。二发技术隔离仍需维持营销禁用，AI 服务许可另测。
7. **测试方式：** 复用相关 Python unittest 与 Web 合同测试，build 后 typecheck；网络均用替身、临时库模拟旧库迁移两次/中断恢复。语义测试使用用户已确认参考答案、四市场多轮合成与经授权脱敏的真实快照；语义复核与代码断言分开。零模型调用的合同测试不宣称模型准确率。
