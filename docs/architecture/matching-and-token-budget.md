# 一发、二发的新匹配体系与 Token 预算

设计版本 v1，2026-09-11。依据用户最新要求重新设计，**不继承旧版粗糙、未实际使用的选品/选人算法**。旧代码只帮助确认字段来源、接口语义与执行条件。

已知规模：商品约1,000–10,000个，达人后期上万。本文以10,000–50,000名达人评估，50,000为压力假设。真实日触达数、模型与费用上限未确定。以下参数均可调整，不是已启用的商业策略。

## 1. 结论与业务对象

采用“结构化事实 → 多路有界召回 → 稀疏候选 → 关系级决策与话术 → 执行证据反馈”。大量商品与达人进入可查询索引，模型只接收本次需要处理的一个关系和少量商品方案。

一发以发现新的适配合作为主；二发利用已知同款带货/合作证据寻找新的有效合作机会。它们是候选来源，不能用来判断这是第几条消息。新需求、再次营销、未完成服务分别管理，最终由同一个关系负责人协调。

商品与条件拆开：`Product` 表达市场内的精确 PID；`Offer` 表达某活动的条件；`CommissionQuote` 表达可给达人及机构保留的佣金；`CardBinding` 表达某账号能发送的具体商品卡。匹配商品不等于已经拥有可发卡片。

**真正优化的结果**是有效合作与机构贡献，同时控制人工负担、拒联和费用。单纯追求发送数、相似度或高佣金都会偏离目标。

## 2. 最小可落地架构

首版一个应用、一个独立业务数据库、一组有限 Worker 即可。优先普通索引；语义召回作为可插拔能力，证明价值后再启用。正式数据层建议独立 PostgreSQL，可按需使用 pgvector；不预设需要独立向量数据库、Kafka、图数据库或常驻多 Agent。

现有 SQLite 本地切片继续验证接管、幂等与未知结果。它的全量快照、关系内聚合 JSON、单关系一个示例商品不适合直接承载正式匹配，必须先改成可分页的规范化查询和多事项关系模型。正式数据库/框架选择仍按试验决定，未迁移旧数据库。

```text
商品/Offer更新 ─┐                    ┌─ 精确PID既有带货关系（二发）
达人/行为更新 ──┼→ 标准事实与索引 ────┼─ 类目/价格带/内容形式（一发）
明确需求/回复 ──┘                    └─ 语义/冷启动补充召回
                                              ↓
                                 去重、轻量排序、保留候选证据
                                              ↓
                         关系协调：已有事项、承诺、控制、联系计划
                                              ↓
                         费用预留 → 单次关系决策 + 个性化话术
                                              ↓
                         当前方案/卡片/账号核对 → 执行 → 反馈
```

## 3. 哪些数据值得存，哪些不应发给模型

| 对象 | 匹配工作集 | 原始信息与缺口 |
| --- | --- | --- |
| 商品 | 多级类目、用途/人群、价格带、内容表现形式、关键差异、季节性 | 精确PID、来源、描述/图片留库；不能凭标题猜特殊功效 |
| Offer | 市场/币种、活动、有效期、库存、样品可申请性、佣金方案、准备状态 | 商业条件独立版本；缺库存/额度不补0，未知不冒充可用 |
| 达人 | 多类目分布、常见价格带、视频/直播形式、可核实表现、实际偏好 | GMV必须有窗口/币种；样品表现要明确分母与周期；不只取第一个类目 |
| 已有关系 | 精确PID表现、来源窗口、原始消息引用、未完事项、已交付记录 | “本窗口未观察到”不等于从未带货；旧销售不等于现在仍持有实物 |
| 当前需求 | 商品指代、明确诉求、合作限制、下一步、来源消息 | 有需要时回查原文；模型推断与达人陈述分开 |

旧代码真实字段与缺口见[数据输入调查](../research/matching-data-inputs-20260911.md)。先使用可靠且成本低的结构字段，再补增量语义。图片/视频理解不是全量建档前提，只对文字信息不足且有潜在价值的少量对象启用。

每条特征保存 `entity_ref / source_ref / observed_at / window / currency / status / extractor_version`。明确 `known / missing / stale / conflict`。不把缺数据的达人默认当低价值，也不让模型补出不存在的 GMV、履约率或合作意愿。

## 4. 首次建档与增量更新

### 首次

1. 规范化商品/PID、市场身份、Offer、类目和金额；先去重，不调用模型。
2. 从可靠结构字段建立倒排索引、价格带和行为分布，不调用模型。
3. 对仍有价值但难以归纳的描述/内容，批量提取一次受限语义特征。不是所有对象都必须走此步骤。
4. 可选：为商品语义与达人兴趣摘要建立向量。向量表示兴趣/用途，不能决定商业资格。
5. 用人工评审样本比较结构召回与增加向量后的改善，达不到收益则保持结构方案。

### 日常

把版本分成三类：

- **语义版本**：标题、用途、内容主题改变，才需要重提取或重建向量。
- **商业版本**：佣金、价格、库存、活动期限变化，只重算相关候选、报价和发送资格；不重写达人画像或向量。
- **关系版本**：新回复、接管、拒联、合作结果改变，更新该关系和相关事项；不重排全库。

以标准化内容 hash + 提取器/模型版本缓存；一次提取供多个匹配和话术任务复用。相同源数据重复同步不产生新的模型任务。脏对象进入去重队列，同一轮多个变化合并。

增量处理既要使旧候选失效，也要召回**刚变得合适的新候选**。例如以前不在价格带的商品降价，不能只更新它已有的候选边。

## 5. 一发：双向召回与少量语义决策

### 从商品找达人

按市场与可核实业务身份确定搜索范围，结合多类目、价格带、内容形式/受众需求和已有商品表现召回。具体产品尚缺某项准备，不必从发现库存消失；候选中标明准备缺口。

### 从达人找商品

达人主动回复、出现明确需求、近期内容变化或进入一次可联系机会时，以这个达人为查询取少量商品。这能避免每天把所有商品再遍历一遍去“寻找这个人”。

### 候选规模

每路先返回有限候选，再合并去重。可从每商品/达人50–200个候选作为离线实验起点，轻量排序后每个关系留5–10个有依据的方案，最终决策时只提供3–5个。它们是待验证的工程参数，不是商业硬规则。

召回质量按不同市场、类目和冷启动组检查，不能只看热门达人总命中率。探索候选与高确定性候选分别标注来源，比例由测试和容量设置，避免长尾永远得不到机会。

### 排序目标

先检查明确需求与事实冲突，再比较内容/价格/形式适配、方案价值、近期关系进展与服务负担。机构预期贡献可以概念化为：

`有效合作概率 × 可归属成交价值 × 机构保留佣金 − 本机构实际承担的样品/服务/模型成本`

冷启动阶段没有可靠概率时用可解释的排序和理由，不伪造精确成功率。权重由样本比较校准，不把“类目40%＋佣金30%”一类随意数字写成最终算法。无回复不自动当作负样本。

## 6. 二发：经营已有商品关系

维护精确 `market + creator_ref + pid` 的关系边，附来源、销量/合作事件、窗口与覆盖范围。查询某 PID 时直接读取已有边；不要把这些组合再次当作一发逐对调用模型判断是否“相似”。

重评的有效触发包括：新的商品表现、当前可提供条件变化、卡片失效/重新准备、明确需求、合作周期变化。已有实物但链接不可用属于服务工作；缺实物时先核实诉求，不机械重复寄样。

“我方能提供X%”与“比你现在更高”是不同结论。后者必须有可比较的达人实际条件；公开佣金不能替代其实际所得。机构总佣金也不能直接写进对达人的承诺。

候选去重、同关系协调、具体行动幂等分开。旧合作结果保留；新的主动需求可进入新事项，主动再次营销的频次/新方案条件仍需设定。尚未确定的规则不由模型临时决定。

## 7. 把模型调用合并到关系这一层

默认不做“每对候选先由一个模型打分，再由另一个模型重读生成话术”。先用结构排序筛小；关系 Agent 在一次判断中选择当前最合适的少量方案，并组织个性化表达、必要澄清或等待。

| 工作 | 默认实现 | 何时才用模型 |
| --- | --- | --- |
| 身份、币种、价格、佣金计算、去重与资格 | 程序和当前事实 | 不交模型判定 |
| 类目/价格/渠道召回、精确PID关系检索 | 普通数据库索引，按需向量 | 不逐对调模型 |
| 内容主题/明确需求提取 | 已有结构字段优先，语义结果缓存 | 新文本的必要缺口一次提取 |
| 最终选方案与话术 | 一个关系 Agent，受限候选和上下文 | 准备真正处理该关系时调用 |
| 专家调查 | 有界按需任务 | 只有缺口影响结果且有剩余预算 |
| 质量评估 | 规则检查＋抽样评审 | 难例离线判断，不默认每条再跑一轮模型 |

同一达人跨多个商品/目标先合并计划，避免多次模型重复读取同一画像，也避免多条互相冲突的邀约。关系 Agent 是可复用定义，不是为每位达人常驻一个进程。

## 8. 上下文和预算合同

常见一次匹配＋首轮话术的输入预算可从1,200 token起测，例如稳定指令/输出合同300、达人摘要180、当前事实与关系220、5个候选各100。计费输出从200 token起测。具体模型、语言及复杂事件必须用实际usage校准；这些不是长度保证。

关键规则：

- 原始全画像、全部商品、全量对话不进入每轮提示；只放当前必要事实和可回查引用。
- 长对话保留当前诉求、未兑现承诺、拒联、控制与相关原文。不能为了省token丢掉实际义务。
- 写话术尽量靠近执行时刻；大候选库存先保留特征和匹配理由，避免提前生成大量后来作废的文案。
- 冻结 `relationship/inbox/policy/offer/context` 版本和请求ID；重入复用同一结果，业务变化后重算需计入重工费用。
- 计费输出包括所选供应商计费的隐藏推理部分，不能只数看得见的文案。普通复杂度选择短判断预算，疑难升级单独限额。
- Prompt缓存与Batch折扣作为额外收益；基础测算不依赖缓存命中，不把向量token算作免费。
- 预算按“已有服务、主动获客、资料更新、评估”分别预留。已进入服务的达人不应被新获客占满资源。
- 调度前按最大允许成本预留，收到实际usage后结算；重试、超时、作废输出也记成本。预算不足延后新获客/低优先研究，不能偷偷换低质量承诺或盲目压缩。

严格预算包含 token、金额、请求速率和人工负载；费用额度不是触达人数固定硬上限。

## 9. 可复算的量级测算

以下只计算匹配与首轮话术，**不含后续多轮咨询、第三方采集、图片/视频模型、主机或人工费用**。每日决策轮次是假设，指进入模型的匹配与首轮文案判断（也可能决定不发），不代表实际消息数或平台允许发送量。

共同假设：日商品语义变化2%，达人语义变化1%；变化对象中10%需模型提取，每次600输入＋100输出；关系决策1,200输入＋200计费输出；额外重工10%。可选向量按商品120、达人180 token计，独立记账。

| 商品/达人 | 日匹配决策轮次假设 | 日LLM token | 日向量token | 日费用示例 | 首次建档费用示例 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1,000 / 10,000 | 500 | 778,400 | 20,400 | $1.22 | $1.31 |
| 5,000 / 20,000 | 2,000 | 3,101,000 | 48,000 | $4.88 | $2.96 |
| 10,000 / 50,000（压力假设） | 5,000 | 7,749,000 | 114,000 | $12.18 | $7.11 |

**费用使用占位单价：输入$1/百万、输出$5/百万、向量$0.05/百万。不是任何模型的当前报价或承诺。** 首次建档假设10%的实体需要模型语义提取、全体建一次向量；没有重复计入每日费用。关闭向量则不发生向量成本。

如果不调用额外语义提取且不生成新话术，存量数据即使很多，也不应自行消耗LLM token。费用主要随实际决策数和语义变化量增长，不随商品×达人组合增长。

计算方法：

```text
E = ceil((商品数×语义变化率 + 达人数×语义变化率) × 需提取比例)
J = ceil(日匹配决策轮次 × (1 + 重工比例))
LLM输入 = E×提取输入 + J×关系决策输入
LLM输出 = E×提取输出 + J×关系决策输出
向量输入 = 变化商品×商品向量token + 变化达人×达人向量token
费用 = 输入×输入单价/百万 + 输出×输出单价/百万 + 向量输入×向量单价/百万
```

精确计算与参数见 [matching-budget.mjs](../../scripts/matching-budget.mjs)，在项目根目录运行 `node scripts/matching-budget.mjs`。算术、零工作量、固定吞吐下存量增长与预算上界已经独立检查。实际上线前记录真实token分布的P50/P95/P99，替换平均假设。

## 10. 为什么当前规模可以保持简单

10,000商品×50,000达人有5亿个理论组合，不应逐对调模型或永久落库。稀疏候选每商品保留50条时约50万条边，仍需去重和清理失效版本，而不是存5亿条。

可选384维float32向量：1,000商品＋10,000达人原始约16MiB；5,000＋20,000约37MiB；10,000＋50,000约88MiB。这只计算向量数组，不含索引、数据库、缓存、媒体和工作集，不能当作整机内存需求。当前Mac可用于小范围基准，不需要为这一步预先购买GPU服务器。

先用普通索引/全量小向量精确检索做基准，再决定是否需要ANN。向量索引不是为了“显得AI native”而强制配置。关键是查询确实先缩小范围；返回LIMIT 50不能证明后台没有扫描全库。

## 11. 实体与任务设计

| 实体/任务 | 关键字段或触发 |
| --- | --- |
| product_feature / creator_feature | entity_ref、semantic_hash、结构字段、证据状态、版本；按实体/市场索引 |
| offer / commission_quote / card_binding | 活动、账号、条件、报价规则与有效期独立；按精确标识查询 |
| creator_product_evidence | market＋creator＋PID＋来源事件/窗口，既可正向也可反向查 |
| matching_policy | 目标、来源范围、排序版本、候选K、探索与费用预算；策略不是提示词中的任意文本 |
| match_candidate | relationship＋product＋目标，合并多个召回来源；保存理由/特征版本/失效原因 |
| relation_plan | 聚合当前关系的候选与服务事项；本轮准备哪些方案、何时判断 |
| decision_run / usage_reservation | 输入版本、实际usage、重工原因、金额预留与释放 |
| feature_changed | 仅更新受影响实体；商业变化不触发语义提取 |
| candidate_inventory_low | 给缺候选的市场/类目补召回，不每天对所有对象重算 |
| creator_message_received | 先处理明确需求和未完服务，再决定是否加入新商品 |

旧底座的消息意图、控制版本、组件结果与unknown核验可以继续复用；旧固定要WhatsApp剧本、粗糙选人打分、单商品关系模型不作为目标架构。

## 12. 验证与实施顺序

1. **事实层与基准**：先把商品/Offer和多类目达人特征规范化，检查来源窗口、缺失与币种；做索引查询基准。此时不接模型也应能找出可解释候选。
2. **第一版召回**：精确PID关系、结构匹配和明确需求三路，使用可解释轻量排序；比较按商品和按达人两种触发的覆盖与成本。
3. **关系决策**：只把最终少量候选接入一个关系Agent；一轮同时选方案与写个性化话术，独立核对商业承诺。
4. **按证据加能力**：语义向量、额外精排、视觉或专家任务分别做增益/成本实验，不能一起启用后无法判断收益。
5. **低风险真实验证**：在明确范围与商业参数后检验效果，再扩大自动化。新旧系统对同一关系的执行归属必须清楚。

验收比较至少包含：正确候选覆盖、Top-K适配度、商业事实错误、重复/拒联、有效合作进展、单位有效结果token、总模型费用和人工分钟。按MX/BR/IT、冷启动/成熟达人和热门/长尾商品分层；旧回复不是天然标准答案，评估与训练按达人隔离，避免未来事实泄漏。

目前尚需用户确定的经营参数是日预算、期望触达规模、各市场商业条件和主动再次营销频次。它们不阻止搭建低成本事实/召回层，但不能由模型自行填入生产配置。
