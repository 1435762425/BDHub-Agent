# 账号调度与跨业务并行

2026-09-14，只读调查与调度设计。后续产品经理已确认每个市场两个账号，意大利ACC6＋ACC9已登记并通过双号只读核验。最新执行边界与完整设计见[双账号生命周期](dual-account-lifecycle.md)。新建货盘只读路由已迁移ACC9；写入/画像迁移、自动接管和新维护Worker尚未启用。

## 现场事实

- 新版货盘读取与全托选入都使用`global_source_transport`并固定到IT/ACC9；通信、OECID与发送继续固定ACC6。
- 新版IM收信和发送经`second_live_runtime._authenticated`，也固定IT/ACC6；`authenticate_it`当前直接拒绝其他账号。
- 两条路径都通过`probe-italy-profile.readonly_guard`取得各自Profile的排他锁，并检查旧版已有owner。使用ACC9与ACC6时可并行持锁；同账号的跨模块任务仍互斥。
- 选入的8通道和身份查询的12 QPS属于单个持有锁的任务内部并发，不表示不同任务可各自叠加请求速率。
- `poll-cycle-inbox.py`有独立循环，但同样需要账号锁；长时间货盘任务会使它等待或返回`live_guard_busy`。
- 新版当前有几个独立Worker和任务状态机，没有覆盖全部业务的统一账号分配器。`run-second-cycle.py`只会在存在发送动作时让部分货盘阶段延后，不能代表全面调度完成。
- 本轮旧配置只读核对：10个注册账号；IT候选发送账号为ACC1/6/8/9/11，各自Profile独立。配置归属不等于当前登录健康、接口可用、同机构可见或跨账号发卡已验收。不能直接宣称5个账号都能在新版发送。
- 新版发送的旧项目冲突检查是只读快照，不是跨两个系统的原子调度。旧版仍在使用的账号不能被新版直接当空闲资源。

## 并行边界

| 组合 | 当前实现 | 目标安排 |
| --- | --- | --- |
| 同账号货盘任务与IM发送 | 共用排他锁，互相等待 | 统一账号执行器协调；初版保留跨业务互斥，在安全边界切换 |
| 不同独立账号：货盘与发送 | 新版尚未完成分配与组合验收 | 同机构、同市场能力核实后可以并行；机构额度仍共享 |
| IM发送与收信 | 目前是不同Worker抢同一锁 | 由统一IM会话服务持续收信、串行提交发送写入；IT需专门验收 |
| 营销发送与AI自动回复 | 用户暂停回复 | 未来继续按业务阶段切换；账号变多不解除回复暂停 |
| 账号登录/身份维护与业务 | 维护检查已有，但跨业务协调未统一 | 该账号先排空在途写入并回查，再独占维护；其他独立账号可继续 |
| 本地统计/筛选/名称生成与平台任务 | 不需要占用平台账号会话 | 可并行，仍控制本机资源和数据库写事务 |

跨账号并行需要同时确认：Profile/设备身份独立、机构市场对应、接口能力、商品卡可见与可发、当前租约、发送身份归属。不同登录账号如果实际共用同一IM sender身份，其发送队列与节拍必须合并。新联系人500额度始终按机构×市场共享，不按账号叠加。平台机构级限流也应共享退避。

同一登录账号跨市场仍可能共用同一个Profile，不能按市场分别创建互不知情的账号锁。

## 建议的调度结构

1. **账号中心**维护账号自身身份、可用市场/机构、已验能力、当前任务、维护状态和等待原因。旧配置只读导入参考，实际调度状态保存在新项目。
2. **每个账号一个会话负责人**管理该账号的认证、HTTP通道和IM会话。验证结果在本账号会话内协调；身份更新后让旧会话失效，不复制到其他账号，不让各Worker各自重新认证并争用状态。
3. **统一任务队列**区分货盘发现、选入、建链、身份查询、发送、收信与维护。每项声明所需能力、机构市场、原账号亲和、是否已有外部写入和可释放资源的边界。
4. **账号分配先看证据，再看空闲程度**。有可用独立账号时分工并行；没有时排队。产品经理最新要求每个市场固定两个账号，同一账号在新系统中不跨市场复用；组内职责按能力与健康弹性接管。
5. **任务内部并发由账号执行器给预算**。不能让货盘任务自取8 QPS、画像自取12 QPS、IM另开一套节拍后全部叠加。具体接口类别与账号总预算需要组合实测。
6. **写入结果与任务调度分离**。已提交请求收齐并回查；未知结果保留原账号/意图，不通过换号补发。停止领取新工作不等于强杀当前请求。

## 优先级与公平性（待产品经理确认默认业务优先级）

- 先完成已提交写入的必要回查，保证拒联/回复等入站事件及时处理。
- 发送前定向核验属于发送流程，不能与后台全量货盘刷新一起降到最低优先级。
- 建议没有空闲账号时优先保障收信和发送，普通货盘扫描/刷新保存断点后让出。
- 已发商品卡后的后续文字仍须检查新回复与拒联，不把整套卡文看作必须无条件完成的不可中断事务。
- 给后台任务设置可观察的等待时长与完成目标，不能让持续“发送优先”导致货盘永远不更新。具体批次/时间片上限依据实测确定。
- 账号到期维护不能被长期busy无限延期。已有任务在安全边界排空后进入维护，不把维护误当成普通低优先级货盘任务。

## 身份维护最新周期

新版已确认无感身份更新48小时、登录维护72小时；取消5分钟巡检、6小时深检和提前2小时维护。按各账号成功时间安排到期任务，正常业务认证异常才按需恢复。旧服务仍按其现有规则执行，本轮未改旧服务；周期移交须同时更新任务准入和到期门禁。

## 每日03:00与7天刷新

产品经理已确认：货盘发现与刷新默认每天北京时间03:00；已查PID的达人线索默认每7天刷新。

建议03:00作为日任务进入队列的时间，实际启动由账号调度器决定。有空闲已验账号就执行；没有则显示“等待发送任务释放账号”等具体原因，不能强抢或把等待记作执行失败。日作业按市场、业务日期与任务类型去重，中断续跑，不因错过03:00丢掉当天任务。

货盘刷新、已选增量对账、链接维护仍分层，不把每日任务解释为逐项重抓全部已选商品与全部链接。商品日任务和账号身份维护是独立时钟。旧版现行身份维护允许到期全天排空处理，历史03:00–05:00维护窗口已经失效，不得与此次商品03:00计划混淆。

这是新版产品内调度设计，尚未创建或启用新的实际定时作业。

## 页面与验收

账号中心显示“当前执行、可用能力、等待/维护原因、下次分配”；任务页面显示排队原因、最近进展和断点。日常界面不要求运营人工选Cookie或分配底层锁。

实现后至少验证：同账号跨模块互斥、不同行为不会叠加超限、独立账号跨业务并行、不同登录账号同sender共享节拍、同账号跨市场锁定、收信不被长扫描饿死、维护到期排空、运行中暂停、未知不换号重做，以及03:00任务遇发送时的断点延期。当前没有恢复真实发送来做并发试验，不能称为已完成平台并发验收。
