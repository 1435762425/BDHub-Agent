# BDHub-Agent 自动运营首页与持续经营工作流开发计划 v1

状态：自动运营主链的历史执行合同，基础能力已实施。日期：2026-09-20。注：Campaign 现为每 2 天刷新（`config/operations-policy.json` 的 `campaignRefreshDays`），文中“每天 07:00”是当时口径。首个实施市场：意大利。全市场共享页面、无全托空态、market 隔离、资源并发与性能目标以[多市场统一计划](multimarket-ui-runtime-hardening-plan-v1.md)及当前项目/技术文档为准。

本文是本轮开发的执行合同，描述目标页面、业务顺序、状态机、数据迁移、API、测试和验收。它不是当前运行状态；当前事实仍以 `docs/PROJECT.md`、`docs/TECHNICAL.md`、代码和 `var/` 台账为准。

## 1. 目标与完成定义

将当前需要运营逐页操作的意大利 V1，改造成每天自动推进、只在异常与人工会话时要求处理的完整经营工作流：

```text
完整货盘更新
→ TapLink 清洗、准备与核验
→ Kalodata 整批达人线索
→ 新达人 OECID
→ 发送池
→ 持续二发
→ 收信与 Agent 集中回复
```

完成后：

- 登录默认进入“运营首页”，可以直接判断整条链路是否正常；
- 正常日无需逐步点按钮；
- 全托货盘按市场能力独立开关；
- 货盘只发布完整版本，Kalodata 按本轮完成或额度耗尽形成阶段结果；
- 二发不再以“批次/冻结”作为用户概念，而是持续消费当前发送池；
- 账号身份、HTTP 和 IM 能力作为同一身份代次一起刷新；
- 真实发送、建链、清洗和自动回复仍有持久意图、回查、去重和 unknown 语义。

## 2. 已确认的产品决定

### 2.1 首页与自动化

- 新增一级“运营首页”，作为默认入口。
- 首页以监控为主，只保留三个高频控制：
  - 自动运营总开关；
  - 全托货盘周更新开关；
  - 持续自动发送开关。
- 具体时间、账号维护、立即执行和技术信息进入“运行与设置”。
- 收信监控全天常驻，不作为串行主链的一步。

### 2.2 调度时间（北京时间）

| 时间 | 任务 | 规则 |
| --- | --- | --- |
| 每周一 04:30 | TapLink 清洗 | 整批执行、整批结束后统一回读 |
| 清洗完成后 | 全托货盘完整更新 | 市场支持且开关开启时执行；不设并发硬启动 |
| 每天 07:00 | Campaign 货盘完整更新 | 周一若货盘账号仍忙则排队 |
| 货盘发布后 | TapLink 准备 | 自动核验并创建缺失的当前标准链接 |
| TapLink 阶段完成后 | Kalodata | 整批执行，直到本轮范围完成或平台额度耗尽 |
| Kalodata 阶段结束后 | OECID | 集中处理本轮新增 handle |
| OECID 阶段结束后 | 发送池 | 统一重算并发布当前发送池 |
| 15:00–16:00 | Agent 集中回复 | 与二发严格不重叠 |
| 16:30–24:00 | 持续二发 | 自动或人工启动都必须等待窗口 |
| 每 72 小时 14:30 | 通信账号维护 | 每市场通信账号；多市场进入统一维护队列 |
| 每 72 小时 14:40 | 货盘账号维护 | 每市场货盘账号；通信账号优先 |

### 2.3 两账号固定分工

- 通信账号：收信、IM 发送、Agent 回复、OECID、达人画像。
- 货盘账号：货盘、Campaign、选入、TapLink。
- 不自动交换角色。
- Kalodata 使用独立身份，不复用两个 TikTok 账号的 Cookie、fp 或令牌。
- 多市场不要求运营手工交错维护；到期账号由全局维护队列串行处理。

### 2.4 合作状态

合作状态固定为：

1. `normal`：正常合作；
2. `collaborated`：达成过合作；
3. `paid`：付费合作；
4. `rejected`：拒绝合作。

规则：

- 默认 `normal`；
- 加橱窗事件只在状态仍为系统默认时自动升级为 `collaborated`；
- 人工设置优先，后续自动事件不得覆盖人工状态；
- `paid` 与 `rejected` 均阻止该达人所有 PID 进入发送池；
- `normal` 与 `collaborated` 继续按身份、材料、冷却和关系门禁判断。

### 2.5 TapLink unknown

`unknown` 不是验证码或账号风控的同义词。它表示创建请求可能已提交，但缺少确定回执或即时回读未找到新卡。

处理规则：

1. 单个 PID 创建 unknown 后隔离该 PID；
2. 不再次提交同一创建 POST；
3. 继续处理本轮其他 PID；
4. 整批结束后统一回读；
5. 尚未找到的 PID 再轮询两次，默认间隔 30 秒、120 秒，作为可配置技术参数；
6. 查到链接则补记成功并建立当前绑定；
7. 两次仍未找到则把该 PID 标为 `skipped_unknown`，不进入本轮下游；
8. 保留原创建意图，后续周期只读核验，不创建替代意图；
9. 只有明确验证码处理失败、登录失效、账号级拒绝或整个传输通道不可用时才暂停账号/作业。

项目已有同账号滑块求解与原请求重放链。验证成功且原请求重放为正常业务响应时继续，不记为 unknown。

历史证据：ACC9 全托 `selected` 路线曾有 28 个创建后即时回读 unknown，之后只读回查全部结算；Campaign 路线也出现过单 PID 临时 unknown。均为 `created_card_not_verified`，没有账号风控证据。

## 4. 运营首页

### 4.1 顶部控制

- 自动运营总开关：关闭后不启动新的主链阶段；收信只读监控保持独立配置。
- 全托货盘周更新：每市场独立，市场不支持时隐藏或显示“不适用”。
- 持续自动发送：开启后每天进入发送窗口自动继续；关闭后允许合作工作台人工启动。

所有开关使用 revision 和 request ID，重复请求幂等。打开自动运营不等于恢复历史任务、旧批次或 unknown 意图。

### 4.2 主链展示

按顺序展示：

```text
货盘 → TapLink → Kalodata → OECID → 发送池 → 持续二发 → Agent 回复
```

每个阶段显示：

- `未启用 / 等待上游 / 排队 / 运行中 / 已完成 / 额度耗尽 / 需人工 / 失败`；
- 今日处理数量和增量；
- 当前进度及单位；
- 上次成功；
- 下次计划；
- 当前断点；
- 停止原因；
- 平台写入数量（适用时）。

首页正常状态不铺技术日志。只有异常、结果未知、身份维护需人工、人工会话等进入“需要处理”区域。

### 4.3 数据一致性

- 页面数量必须从台账聚合，不缓存 demo 数字。
- 阶段状态必须引用相同 workflow run/generation。
- 旧成功版本继续提供当前业务数据，但首页明确显示本轮是否尚未发布。
- 不能把“进程活着”显示成“业务完成”。

## 5. 自动工作流编排

### 5.1 运行对象

一次每日/每周自动工作流建立不可变 `workflow_run`，包含市场、触发来源、计划时间、适用来源和配置 revision。每个阶段有独立 `workflow_stage_run`，保存输入 generation、断点、计数、输出 generation 和终态。

该 run 是后台审计对象，不在业务页面称为“批次”。

### 5.2 货盘发布屏障

- 全托和 Campaign 均必须完成本次完整读取、筛分和恒等式校验后，才原子切换当前 generation。
- 不允许完成一个商品就向下游发布。
- 周一适用来源＝全托＋Campaign；其他日期适用来源＝Campaign。
- 周一 Campaign 07:00 到点时若 ACC9 正在清洗或全托更新，进入队列，不并发抢账号。
- 任一适用货盘来源未形成完整新版本时，不消费该来源的半成品；其上一次完整版本保持当前。

### 5.3 TapLink 阶段

- 清洗、核验、创建为不同子阶段，共用当前绑定和持久意图。
- 货盘 generation 发布后，按合格 Offer 计算应有的标准链接集合。
- 缺链接自动创建，不再逐项人工确认。
- 创建前冻结 PID、来源、Campaign、佣金规则、命名规则和账号。
- 每项创建后保存 receipt；即时回读失败按 2.5 的 unknown 规则处理。
- 阶段结束只向下游发布拥有有效 `currentListId` 的商品。

### 5.4 Kalodata 阶段屏障

- 不按单 PID 立刻触发 OECID。
- 对本轮所有拥有当前标准链接的 PID 运行 A/B 查询。
- 终止条件为：本轮范围全部完成，或平台明确额度耗尽。
- 额度耗尽时保存 PID/页/详情断点。
- 只有内部读取完整的 PID 才进入本轮发布；正在读取的 PID 保留断点，不发布部分结果。
- 阶段终止后一次发布本轮完成的线索 generation，再启动 OECID。

### 5.5 OECID 与发送池

- 从本轮线索 generation 中提取新增、尚未判定的去重 handle。
- 复用既有 resolved/unresolved 终态；只提交真正未知或技术 blocked 的 handle。
- 收信监控优先，OECID 使用短 cohort 并在 cohort 间释放 ACC6。
- OECID 阶段结束后统一重算发送池；resolved 进入候选，unresolved 留证，blocked 保留断点。

## 6. TapLink 清洗

### 6.1 删除资格

平台明确返回失效、已删除、被治理或活动失效即可删除，不额外要求“不是当前绑定”“没有发送历史”或“佣金版本旧”。

删除前仍保存 PID、listId、账号、平台失效证据和清洗 run，以便审计；历史发送记录和旧绑定事件不删除。

### 6.2 执行与回读

1. 周一 04:30 固定范围扫描；
2. 对平台明确失效的链接建立删除意图；
3. 顺序/受控并发执行删除；
4. 单项超时保存 unknown，不重复删除；
5. 全部删除请求收口后重新读取完整平台链接列表；
6. 已消失＝verified；仍存在＝failed_known/needs_review；读取不确定＝unknown；
7. 被删除的当前标准链接失效后，后续 TapLink 准备为仍合格商品重新创建。

## 7. 持续二发，移除用户可见批次/冻结

### 7.1 用户模型

发送页不再出现“冻结批次”“正式成员”“候补”或每批授权。

用户只看到：

- 当前发送规则；
- 发送窗口；
- 自动发送开关；
- “发送”与“停止”按钮；
- 当前发送进程。

人工点击“发送”与自动触发都必须遵守 16:30–24:00 窗口；窗口外进入 `waiting_window`，不绕过 Agent 时间。

### 7.2 后台执行保障

用户不再操作冻结，但后台仍必须在领取单条发送前保存不可变执行快照：creator/OECID、PID、Offer、`currentListId`、模板 revision、最终正文、控制 revision 和去重键。

持续执行器：

- 按发送池当前顺序领取；
- 每位达人同一时刻只有一个发送位置；
- 达到滚动 24 小时本地额度后等待下一日窗口；
- 每日自动继续，直到自动发送关闭；
- 明确单达人限制只跳过达人；
- 结果 unknown 只核验原 delivery；
- 账号级拒绝、身份失效或共享写门禁异常暂停持续发送；
- 历史 `cycle_bulk*`、freeze 与 candidate 表只读保留，不作为新执行授权。

### 7.3 当前进程卡

展示：

- `关闭 / 等待窗口 / 发送中 / 当日额度用尽 / 暂停 / 待核验`；
- 今日确认触达 / 当日额度；
- 当前速度与最近 5 分钟速度（达人/分钟）；
- 当前发送池剩余；
- 成功、明确失败、unknown；
- 当前达人/PID；
- 最近停止原因和最后证据时间。

## 12. 账号身份代次与维护

每账号只有一个身份负责人。一次成功刷新/重登生成新的 `identity_generation`，原子包含：

- 浏览器 Cookie/Profile 指纹引用；
- HTTP Header、Cookie、fp 的版本引用；
- IM token/session 的版本引用；
- 机构、市场、账号一致性；
- 各能力验证结果。

维护流程：

```text
停止领取新任务
→ 收齐在途请求
→ 无感刷新
→ 失败时自动重登
→ 重新生成 HTTP 与 IM 身份
→ 验证能力
→ 原子发布新 generation
→ 常驻收信重连
→ 恢复任务
```

失败不能覆盖最后有效 generation。验证码使用现有同账号求解与重放；无法通过时进入人工处理。维护期间允许短暂收信空窗，恢复后从 checkpoint 补捞。
