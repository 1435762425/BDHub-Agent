# 大规模选品选人：独立架构评审

> 本文是独立反证评审，token情景采用较保守的独立假设。主方案与统一预算参数以 [matching-and-token-budget](../architecture/matching-and-token-budget.md) 和对应计算工具为准；不把两组假设混称为实测。

日期：2026-09-11。性质：供正式蓝图使用的技术建议，不是已选商业规则、已完成压测或模型效果结论。本轮不调用模型、不读取私密会话、不修改旧系统。

## 结论

新设计应当把“全库发现机会”与“经营一个当前值得联系的关系”分开。前者主要是索引、增量事件和数值排序，后者才调用关系 Agent。大量商品和达人不应直接变成大量模型调用；实际触达、回复与必要资料解释才是主要 token 驱动量。

一发/二发是发现来源，不能各自拥有一套独立发送队列。语义候选、精确同款证据和主动需求在关系层汇合，再决定本次是否值得联系、带哪几个可核实方案。新增商品不能让一个达人收到多套互不知情的消息。

旧版源码仅支持对身份、商品/Offer、平台数据覆盖、发送意图与未知结果等事实的理解。旧匹配逻辑、样品筛选、佣差门槛、两个月期限、固定候选数和每次卡片数均不作为新设计默认。既有 [PRD](../PRD.md) 中 G01–G06、F05、F07、F10–F14 是本评审的经营与执行边界；F03/F04 的具体匹配实现仍应由新蓝图覆盖。

## 1. 建议流水线

| 阶段 | 处理方式 | 主要产物 | 是否调用 LLM |
| --- | --- | --- | --- |
| 事实规范化 | 按市场、稳定达人 ID、精确 PID、Offer 分开存储；保留来源、时间、缺失和覆盖 | 结构化事实、版本、水位 | 只有无法用源字段/规则提取的必要语义才按需调用 |
| 机会发现 | 一发使用多个索引召回；二发保存已有的精确同款证据边；真实需求直接进入服务队列 | 有界候选和证据，不创建全量事项 | 默认不调用 |
| 硬条件校验 | 身份、市场、拒联、暂停、动作范围等已确认约束；业务筛选来自版本化政策 | 合格/不合格/待核实及原因 | 不调用 |
| 数值排序 | 有效需求、证据时效、货盘条件、匹配特征、预期成本等分别打分 | 候选排序、置信和缺失项 | 不调用 |
| 关系协调 | 合并同人来源，联系频次/在途/服务容量/目标资源约束；选出当前准备集 | 每关系一个可处理工作项 | 不调用 |
| 按需精查 | 临近触达才刷新高成本画像/Offer，少数模糊候选做语义比较 | 小候选集、核实证据 | 可选，默认关闭独立语义精排，先做对照实验 |
| 关系 Agent | 使用当前必要事实，选择回复/询问/交付/等待，并生成语言表达 | 带证据和版本的行动建议 | 按实际工作项调用 |
| 执行与学习 | 程序重校验、持久提交、分组件回执；结果事件更新特征和评估 | 实际事实、归因边界、待续任务 | 执行不调用；复杂评估按需 |

“程序排序”和“Agent 最终选择”各负其责：排序减少要看的数据，Agent 可在这个小集合中取舍，也可在证据不足时不发。程序仍在执行前核对最新条件，不能拿模型认可代替资格检查。

### 一发：多路召回后合并

- 商品找达人：类目/子类目与价格带索引、已观测相似商品的行为邻接、明确需求/偏好索引；内容语义向量只是可选通道。
- 达人找商品：收到需求、画像重要变化或合作结束等事件触发；同样查询有界货盘候选。
- 冷启动和探索单独保留通道，避免“没有历史销量”等同“不值得联系”。探索额度是待确认经营参数，不在代码中写成固定比例。
- 每路记录召回原因、查询版本、截断范围。跨路去重不丢证据；相似商品的成交记录不能升级成精确同 PID 的二发证据。
- 通用大类倒排桶也可能包含数十万人，必须有桶内分层、分片游标或有界扫描，不能写成“用了索引就没有全量成本”。有界召回会损失覆盖，须测量并探索被截断区域。

### 二发：证据边的增量供应

保存 `market + source_creator_id/OEC + exact_pid + observation_window + source + observed_at + coverage`。同一证据更新或重复导入只推进水位，不反复生成机会。已有销量说明发生过相关带货，不能推出当前仍有实物、喜欢该商品或正在用某佣金。

商品查询调度以“每单位查询资源带来的新增、合格、未重复达人”观察边际收益。高重复商品减少连续扫描频率，低覆盖/长尾商品有独立探索机会。该观察是调度特征，不保证因果收益；平台只返回头部时，必须显示来源覆盖限制。

先发现再准备和先准备再发现可以共存：已就绪方案优先进入可触达库存；未准备方案保留研究机会，并在有限准备预算内推进。准备动作是否授权、真正能承诺什么仍由具体业务政策决定。

## 2. 复杂度与容量边界

使用者补充的经营规模是商品上千至上万、达人后期上万。主方案因此收敛到单个 PostgreSQL、结构化/全文索引、少量 Worker 和有界候选缓存；可选 pgvector 必须有召回收益证据后再加入。现有本地 SQLite 底座可以用于小闭环验证，此处不是立即迁库指令。50,000 达人仅作压力假设，不能写成实际存量。

| 场景 | 商品 P | 达人 C | 两两组合 P×C |
| --- | ---: | ---: | ---: |
| 范围下端 | 1,000 | 10,000 | 10,000,000 |
| 商品增长 | 10,000 | 10,000 | 100,000,000 |
| 压力假设 | 10,000 | 50,000 | 500,000,000 |

即便每对仅消耗 500 tokens，两两 LLM 匹配也分别需要 50 亿、500 亿、2,500 亿 tokens，而且刷新一次就重复付费。把它们批量放进超长上下文只改变打包方式，没有改变问题数量。避免全量组合已经足够，不需要为了远期百万达人预先搭分布式检索系统。

设某周期内需要召回的商品数为 `U_p`、达人数为 `U_c`，各自合并后最多保留 `k_p`、`k_c` 条候选，新增精确行为边为 `ΔE`：

`候选排序工作量 ≈ U_p×k_p + U_c×k_c + ΔE`，再加索引查询的实际扫描/ANN 成本、去重和 Top-K 成本。

这不是严格的所有索引复杂度上界。低选择性过滤、热点大桶、跨分片合并和 ANN 参数会增加成本，必须记录实际扫描条数和 p95 延迟。

例如每周期 200 个商品触发、每品 100 候选，1,000 个达人触发、每人 30 候选，共 50,000 个待数值排序候选（未含 ΔE、去重和索引扫描）。这些数字是压测输入，不应直接成为默认业务上限。

冷启动也要限速：50,000 达人各保留 30 条边会产生 150 万条边。若每边仅按 200 bytes 估算，裸数据约 300 MB，尚未包含索引/WAL/副本。这个量不要求分布式架构，但无需把每个召回候选永久写成机会；先保存原始事实、索引和短期候选缓存，只有进入准备库存、发生实际咨询或需审计时才持久化业务机会。

可选向量也不是零成本：压力假设中的 60,000 实体各存一条 768 维 float32 向量，裸向量约 176 MiB，尚未包含 ANN、元数据和进程内复制。该体量不足以证明需要独立向量数据库。先让单 PostgreSQL 中的结构化/全文/行为通道跑通，再用召回提升和实际内存决定是否启用 pgvector。不能仅凭裸向量大小直接承诺整机运行性能。

## 3. Token 与费用模型

为避免混淆，分别记“模型工作项”“模型实际请求”“工具调用”“发送组件”。一个工作项可能有多轮请求，预算统计必须覆盖所有轮次及工具结果，不只统计最后生成的消息。

定义：

- `X`：本周期必须抽取语义且内容确实变化的实体数。
- `A`：本周期进入准备/表达阶段的关系工作项数，不能用全库达人数量代替。
- `f`：需要额外语义精排的比例，`0≤f≤1`。
- `R`：实际需要模型判断的回复/业务事件工作项数；重复事件和正常等待不算。
- `i_j、o_j`：工作项 j 跨所有请求的输入/输出 tokens，包含系统指令、必要事实、工具返回和重试。

`T_input = X×i_extract + A×f×i_rank + A×i_compose + R×i_reply`

`T_output = X×o_extract + A×f×o_rank + A×o_compose + R×o_reply`

生产中分模型 m、输入类型和请求计量：

`Cost = Σ_m[(T_uncached,m×p_input,m + T_cached,m×p_cached,m + T_output,m×p_output,m)/1,000,000] + Cost_embedding + Cost_tools`

价格作为配置输入，本文不提供或假设在线价格；没有供应商缓存命中证据时按未缓存价格估算。应用层同内容结果复用可以不调用模型，供应商 Prompt Cache 则仍是一次有成本的请求，两者不能混算。

按每日准备触达的活跃关系 `A=500/2,000/5,000` 测算。以下仍是纯说明场景：`X=1,000/日`，`f=10%`，`R=0.5×A`；各类工作项输入/输出预算分别为抽取 `500/100`、精排 `2,500/250`、表达 `1,400/180`、回复 `2,300/250`。

| 每日准备触达的关系 A | 假设需处理回复 R | 估算总 tokens/日 |
| ---: | ---: | ---: |
| 500 | 250 | 216.5 万 |
| 2,000 | 1,000 | 686 万 |
| 5,000 | 2,500 | 1,625 万 |

这里 `R=0.5×A` 只是让表格可复算的情景参数，不是预测回复率；回复也可能来自此前触达。同样，进入表达阶段不保证最终发送，`X` 不是必须每天处理固定 1,000 人。各项随真实数据改变，不含嵌入，不是模型实测、质量保证或已选日额度。使用者未提供日预算，不能把这张表折算成默认经营预算。如果多轮工具调用使输入超过该预算，计算器必须显示增加后的成本，不能隐藏在“Agent 调了一次”里。

不能承诺发送数量增加而 tokens 永不增长。可实现的目标是：成本随确实处理的关系/变化增长，而不随全库商品×达人组合增长。每条 AI 消息都有真实成本，预算用尽时应暂停新的可延后获客、保留已承诺服务的预留容量，而不是静默切换未经评测的廉价模型。

### 不应调用 LLM 的环节

稳定 ID 解析、精确 PID 匹配、去重、分页、水位、币种金额、佣金计算、授权/拒联/频次、硬资格、额度预留、调度、重试、未知结果核验路由、状态写入、计费与统计均由程序完成。模型可以解释返回事实，不能创造或替代这些事实。

无需每天为所有实体写一篇自然语言画像，也无需在初召回后对每个 pair 做语义解释。只给真正准备触达的关系生成可回溯的解释；若最终关系 Agent 已能处理小候选集，就不要额外增加独立 LLM 精排请求。

## 4. 只对变化重算

| 变化 | 必须更新 | 不应连带重算 |
| --- | --- | --- |
| 商品标题/类目/核心描述 | 内容特征、相关检索索引；必要时重做语义抽取/向量 | 全部达人自然语言画像 |
| 价格、库存、佣金、有效期 | 对应 Offer 特征、受影响机会和未提交动作；必要时新召回 | 没变化的内容向量 |
| 新带货边 | 对应 PID/达人证据、去重、相关候选 | 所有商品×达人组合 |
| 入站/人工接管/拒联 | 对应关系控制版本、待执行稿失效、最新服务判断 | 全市场内容索引 |
| 匹配策略改版 | 受策略范围影响的候选，分批生成新版本；执行前认最新资格 | 一次事务扫完全部关系 |
| 到期/信息陈旧 | 定时失效及按准备优先级刷新 | 每日全库模型回读 |

按“语义内容 hash”“数值事实版本”“关系控制版本”“规则版本”分开。只用一个 `updated_at` 会让销量微小变化触发全文模型重读；只追踪已有候选的反向引用又会漏掉因降价/新条件而首次合格的人。因此变化处理必须包括 **已有依赖失效 + 必要的新增召回**。

TTL 是针对事实类型的刷新策略，不代表超时后事实自动变成 false。队列对同实体的短期密集事件合并，处理到最新水位；授权、人工接管和发送前资格变更不等待普通批量合并窗口。

## 5. 冷启动、缺失与探索

- 区分“不满足”“没有资料”“资料过期”“来源没覆盖”。未知不当 0，不当拒绝，也不能当已合格。
- 先补会改变当前决策的少数字段。给全部上万达人刷新完整画像再开始发送，会把系统卡在数据收集阶段。
- 新商品使用已知结构化特征和相近类目分层验证；新达人使用可核验近期行为/明确需求，不靠粉丝数一个字段决定去留。
- 为未覆盖类目、价格带和长尾候选保留可记录的探索曝光；比例、单次风险和停止条件由经营策略确认。
- 墨西哥历史是语言/场景/行为的证据来源，不能直接当巴西、意大利的概率标签或现行商业规则。
- 没回复不自动当“不匹配”：可能未送达、未看见或窗口尚未结束。未出单也可能因为没有归因能力。训练标签应先区分观察条件和业务结果。

## 6. 上线前应看到的指标

| 类别 | 指标与分母 |
| --- | --- |
| 发现质量 | 在人工核实的小规模候选基准中的 Recall@K；另对未召回区域做分层抽样。不能声称已测全库真实召回率 |
| 排序质量 | Precision@K、NDCG 或每准备名额的有效机会；按市场/类目/冷启动分层，建议分数不称成交概率 |
| 事实错误 | 身份/PID/Offer 绑定错误率，过期事实率，缺失误判率；分母为实际核验对象/行动 |
| 运营错误 | 重复主动联系、违背拒联、人工接管后外发、未经许可条件承诺；分母为唯一关系与行动，两者分别报告 |
| 执行质量 | 真实接收、unknown 比例及年龄、部分成功；接收不等于采用或成交 |
| 经营效果 | 新增唯一合格达人、有效回复、方案采用、可证实合作进展/人工分钟与全部成本 |
| 资源 | 每新增有效关系的工具请求/tokens/费用，候选扫描 p95、刷新延迟、内存/磁盘、待办年龄 |

初期对“结构化/行为召回+规则排序”与“额外语义精排”做同等触达容量/资源的对照，保留随机探索和曝光概率。历史回放按关系分组并按时间划分，只提供当时可见事实；相同消息或同一达人泄漏到训练和留出集会虚增效果。不同商品泛化另加商品族隔离评测，不能只在同款变体之间测试。

“抽查没有错”不等于错误率为 0。例如独立抽样 300 个对象未发现错误，粗略 95% 上界仍约 1%；多条消息来自同一达人时不是 300 个独立样本。不可接受的执行错误由程序约束与对抗测试保障，再以运行观测补证。具体质量阈值、评测样本量和获客/回复资源分配保持待定，不替用户选择。

## 7. Agent 数量的判断

建议保持一个关系负责人，按工作项加载，而不是给上万达人启动上万常驻 Agent。批量采集、召回、排序、成本统计和任务队列是服务或 Worker，不需要人格化成多个互相对话的 Agent。

只有独立且有实际收益的任务才委派专家，例如一次复杂的商品内容解析或含多个不确定条件的独立研究。委派需要输入范围、版本、token/工具预算、返回结构、超时和完成证据；专家不能另行发送。并行专家产生的重复上下文和汇总调用也计入账单。没有离线效果提升证据时，不增加“选品 Agent→选人 Agent→匹配 Agent→审核 Agent”固定接力。

## 8. 最容易让方案不可落地的三个风险

1. **数据覆盖和身份质量被误当成已解决。** 即使排序成本很低，只有头部数据、错误 OEC/PID 或过期 Offer 仍会导致错误推荐；LLM 不能补出从未获取的真实事实。先测源覆盖、精确绑定、缺失分布与刷新成本。
2. **候选量和成本被有界接口掩盖。** 一次只返回 30 条不代表底层没扫全部达人；候选反复落库且不过期也会膨胀；首次初始化、策略改版和热点商品都会造成洪峰。先压测单 PostgreSQL 的查询、写入和失效链路，再按瓶颈扩容，不为假设中的百万规模预支架构复杂度。
3. **优化了发送或回复数量，却没有增加有效合作。** 若没有独立执行归属、可靠结果标签、容量反馈与探索对照，高速模型会更快耗尽联系机会、运营时间和预算。把“准备→接收→有效回复→合作进展”分开测，并保留不发送、等待和缺证据三种正常结果。
