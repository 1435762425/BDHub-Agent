# 指定数量任务卡与本地准备协调

2026-09-14。承接 B.17，新增可保存的任务创建流程。**完成的是任务确认、独立台账和本地准备检查，不是完整自动采集、建链与发送执行器。**

## 已交付

- 合作工作台以二发任务为入口；表单填写整数目标、开始日期、北京时间起止窗口、全部合格货盘或限定 PID/类目/活动。数量和时段没有代填的真实任务默认值。
- 任务卡展示 N、ceil(N×10%) 候补、总准备量、范围、窗口及既定规则。服务端保存标准化卡片和策略，确认引用其哈希；确认请求重试不重复建任务，规则改变须重新核对卡片。
- `batch-tasks.sqlite` 独立保存任务、策略快照、准备成员、检查进度及事件；确认与准备工作记录同一事务落库。进程重启可继续读取准备工作。
- 本地 Worker 对全部目标＋候补做一次候选整理，再周期检查已有来源/材料变化。其工作不受每日 500 新联系数量限制，也不修改旧计划的 capacity。默认同范围按优先级/创建时间处理，单次读取结束后可处理下一任务。
- 同市场稳定 OEC 去重；保留同 PID Kalodata 证据。按具体来源排除已消费线索，未知/在途及部分投递未完成的达人不再分配。拒联、人工接管、咨询、原有频次及身份冲突继续排除。
- 全托已证实商品不要求库存数；普通商品继续原门槛。严格保留商品范围，缺类目字段不会假定在指定类目中。
- 短名和卡片记录从当前商品方案读取。历史卡片为“已定位”，`checks.taplink=false`，不会冒充本任务核验。任务仍保持 preparing，并显示具体待接入步骤。
- 暂停/继续/调整优先级带版本检查；读取期间用户暂停时，旧检查不能回写覆盖暂停。检查结果不变不重复改成员或追加事件。
- API 仅本机同源，固定命令、固定数据库/脚本路径。确认/继续后唤起单实例本地检查 Worker；不启动回复或发送 Worker。
- 修正旧试验批次 local_capacity_reached 被页面默认渲染成“正在逐项发送”的文案；明确它仍是本地保护，不能当平台原生上限信号。

## 执行权限与运行

当前任务卡 `policy.authorizationScope=local_preparation_only`；本次确认只启动本地检查，不是未来外部发送、选入或建链的批准。后续外部执行器必须核对任务明确的权限范围，不能因为有 `task_confirmed` 事件就发送。历史试验发送权限不从此继承。

AI 回复仍为手动暂停；本任务模块不写 service_reply_config。旧 BDHub 的数据、身份、配置与服务没有改动。

本地入口：`scripts/batch-task-control.py`，JSON stdin，支持 list / preview / confirm / detail / pause / resume / priority。Web `/api/batch-tasks` 使用它。准备检查入口：`scripts/batch-preparation-worker.py`；由任务确认/继续时启动，flock 保证单实例，状态暴露心跳。尚未安装开机启动服务；Worker 异常退出后可从任务“暂停→继续”恢复，持久工作不会丢失。

全部新数据库位于新项目 `var`，不进入 Git。真实任务确认不会写旧 cycle 台账；读取的是新项目自己的 cycle 和 identity 数据库。
