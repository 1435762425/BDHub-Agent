# 意大利 OECID 全量判定与吞吐收敛

实施日期：2026-09-20。范围仅为 ACC6 的达人 Find 只读链与本机身份/发送池投影；没有发送 TikTok IM、创建商品卡、修改旧 BDHub、开启自动回复或恢复其他 worker。

## 结果

- 初始：2,038 位去重达人，1,296 已就位、14 搜索不到、728 待补。
- 最终：1,465 已就位、573 搜索不到、0 待补、0 blocked、0 unknown；四项与 2,038 恒等。
- 可达达人×商品位置从 3,281 增至 3,491；发送池 ready 从 1,222 增至 1,391，sent 保持 495。
- 当前配置为每轮最多 50 位，单账号共享 12 QPS / 9 lanes；已发布验收 ID 保持 `accept-ef6d3f880d256fe68deaab01818d`。

## 为什么 728 不能直接全部重查

728 中有 498 位已经存在同 handle 的历史终态：1 位已有精确 OECID、497 位已有明确搜索不到。旧投影没有把这些终态复用到新一轮 source edge，而 `--skip-judged` 又会正确阻止重复 Find，于是页面长期显示待补并在队列中空转。

`IdentityBridge` 现在按 handle 本地复用终态：resolved 必须只有一个稳定身份并持有原始不可变发现证据；unresolved 必须来自明确精确 miss。复用只写当前本机 source edge 的结果，不伪造第二份发现回执。执行一次本地对账后，待补从 728 降到真正需要平台读取的 230。

## 吞吐与验证链

连续两个真实 cohort 共处理 82 位：69 位已就位、13 位搜索不到，总耗时 160.8 秒，约 30.6 位/分钟。两轮均为 12 QPS、9 lanes，请求 82/82 返回明确结果，平台写入 0。该样本没有触发验证码；此前 ACC6 已有一次真实证据确认滑块求解成功、共享验证后的 Cookie/fp，并由各 lane 重放自己的原 Find 请求，重放为 HTTP 200/code0且无验证头。

为稳定保持该速度，正式驱动做了三项收敛：

1. 每轮支持 50 位，但不提高 12 QPS，也不增加账号；
2. 从当前 `lead_query_head` 与未结 outbox 的交集生成精确 batch 白名单，多个小 batch 可合并成最多 50 位，不读取历史范围；
3. 精确身份轮不再先跑一个无关画像刷新，回填也只处理本轮白名单 outbox，减少固定启动与本地对账开销。

最后 6 位曾因同批兄弟先失败、本人没有请求也累加 attempt 而被提前封顶。现在 cohort 中未请求的兄弟项回队不再消耗真实尝试次数；将这 6 位的计数纠正到实际 1 次后，4 位已就位、2 位搜索不到，队列归零。

## 可恢复性

- 运行前状态备份：`var/backups/state/20260920T100116Z-before-identity-50`，21 个数据库、校验通过、凭据 0。
- 全部运行使用持久 cohort、逐目标证据、`--skip-judged`、账号 guard、严格共享 pacer 和原请求重放。
- 技术失败仍保留 blocked，不会冒充搜索不到；明确 miss 不会自动重查。
