# 1000 人任务停在 101 候选的修复

2026-09-14；任务仍为 `batch-19e1044b23d017f1f553a2ecac0d`，未新建替代任务。

## 原因与证据

1. 采集并未停止，但原 PID 排序优先查到旧试验已经覆盖的商品。排查时，任务已解析的 130 位去重达人中，103 位有已确认发送记录、处于原有冷却约束；23 位原本就在候选池，另外为咨询或拒联。增加这些重复线索不会增加候选人数。
2. 准备调度把每个 awaiting_identity PID 继续按 10 位候选估算。97 个等待 PID 被算成约 970 人潜在供给，实际尚未解析的去重 handle 远少于此，导致采集过早减速。
3. 身份队列按旧批次时间排序，重复的已知 handle 和过去未找到的 handle 占用了查询时间；真正从未查询过的新 handle 在后面等待。

## 修复

- 只有还未采集的 PID 使用每 PID 10 人的规划估计；已采到的等待身份记录按实际去重 handle 计数。已解析、终态未匹配、已在稳定库中的 handle 不再重复贡献“新增候选等待量”。这只改变估计，不把这些人直接标为匹配或可发。
- 同一任务和既定商品范围内，优先采集旧供给队列尚未查询过的 PID；保留每 PID 分页、原始回执及身份依据。
- 对 Kalodata 身份任务，优先从未查询过的 handle，其次历史查询未匹配者，最后已知身份。全部仍需精确 Find；不利用优先级修改推测 OEC，也不删除旧队列或失败证据。
- 拒联、咨询、接管、冷却、未知投递规则保持。未降低资格门槛来“补足”计数。
