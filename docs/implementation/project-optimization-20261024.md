# 自主运行、发送可靠性与页面精简

2026-10-24，开发基线 `0d53b3d`。用户确认沿用现有业务规则和持久授权：已允许的工作自动处理，无法判断和超出规则的事项交给人。本文记录本批变更和验收；当前规则见 [PROJECT](../PROJECT.md)，实现合同见 [TECHNICAL](../TECHNICAL.md)。

## 修复范围

| 问题与证据 | 改动 | 保留的边界 |
| --- | --- | --- |
| FR/TH 前夜原投递未知，发送窗口关闭后不再主动核验 | worker 与 scheduler 区分原提交核验和新发送；停止、暂停计划与窗口外仍可有限只读核验 | 原账号、意图、requestRef 和核验预算不变；未提交组件不推进，未知不重发 |
| 短暂读取网络错误让 sender 反复退出 | 四次有界退避，耗尽回到原异常状态；已提交未知必须有台账才进入核验 | 只处理明确的读取网络错误；其他错误仍暴露 |
| 页面与调度并发启动时可能重复 spawn 或覆盖 PID | 发送器与 scheduler 复用启动锁及原子 JSON 发布；watch 在锁内保留停止标记 | 显式启动才解除 scheduler 停止；停用且无原提交不启动 |
| 子进程 PID 晚于旧心跳，父进程退出后可能误释放其资源槽 | PID 与观测心跳在同一事务交接，校验 owner/fence | 旧执行者不能续租、交接或结算；仍活跃子进程保留原槽 |
| BR 身份库约 58.6 万条；概览读取约 32 秒，超过 Web 30 秒期限 | B 作者按输入小集合复用现有别名索引定位，再核对当前身份；总览与发送池共用只读查询 | 历史别名不能路由；跨市场、冲突及歧义身份排除；缺失与错误不补零 |
| 一个慢分区消耗后续概览分区的查询预算 | 各分区重新计算读取期限 | 某项读取失败不连带取消其他分区，不延长平台写入预算 |
| 一发材料缺口不变仍每 30 秒重读，旧准备轮长期占住供给 | 原 job 保存材料证据签名、缺口和次数；无可执行缺口时部分收口，相同证据有界退避 | 复用原台账与 next_attempt；保留原 unknown 核验、有效材料和业务条件 |
| 首页把最近一次 Agent 失败当作当前失败 | 当前状态复用 worker/control 时效合同，历史运行另存 lastRun | 真实失败、旧数据、缺失和 unknown 仍可见；不改草稿或重置次数 |
| 达人资料 Route 在 Web 主线程同步执行大库查询，拖住其他页面 | 固定 Node 只读 CLI 隔离查询；概览、列表、详情独立请求代次 | 复用原 Store/SQL；取消和超时终止自己的子进程，保留缺库与错误语义 |

身份列表增加按市场、最近观测时间的增量索引，由正常 `CreatorIdentityStore` 打开时幂等创建。概览优化直接使用已有索引，无需先迁移真实库。

一发状态读取复用已有的材料 partial index，并在本次请求内复用 locale；没有全局配置缓存。会话候选将逐会话重复读取回执改为本请求、原 plan 范围的批量集合；市场、OEC、CID 及消息归属保持。收信传输错误只增加异常类型诊断，不记录原异常文字、代理凭据或请求内容。

一发 `material_progress` 为原 job 的可空字段，不建立新状态源。相同材料证据按 30/60/120 秒逐步退避、上限 1 小时，证据或处理进度变化重置；`sum(gapCounts)=remaining`，actionable 只统计三类可执行缺口。有效方案、缺口项和轮次数分别计数。原任务实测收口为 10 个缺口、9 个当前有效方案、actionable=0；原未知为 0。原授权供给随后进入同一新任务和 catalog 断点继续采集，14:08 至 14:34 从 206/555 个 Campaign、225 页、4,838 件商品推进到 450/555、495 页、11,456 件商品；14:52 已完成 555/555、608 页、14,257 件商品，进入同任务的匹配准备，startedAt 和控制未变，平台写入为 0。旧完整版本的 212,830 条候选保留，新版本已扫描 40,000 人、保留 12,302 条候选并继续分片；采集完成不等于新匹配已经完整发布。

新 Agent 失败码与原运行同事务写入，只接受安全的 `.code` 或异常类名，不读取原异常文字，也不回填或改写历史执行结果。JSON 回执中的 boolean ID 不再误转为数字 1/0。

## 页面与文档

- 一发与样品：待处理申请前置，未知优先；履约等待和历史默认折叠；商品长名称收起，完整内容仍可查看；只展示当前适用动作。
- 一发货盘换代期间：用既有 `prepare_required` / `catalog_changed` 原因把匹配数量标为待更新，完整有效匹配的真实 0 保持 0；不把未就绪伪装成零匹配，也不把旧版本数量当作当前可发送数量。
- 会话：收紧筛选区域，历史筛选折叠，保留人工原因、技术挂起和计数；减少重复理由，使列表更早出现。

- README 提供当前入口与全链路概述；TECHNICAL 增加关键文件导航和恢复合同；PROJECT 写明本次确认的自主范围，纠正已统一的登录恢复状态；文档导航合并重复入口。

## 验证与限制

独立 worktree 验证：Python 全量 2,109 项、Web 全量 235 项、build、随后 typecheck 通过。测试覆盖并发启动、停止竞争、stale fence、原未知恢复、暂停/窗口边界、未提交不推进、市场隔离、歧义身份拒绝、人工/技术挂起计数与完整列表对账、匹配未就绪与真实零的区别，以及只读子进程的查询校验、错误映射、超时/取消和主线程响应性。后续纯文档变更另执行文档链接与 diff 检查。

只读真实数据检查中，BR 概览由约 32 秒降至约 11 秒，六分区均可读；原先可读的库存、身份、发送池指标一致。七市场原提交检查复用现有活跃投递索引，由约 2,075 ms 降至 2.59 ms。这些是当次本机测量，不是吞吐承诺。

一发状态读取由约 7.9 秒降至约 2.1 秒，商品、匹配、成功推送、待处理、候选及申请计数一致。巡检 `gather` 由约 11.4 秒降至约 4.5 秒，七市场的新旧会话候选集合逐一相同，返回告警通过 Web 契约校验；此结果证明读取成本降低，不能据此宣称外部收信通道已经正常。

六步真实页面审计覆盖运营首页、二发、一发、样品明细、经营总览和会话；截图及笔记保存在本机 `outputs/frontend-audit-20261024/`。回归与只读检查证据位于 `outputs/optimization-20261024/`。

达人读取隔离前的生产并发样本中，概览 13.632 秒、静态请求等待 12.703 秒、一发 HTML 等待 11.710 秒。隔离后冷启动压力样本中静态请求 0.225 秒、一发 HTML 0.035 秒，说明主线程阻塞已解除；同轮重叠读取仍有 API 超时，不把隔离描述成 SQL 本身变快。七个 SDK ready 后相同五请求的暖态并发对照全部成功：静态请求 0.041 秒、一发 HTML 0.016 秒、ops CLI 10.883 秒、ops API 10.720 秒、达人概览 12.477 秒。静态请求使用缺失 favicon 的正常 404 作为响应性心跳，其余 HTTP 为 200。14:33 正常回读时首页、一发、达人概览再次成功，但巡检出现一次 30 秒超时，后续定位及最终状态以发布核验为准，不能由暖态单次成功宣称所有负载稳定。
