# 达人线索查询队列（PID → Kalodata）

2026-09-14 用户确认查询顺序策略（今天对话第 4–6 条提问）：

> 优先查询未查过的合格 PID，按累计销量降序排列；支持手动指定商品。已查过的 PID，其达人线索默认每 7 天刷新一次。

本页记录把这条策略落成机制时的实测数据与设计决定。**本轮只算出并展示队列，执行尚未接入。**

## 为什么不轮询

平台按 `DETAIL.ACCESS_TIMES`（今日详情查看次数）计费，是硬日额度。每天全表扫一遍会把额度花在"不可能过期"的商品上。所以用**两个持久队列**，而不是轮询：

- **首次队列**：有合格链接、从未查过的 PID，按累计销量降序。
- **刷新队列**：已查过、且记录已到刷新年龄的 PID。它只会"到期"，不会被扫描。

队列范围随链接准备进度自己增长（新备好链接的商品自动满足入队条件）。**首次队列完全优先**：每天先用额度跑首次队列，用完再用剩余额度跑到期刷新。手动指定的商品可插队。

## 队列作用域：只放已有合格链接的商品

用户确认：只放 `ready` + `reuse` 两种链接状态的商品。理由是一发的逻辑就是"先备链再找达人"——没链接的商品查出来的达人也用不上，白花额度。

## 补上的缺口：`queried_at`

`source_job`、`batch_source_job`、`source_edge` **都没有查询时刻**，只有数据窗口（`window_start → window_end`）。因此原本只能判断"查没查过"，**"每 7 天刷新"无法计算**——没有时间基准算不出到期。

新增 `var/kalodata-leads.sqlite` 的 `leads_query(pid, queried_at, state, window_end, leads, note)` 作为**唯一的新状态**；执行机制复用现有 `batch_source_job`（已有租约、fence、退避、额度处理），不新建执行器。

历史回填按用户指示记为**查询当日**（今天确实在跑）。

### 回填口径的一个纠正

第一版回填把"有作业记录"当成"问过平台"，于是把 102 个 `queued`/`awaiting_identity` 作业（**从未发出请求**）也记成了"今天查过"，等于把它们错误地锁了 7 天。

正确口径：**只有 `completed` 算查过**。

- `queued` / `awaiting_identity`：从未到达平台，必须留在首次队列。
- 额度耗尽的 `blocked`：请求发出去了，但没拿到数据，**该重试**，不算查过。

修正后真正查过的是 **2,022** 个（原记 2,125，移除 103），首次队列从 216 涨到 **255**。
`sync` 的规则：只处理 `state='backfilled'`（本模块自己写的估计值），会按当前时间重新标注，并删除从未真正查询的；**真实记录的时间与状态一律不动**。重复运行是幂等的（移除 0）。

## 一次跑多少条：上限，不是目标

用户要求批量条数可设，并明确一条规则（2026-09-14）：**队列不足这个条数时，不要用"7 天内查过、还没到期"的 PID 补足。**

所以 `batchSize`（1–5000，默认 200）只是从**队首截断**：

```
队列 = 没查过的（按累计销量降序） + 真到期的（按最早查询时间优先）
本次跑 = 队列[:batchSize]
```

实测（队列 216、未到期 1194）：

| 上限 | 实跑 | 首次 | 刷新 | 差额 | 补足 |
| ---: | ---: | ---: | ---: | ---: | --- |
| 50 | 50 | 50 | 0 | 0 | 否 |
| 200 | 200 | 200 | 0 | 0 | 否 |
| 1000 | **216** | 216 | 0 | **784** | **否** |

差额被**如实报告**而不是填满。协议上 `padded` 必须为 `false`，若上游声称补足过，桥接层直接判为契约违规拒绝，而不是悄悄放行。

理由：查一个几天前刚查过的商品买不到新信息，只会花掉当日额度。

## 配置与页面

`config/leads-queue.json`：`refreshDays`（1–90，默认 7）、`leadsPerPid`（1–50，默认 10）、`windowDays`（1–30，默认 14，沿用平台 T−2 窗口）、`batchSize`（1–5000，默认 200）。页面上可改，改后立即重算到期。

页面面板「达人线索查询队列」在货盘页底部，展示：队列范围、首次查询数、到期待刷新数、下次到期时间、队列外数量、队首 5 个商品，以及三个可调参数。

## 执行（2026-09-14 接入）

`scripts/leads-run.py` 跑一批，页面上的「立即运行这一批」把它作为后台进程启动，前端每 4 秒轮询进度。

**复用而不重写**：传输与端点/范围校验来自 `batch_source_runtime.kalodata_provider`，响应解析与额度识别来自 `cycle_kalodata.parse_page`，达人线索写入系统已有的 `source_edge`（`bjn-local-research` 的 IT plan），并取与现有读取器相同的排他浏览器锁。

保留的纪律：

- 一次请求一页；**页面回执先落盘再导入**，崩溃既不丢页也不重复。
- 额度耗尽或身份失效**立即停止**，不继续消耗。
- **失败的查询不写 `queried_at`**：商品留在队首等下次重试，不会被错误地锁一个刷新周期。
- 同一商品连续失败到 `maxAttempts`（默认 3）次后移出队列，计入「连续失败暂停」，避免永远烧额度。
- 一批同时只跑一个：已在跑时再点返回 409。
- 运行记录超过 6 小时仍停在 `running` 的按已结束处理，进程被杀不会让页面永远显示"在跑"。

额度续跑按用户决定采用最简方式：**跑不动就停、保留断点、下次手动再点**。用户会先在 Kalodata 上测身份，身份有效后再跑。

### 实测（假 provider，未消耗真实额度）

8 项测试覆盖：成功批次写入线索并开始刷新计时、只跑队首 N 条、额度耗尽立即停且第三个商品未被请求、失败不写时钟且留在队列、连续失败后移出队列、回执复用不重复请求、空队列不发请求。

真实按钮未在验证中按下——`leads_attempt` 与 `leads_page` 均为 0 行，未消耗任何额度。

查询是只读的：不发消息、不写平台业务数据（`platformWrites` 字段在桥接层强制必须为 0，否则判契约违规）。
