# 同账号 SDK 收信与 HTTP 发信：前置验证

2026-09-26。用户同意先验证“通讯账号使用 SDK 实时收信、保留当前 HTTP 发送；另一账号处理货盘和 OECID”的关键共存条件，再决定是否迁移。

**结论：MY/acc8 的两轮短时真实验证证明 SDK 与现有 HTTP 认证/读取可以共存，原 HTTP 发送适配器也能在同一会话下走到最终许可检查。值得继续做受控真实发送试点；尚不能据此宣称真实发送吞吐、送达率或实时收信延迟已通过验收。正式收发没有切换。**

## 方法与边界

开发在 `../BDHub-Agent-sdk-probe-20260926`，实验提交 `4969c7d`，**不合入生产执行路径**。正式 HTTP 协议、发送适配器、消息状态机和 worker 不改。只给实验认证包装增加默认关闭的 retain_profile；它只能用于只读上下文，返回 adapter=None，不产生发送权限。

选择 MY 是因为当时不在 AI 09:00–16:00 或二发16:30–24:00窗口，MY 主链关闭且无在途回复/卡文。CLI 每次读取都复查窗口和任务状态，限定最长墙钟时间180秒；实际两轮分别约50秒。期间持原账号 ProfileLease，原 MY 轮询可能短暂等待；没有停止任何正式 worker。

在原账号锁内复制**同一个 acc8** 的已发布浏览器 Profile 到本项目私密临时目录，使用副本登录 SDK，避免修改正式浏览器目录。HTTP 仍使用原账号、原已发布身份和当前生产协议实现；不是把别的账号凭据拿来混用。SDK 的 IM 身份响应与 HTTP im_id 精确相符。测试后临时 Profile 删除、原锁释放，headers 摘要及已发布身份代次未变。

这是同账号、同已发布身份的临时浏览器副本实验，尚非长期驻留正式 Profile 的集成上线。没有登录维护、角色迁移、OECID 迁移、数据库迁移或生产消息投影写入。

## 实测结果

| 检查 | 第一轮 | 第二轮 |
| --- | --- | --- |
| SDK 启动到就绪 | 7.530 秒 | 6.633 秒 |
| SDK 与 HTTP IM 身份匹配 | 通过 | 通过 |
| SDK 回调挂载 | onMessageReceive / onMessageUpsert 两个入口 | 同左 |
| 另一个独立消费者重新抢同账号锁 | 被拒绝，符合现有互斥 | 同左 |
| 已持锁负责人复用 HTTP 会话 | 通过 | 通过 |
| SDK 启动前，会话＋历史读取中位数 | 1.0017 秒 | 1.0105 秒 |
| SDK 在线时，同样读取中位数 | 0.9141 秒 | 0.9184 秒 |
| 原 HTTP 发送适配器到达最终许可检查 | 未执行该项 | 通过；许可拒绝，POST 尝试0 |
| 临时 Profile 清理、headers/代次不变 | 通过 | 通过 |

每轮基线3对“会话身份＋历史”读取，SDK 在线时4对，对同一会话返回相同消息 ID。样本很小、包含网络抖动与节拍等待；只能说短时读取未见变慢，不能把数值下降解释为 SDK 提高了性能。认证请求数未独立计量。

第二轮直接使用未修改的 ItalyImDeliveryAdapter 构造文字发送路径，在原 before_dispatch 最终许可处返回拒绝；另有 HTTP endpoint 拦截层防止测试误发。原 sendRequests 计数不变，没有 POST、没有创建测试会话。浏览器端同样阻断已知发信/建会话/商品写入口；没有调用 SDK sendMessage。此处“零写入”指本探针控制的业务写入，不把 SDK 的连接心跳或协议 ACK 当成业务发送。

## 启动回放必须与新来信分开

第一轮捕获1,511条去重后的回调事件，涉及730个会话：32条达人消息、19条通知、1,460条我方消息。它们全部能在原库找到，且消息发生时间早于探针启动。第二轮捕获1,407条回调，依据 SDK 消息时间判断，真正发生在探针期间的新消息为0。

因此这些数据证明 SDK 事件回调可用，**不证明本次收到了1,511条新来信，也不能估算新来信实时延迟**。迁移时必须先精确映射原消息 ID、CID、角色和正文版本，与现有 inbox 台账去重；启动回放不能再次创建待答事项或改变原处理水位。橱窗通知也需按原生字段适配四市场，不能直接沿用旧监听器的西语/中文文本正则。

## 已验证与未验证

已验证：单一负责人持账号锁时，SDK 浏览器与独立 HTTP 通道可同时工作；当前独立进程分别抢锁的模式确实不能原样并跑。无需为了复用账号而把 HTTP 发信换成浏览器 SDK sendMessage，也不需要让 HTTP 发送等待旧版监听 tick。

仍未验证：真实卡片＋文字发送速度/确认率、真正新来信的端到端接收延迟、长时间 SDK 断线重连、身份维护/代次切换期间的在途恢复，以及其他三个市场。HTTP 读取和最终许可拒绝不能替代真实发送验收；临时 Profile 实验也不能替代正式常驻会话的长期验证。

下一步应先实现通讯账号唯一会话负责人，保留当前 HTTP 协议、唯一请求号和台账；SDK 只负责接收，HTTP 独立处理原业务队列。准备单市场小批真实业务试点入口后，再对原账号正常卡文投递测量：整套确认耗时、单位时间确认数、未知/拒绝率，以及同时到达的新来信延迟和去重。按项目约定，新执行器首次真实发送通过页面明确启动；当前探针没有真实发送入口，不复用既有全量授权制造测试消息。

若小批对照保住原 HTTP 发送表现，再推广；若会话协调代价过高或实测退步，专用收信账号方案仍可作为备选。现有四市场正式收信、二发和 AI 全量授权继续按原配置运行。
