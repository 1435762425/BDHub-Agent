## 1. 总原则（用户 2026-09-25 确定）

1. **一套逻辑覆盖所有市场。** 市场差异只进配置：市场注册表（`markets.json`）、账号角色（`market-accounts.json`）、语言与内容（`market-content.json`）、额度与节奏（`operations-policy.json`）。新代码不写 `if market == 'it'` 这类分支；现有的 IT 与 BR/MY/UK 两套实现逐步合并。
2. **先看清再优化。** 先做每市场每日漏斗看板，用数字决定后续投入。
3. **结果未知的处理统一。** 共用记录意图、原意图只读核验和证据追溯机制；后续动作按各业务已确认的规则执行，不一律转人工。Campaign 加入、全托选入/建链、二发和 AI 回复分别采用 §9 已确认的有限核验及跳过/隔离规则，技术异常不一律转人工。不换意图重发，不把未知改判成功。
4. **执行边界不变**，以 [AGENTS.md](../../AGENTS.md) 为准：
   - 在独立 worktree 开发，全量 unittest（以及相关 Web 测试、build、typecheck）通过后才 ff 合入。
   - 合入不自动重启 worker。
   - 迁移只做增量加法且保证幂等，不删库重建。
   - 对生产数据只读试跑（`mode=ro`），用来抓测试覆盖不到的问题（09-25 曾靠这一步发现漏掉的导入）。

## 3. 四市场只读运营面板

**目标：** 首页回答“已处理什么、正在等什么、真正需要人做什么”，明细按需展开。不是把不同单位的数字串起来就宣称转化漏斗。

- 当前供给/队列：累计合格 PID、当前有效绑定、A/B 线索、身份已解析/搜索不到/未完成、可发达人、首次/刷新/断点队列及最久等待，明确 PID/线索行/去重达人等单位和来源时刻。
- 近 7 个北京日：卡/文字组件数、完整触达达人、回复和橱窗事件；使用 cycle_stats 既有日界与去重口径。完整触达不能只凭一张卡确认，事件次数不冒充回复/合作人数。
- 等待：来源下一次探查、Kalodata 额度、发送/回复窗口、账号恢复、缺材料、主动暂停，显示对象范围与可知的下一动作。未知恢复时刻标未知。
- 人工事项：原业务规则明确需要人工决定的合作事项、平台必须人工验证；自动技术隔离/重试耗尽展示数量与原因，不混成必办工单，不因 unknown 历史行仍存在就把整个市场标为停摆。
- 通过固定 argv CLI/server bridge 只读访问，复用现有台账、market_read_model 和缓存；plan 由 institution/market 查询既有 plan 表，不复制到市场注册表。缺数据/读失败显示不可用，不报业务 0。
- 当前 lead_pool 的 counts 是当前投影，不能直接生成过去 7 天库存；没有历史快照的日期标不可用。阶段 itemCount 不能直接代替同群组库存，真正的转化归因另行设计。

**验收：** 四市场、空/暂停市场、缺表/缺 head、跨日卡文确认、部分送达、历史补录及事件去重均覆盖；与同范围会话/日历口径对账。技术隔离不产生人工待办；真实人工事项不能被隐藏。查询有界、不在 GET 初始化数据库，不改变任务/授权/平台状态；同时展示数据新鲜度和覆盖缺口。

## 4. 各模块方案

每个模块按“现状 / 短板 / 方案 / 验收”写。完善度评估沿用原会话结论。

### 4.1 加入 Campaign（完善度：中高）

> §9.1 的有限核验和已加入货盘独立采集已实施；下列现状/短板保留初次审查基线，当前状态见本页实施表与 §10.5。

- **现状：** 四个市场都能跑。加入属于平台写入，先记意图，结果不明时先核验。
- **短板：**
  - 明确拒绝已经会跳过该活动；加入结果未知或 status 调用失败仍会使 catalog 提前返回，可能连带跳过已加入活动的商品更新。`campaign-join-status_failed` 不能当作单活动明确拒绝的证据。
  - `/api/campaign-join` 把所有以 `campaign_` 开头的 CLI 崩溃都映射成 409，还把 stderr 尾部回传前端（审计 §6 P2）。
- **方案：**
  1. 新加入与已加入活动更新解耦。符合条件自动申请，明确拒绝沿用可追溯的跳过结果；单项未知不阻塞其他活动。没有新活动可加入或新申请全部被拒，不影响已加入活动更新。
  2. 平台原生码和脱敏原因落账，页面显示稳定码。Route 区分业务错误和崩溃，不回传 stderr。
  3. 未知只核验原申请：首次核验后最多补查 3 次，同市场本轮整批专项核验总预算 5 分钟；正常商品准备优先。预算耗尽停止主动跟进，不转人工、不安排跨轮专项追查、不重复申请。后续正常刷新若确认已加入，自动纳入商品流程。
- **验收：** 单项未知不阻止其他活动商品准备、旧活动刷新及下一轮更新；次数/时间上限、重启恢复、后续顺带确认与既有绑定保留均按 §9.1 验证。结果明确的消费范围必须完整，未知缺口单列；不得未经状态机适配直接新增 `completed_with_gaps` 阶段终态。

### 4.2 TapLink 准备：Campaign 与全托两条路线（完善度：高）

> 资格职责见 §9.2；两条来源路线、分佣、全托选入及建链单项失败/未知处理已由 §9.3 确认。已建链接维护见 §9.4；各自有限核验参数仍待细化，不能自动套用 Campaign 加入的重试预算。

- **现状：** 意图台账完整（准备、提交、回执、未知、作废）；写后按 30 秒和 120 秒各回读一次。UK 09-24 一轮建了 682 个。
- **短板：**
  - 准备逻辑集中在 `catalog_prepare.py`（727 行，一行多语句）。
  - 步骤顺序分市场：IT 是 seed/read → names → create，其他市场是 seed → localized names → read → create。
  - TapLink 清理只在 IT 执行，BR/MY/UK 整段跳过（`market_taplink_cleanup_not_enabled`）。
- **方案：**
  1. 统一步骤顺序为 seed → names → read → create。短名来源（IT 缓存或本地化生成）由 `market-content.json` 的 locale 决定，去掉市场分支。
  2. `taplink_clean` 对所有市场启用。先做只读扫描和本地停用（期限、佣金门槛），经用户确认后再对非 IT 市场开放平台删除。
  3. 按步骤把 `catalog_prepare.py` 拆成 seed、names、read、create 四个函数模块，意图台账不变。
- **验收：**
  - 同一批输入在新旧顺序下，生成的意图和绑定集合一致。
  - BR/MY/UK 清理只读扫描的输出与 IT 口径一致。
  - 平台写入数没有额外增加。

### 4.3 全托商品：货源采集与选品（完善度：中）

> 本节原有“普通周更维护货盘”的优化方向已被 §9.2 替代：首次及每 15 天按类目发现新增合格 PID，候选累积不覆盖。下文现状与历史短板保留供审查追溯，实施以 §9.2 为准。

- **现状：** 采集有普通增量和按类目两种模式。选品先记意图再逐个回读；09-25 补上了跨活动选品自动隔离（`isolated_unverified`）。
- **短板：**
  - 这是最脆弱的模块：IT 从 09-21 断到 09-24，靠临时写的恢复工具（`workflow_recovery.py`）才续上。
  - 轮次和货源的对应关系是推算出来的（`selected_source_run_id` 由市场、北京日期和 run id 摘要算出），没有持久记录。
  - 采集模式分市场硬编码：IT 固定普通周更，UK 首次/月度按类目。
- **方案：**
  1. 在 catalog 阶段开始时，把本轮选定的来源轮次写入 stage 的持久字段（例如 `workflow_stage_run.input_source_run_id`，增量迁移）。下游和恢复只读这个字段，推算函数只用于兼容旧轮次。
  2. 按 §9.2 将首次及每 15 天按类目探查、市场全托能力进配置；目标为发现新增 PID，不再用普通周更维护旧商品作为常规采集任务。
  3. 把“部分完成可续跑”作为采集的正常路径：分区断点、repair page 和 `accepted_partial` 都写进 stage 结果，由通用续跑入口处理（§4.10 第 3 条），不再为每种故障写一次性工具。
- **验收：**
  - 模拟采集在第 N 页中断后，原轮次跨日从持久断点续跑，不建立第二天的新轮次冒充原轮完成。
  - 旧轮次仍能被推算函数识别。

### 4.4 ② OECID 获取（完善度：中低）

- **现状：** 两套完全不同的实现：
  - IT：`creator_discovery.py` / `identity_queue.py` / `second-cycle-identities.py`，精确 Find 加身份队列。
  - BR/MY/UK：`market_identity.py` 由 scheduler 调用，每 3 个 handle 拉起一次 `probe-italy-profile.py`（542 行），依赖旧系统的签名 runtime。
- **短板：**
  - IT 有 1,406 条线索未解析（lead-pool `unresolved`，09-25 10:45）。已判定的 `unresolved` 会被复用，目前看不到重试节奏，需核实。
  - B 类作者从不送去解析：`cycle_identity.freeze` 只取 A 类 selection，IT 有 134 条 `videoUnresolved`。
  - 探针初始化存在竞争（09-25 已加一次重试）。
  - 证据目录 `var/market-identity-{m}-*` 不清理。
  - 页面的身份队列、精确发现和画像刷新只支持 IT。
- **方案：**
  1. **统一实现。** 以证据更完整的一套为核心（建议 IT 的 discovery/outbox 台账，Codex 审查时确认），抽出“handle → OECID”的市场无关服务：
     - 输入：市场、handle 列表、来源（A/B）。
     - 输出：resolved、unresolved、blocked，附证据。
     - 账号、QPS、profile 类型集合从配置读取。
     - BR/MY/UK 切到这套服务后，删除 `market_identity.py` 与 `probe-italy-profile.py` 的重复部分。
  2. **身份终态复用与技术失败分开。** 用户已选择 §9.7：平台正常返回、没有精确匹配的 `unresolved` 不再自动查询，取消 7 天补查建议；同市场同 handle 在不同 PID、A/B 来源或新查询窗口再次出现时复用判定。`blocked`/超时等没有取得有效结论的任务单独按技术恢复规则处理，不能写成搜索不到。
  3. **B 类作者送解析。** 冻结时同时取 A 类 selection 和 `video_lead_current` 的作者 handle，去重后进同一队列；解析后 B 类位置按 PROJECT 排序进入可发层。
  4. **摆脱旧系统签名依赖。** 把签名 runtime 纳入 `scripts/vendor-runtime`（固定 manifest hash，`--check` 可验），运行时不再读旧目录。迁移前后同一批 handle 的签名结果逐字节对比。
  5. 证据目录纳入 `state-retention.py` 的保留规则。
  6. 身份队列、精确发现和画像刷新的页面与 API 改为按市场参数工作。
- **验收：**
  - 四个市场走同一入口，scheduler 中 OECID 阶段没有市场分支。
  - IT 未解析数、B 类 `videoUnresolved` 在漏斗看板上可见并下降。
  - 同一 handle 重复提交不重复调用平台。
  - 旧目录不可读时，OECID 仍能运行。

- **现状：** 阶段、屏障、租约和检查点都完整。
- **短板：**

## 5. ③ 统一结果未知框架

> 本节是跨模块框架草案，不覆盖已确认的领域例外：Campaign 加入未知按 §9.1 当轮有限核验后自动结束跟进；二发建会话/卡片/文字未知按 §9.12 有限核验后自动隔离原投递，不转人工，不因保留隔离后的 unknown 记录长期阻塞其他达人。其他场景按对应业务确认，不一律转人工或统一终态。

现有做法分散在多处：

| 场景 | 当前实现 |
| --- | --- |
| 卡片未知 | `quarantine_absent_card`（两次回查，间隔 ≥300 秒，读到历史却没有这条消息） |
| 建会话被拒（201） | `quarantine_refused_creates` |
| 建会话无回执 | 人工 `quarantine_unknown_conversation` |
| 选品活动不符 | `isolated_unverified`（两次回读，间隔 ≥5 分钟） |
| TapLink 新建回读缺失 | 保留 unknown，不重复 POST |
| 加入 Campaign 未知 | 先核验 |
| AI 回复未知 | `reply_blocker` 阻断 |

**方案：**
1. 抽出一个通用组件（例如 `scripts/lib/unknown_outcome.py`）：
   - 每类意图登记：只读核验函数、证据标准（最少回查次数、最小间隔、什么算“确认不存在”）、隔离动作（转人工、开 case、排除对象）、阻断范围（只挡该对象，还是挡整个市场）。
   - 台账字段：未知开始时间、最后核验时间、核验次数、证据缺口。
2. 协调层按各领域已确认的原意图策略安排有限核验、跳过或技术隔离；领域台账保持权威，不强制把不同状态改成 waiting_reconciliation。隔离可源于已批准的预算耗尽政策，仍保留未知，不能冒充证实未送达。
3. 页面复用原台账汇总未知/隔离数量与年龄，区分已自动处置、仍阻断的等待和真正人工事项；不把技术历史记录变成必办工单。

**验收：**
- 现有七种场景迁移后，原测试全部通过。
- 正反合同覆盖：证据不足不改判成功/失败；无已确认隔离策略不擅自放行；获准预算耗尽的技术隔离保留 unknown；历史不可读不算不存在；隔离后不重发且不误解除其他限制。

- **“回复后 72 小时加橱窗”需要新归因口径。** 同一达人多 PID、多次回复、重复通知和历史补录如何归属尚未定义；要标为观测关联，不推断 AI 导致合作。不能从 `cycle_stats` 每日事件数直接得出。

#### I. 账号管理（§4.9）

- **项目自管身份代次、72 小时维护、保存密码依赖旧项目属实。** `account_identity.py:3、71–74、434`，`project_account_identity.py:3–4、42、318–323`。72/84 小时是历史实例，不是固定有效期；旧 launchd 的实际加载状态与动作本次未检查，保留待运行审查，不凭任务名判断冲突。
- **健康探测与统一恢复必须按账号角色建模。** 当前 `login_recovery.request_refresh` 固定 communications，按 market/account/generation 幂等（28–50）；OECID 还有 scheduler 自己的恢复入口（`operations_scheduler.py:301–318、548–556`）。要先统一请求身份和去重规则，避免轮询、OECID、发送及维护同时登记刷新；货盘账号不能错误刷新成通讯账号。只有认证失效证据才触发刷新，验证码/签名/网络错误不得一律视为掉线。
- **低成本探测也要服从 profile lease、共享访问节拍和在途写入。** 增加频率前定义请求预算、忙时跳过、抖动和失败退避；刷新失败保留上一身份且不扩大 capability。凭据迁移还需账号配置/元数据的完整依赖闭包；仅换密码存放位置不能证明旧目录不可读时仍可维护。旧 launchd 的检查与停用不是本次授权范围。

#### J. scheduler 与统一 unknown（§4.10、§5）

- **批次领取屏障属实，但“完成一个就结算一个”已经实现。** `operations_scheduler.py:682–710` 使用 FIRST_COMPLETED，逐 future finish/release；问题是 wait 循环内没有再次 `claim_ready`，要等全部 pending 结束。状态在有 done 时会写（714），无完成时不刷新 checkedAt；背景收信/发送/Agent/维护仍每轮被监督（686–689），不能描述成整个 scheduler 停止工作。824 行属实；市场分支数量只是结构指标。
- **只修补调度先于大拆分。** 常驻集合方案需保留单市场槽、平台一槽、Kalodata 两槽、owner/fence、真实子 PID 登记、每 30 秒续租、父死子活不释放槽等合同（`workflow_dispatch.py:9–28`、`workflow_resources.py:14–61`）。新循环每轮重读停止/授权/到期状态，不能沿用启动批次的设置快照；≤30 秒启动的验收前提是上游成功且所需槽位空闲。
- **恢复入口可以统一，恢复条件不能统一放宽为“写入已结清”。** `workflow_recovery.py:36–181、193–284` 和 `operations_workflow.py:290–436` 分别绑定原错误、来源、upstream、配置、实际回执/隔离和一次性 checkpoint。原 selected 恢复还会审查重复轮次，不能被普通白名单吞掉。先让统一入口路由已有策略、保留旧命令及请求幂等；不改变每条策略的证据阈值。所谓六类还包含 check/read-only 与 resume/write 两种动作，不能混为一键执行。
- **needs_human 阻止下一轮属实，放行不是普通调度优化。** `operations_scheduler.py:635–638` 明确 continue。必须先定义旧轮冻结/未知与新输入的关联、唯一活动轮次、head 归属和资源互斥；“下游尚未开始”不足以证明不受旧写入影响。
- **统一 unknown 应是策略协调层，不是第八套业务账本。** 原写入意图/结果仍归现有领域台账；新增核验元数据若必要，只引用原 market/account/intent，并记录策略版本、核验时刻和证据引用。`waiting_reconciliation` 可统一 worker 展示状态，但不能强行替换数据库中 result_unknown/unknown/isolated_unverified/quarantined_unknown 等已有含义。
- **七类不能统一成“证据够就隔离”。** 201 已知拒绝、选入 Campaign 失配、卡消息缺失、TapLink 未读到、AI 回复未知的证据与阻断范围不同；尤其选入失配隔离的是商品，而卡未知隔离达人并开 case。保留原策略；没有已授权隔离策略的场景继续原意图核验或人工处理。核验成功还必须有“确认原意图成功”的路径，不能只设计隔离分支。停止/窗口外核验不得领取下一人、补发未提交组件或换号。

### 8.3 遗漏项

#### A. 增量、幂等迁移的具体合同

当前方案只有原则，尚不足以判定迁移已经可实施或幂等：

| 迁移 | 必须补充的设计与验收 |
| --- | --- |
| B 类 market / generation | 不能只 ALTER 两张表：旧 head/current 的主键仍会冲突，`INSERT ... VALUES` 也会因列数变化失败。推荐增量新建含 market 的替代投影/head 表，保留旧表，确定唯一权威写入路径和兼容读取期限；不是两套长期并行事实源。旧不可变 run/evidence 有 UPDATE/DELETE 禁止触发器（`schema_migrations.py:387–394`），需采用版本化新表或只读归属映射，不能直接回填旧不可变记录。generation/hash、缓存、查询和所有位置参数 INSERT 一起盘点。 |
| stage 来源绑定 | 可新增可空字段或专用绑定表/既有 checkpoint；旧轮次只在证据唯一时回填。相同 run 重复设置幂等，不同 source/hash 拒绝覆盖；崩溃在“落绑定/外部调用/发布”各处均恢复原 source。检查 `state_retention.py:54–78、112–164`，使新字段引用的来源不会被归档误删。 |

| 身份队列与控制 | 旧 outbox/终态/证据引用、retry_at、attempt_no、lease 和 capability 必须保留；跨市场同 handle 用独立键。control revision、pilot/full、runRequested、stopRequested 不因迁移变动，不以新默认值覆盖旧授权。 |

迁移统一使用新增 registry 版本，不改已应用 SQL/checksum（`schema_migrations.py:1137–1144、1174–1194`）。在旧库副本上验证首次、第二次、半途失败重跑、空库/缺表拒绝、同 PID/handle 跨市场碰撞；对账行数、主键、引用、原证据 hash、意图/回执及授权不变。备份/verify、部署兼容矩阵和回退读路径应在实施说明里写清。旧 worker 未退出时不能发布它无法写入的新 schema；只读试跑不得调用会建表/初始化的 Store 构造器或业务执行入口。

#### B. 会影响在运行 worker 的改动及切换条件

本次只确认代码依赖，不声称已核实实时 PID/锁/断点。发布前由实施任务在获准范围内检查：

| 改动 | 受影响执行链 | 切换前必须核对 |
| --- | --- | --- |
| Campaign、来源绑定、TapLink 顺序/清理 | scheduler 拉起的 catalog/selection/prepare/clean 子进程，以及读取 current binding 的发送/回复 | 原 run/source/head、意图是否已提交、prepare lease/fence、未知回查、旧 argv/状态兼容；本地停用后的逐写拦截 |
| 身份、B 类发布/schema | scheduler 的 Kalodata/OECID、identity-batch/profile worker、发送池读取 | 正在扫描的 generation/PID/page、outbox/cohort/attempt、账号 profile lease；禁止新旧写者并跑不同发布协议 |
| poller 合并 | IT job_run/inbox、三市场 poller、Agent 消费链、IT 会话索引 | 原 cursor/checkpoint/基线/gap、全部锁与停止文件、双方 supervisor 启动条件；旧退出后才能启新，防 scheduler 重拉旧入口 |
| 二发/回复/unknown/签名 | 两类 sender、Agent、人工回复、认证与账号维护 | 原 control revision/授权、delivery/service_reply/requestRef、冻结 executionMode、在途组件与账号写锁；只读核验和新发送必须分开 |
| scheduler 循环与恢复 | scheduler 及仍存活的所有 stage 子进程 | 父/子 PID、claim owner/fence/lease、资源槽、下一次重试时刻、原 stage checkpoint；不能以旧父退出推断子任务已结束 |
| 凭据/健康探测 | 本项目维护、所有认证路径；旧系统任务仅作只读核查 | 当前身份代次/能力、同账号维护意图、锁、凭据来源；不因刷新或发布开启新授权 |

**合入本身也可能改变后续执行：** scheduler 按生产路径启动子脚本，旧常驻父进程可以立即拉到新代码。因此“合入不重启”不等于“运行不受影响”；需要兼容版本或用户确定的安全切换时点。避免边改 schema/协议边让旧父进程调用新 CLI。

### 8.4 建议的第一步实施范围

**第一步只做“统计口径修正＋四市场只读运营面板”，暂不接身份新执行器或迁移 worker 状态。** 这保持用户“先看清再优化”的顺序，同时避免用错误的 1,406 和混合单位决定投入。

具体范围：

1. 定义并实现当前 A 来源行数/去重 handle、已解析、已搜索不到、未尝试、排队/blocked，以及 B 已知/未知作者数；另列发送池位置、可发达人和等待原因。身份分类须互斥、总数可对账，修复 `counts.queued` 同名覆盖的接口歧义并保留旧消费者兼容。
2. 复用 `cycle_stats.daily` 展示近 7 个北京日卡/文字组件、完整触达达人、达人回复事件与橱窗事件；明确时间字段与单位。当前库存仅显示当前快照，历史库存无证据则不可用，不展示未经归因的转化率。
3. 增加只读 CLI/bridge/首页卡片，显式 market 校验，缺数据不报 0；复用现有只读连接、快照与缓存，普通 GET 不建表、不推进任务。首步不迁移 B/unknown/source 业务表，不修改授权和调度策略。
4. 完成分类恒等式、市场隔离、缺数据、跨日、部分送达及旧字段兼容测试；在独立 worktree 做相关 Python/Node 测试、Web build 后 typecheck。代码验收和未来生产只读对账分开报告；不借验收启动 worker 或平台写入。

下一步分别提交 **B 类按完整 PID 原子发布修复** 与 **scheduler 在长任务期间补领就绪阶段及刷新心跳** 的小范围方案。两者优先于跨市场大合并，分别明确运行中断点兼容和切换时间；不夹带 7 天重查授权、全市场 B 启用、旧门禁删除或 AI 全量开启。

## 9. 逐模块业务确认

以下记录用户在审查后的业务决定，优先于本文此前相冲突的建议。当前仍处于逐模块讨论阶段；确认业务方案不等于要求立即实施、启停进程或改变生产授权。尚未讨论的模块不自动继承本节策略。

### 9.1 加入 Campaign（用户 2026-09-25 确认）

**目标：符合既定条件的活动自动申请加入；单个活动查不清不阻塞其他活动，不交给用户管理。** 用户接受以放弃暂时无法确认的活动机会，换取有限开销和流程持续推进。

1. **正常申请：** 对符合现有条件的活动自动加入，先记录原意图再提交；明确成功继续，明确拒绝记录原因并跳过。没有新活动可加入，不妨碍更新已加入活动的商品。
2. **未知时跳过当前项：** 保留活动、原账号、原请求和已有回执，继续处理其他活动。已核实活动的商品采集、筛选和建链不等待未知项查清；发布需标明本轮已核实范围与缺口，不把缺口称为全范围完整。
3. **当轮有限核验：** 先完成其他活动的加入处理，优先推进已确认活动的正常商品准备，再批量核验未知项。首次核验后最多补查 **3 次**，即最多 4 轮读取；一轮是完成所需列表核验，不是一页或一个 HTTP 请求。同一市场、本轮整批未知项的专项核验总预算 **5 分钟（300 秒）**，替代此前讨论的 60 秒；初始化、账号锁等待、首次核验、补查、分页、平台验证和核验内等待均计入，不按每个活动分别获得预算。次数或时间任一耗尽即结束，全部查清提前结束；单次请求及验证须服从剩余总预算，不在主流程中长时间 sleep。复用当轮有效读取结果，多个未知项共享列表读取；确认已加入必须精确匹配原活动或返回子活动，判断未加入必须有完整且有效的否定证据，列表没读完整不能证明未加入。
4. **重试只读查询，不重复提交：** 原申请结果未知时，不重新 POST、不换账号或请求意图。有限重试不是重复申请机制。
5. **预算耗尽自动放弃跟进：** 结束该原申请的主动核验，不建立 30 分钟/2 小时/24 小时后台追查任务，不转人工、不产生需要用户处理的活动告警。保存“原申请结果未知、已停止主动跟进”；不改判成功或明确失败，不使用未经确认的新活动材料。
6. **跨轮与重启保持决定：** 保留原意图及已耗核验次数/预算，恢复不重新给满预算，下一轮不能把它当成从未申请过而再次提交。正常活动刷新若顺带发现已加入，可按原活动/返回子活动的有效证据自动确认并纳入商品采集；不为此单独主动追查，也不重跑其他已完成活动。
7. **已加入活动与既有材料不受新申请失败影响：** 已确认加入的活动照常刷新活动和商品信息；合格商品照常筛选、建链、获取线索和发送。不能因某个新活动的未知/放弃或本轮读取缺口，提前结束整轮、跳过旧活动更新、退出旧活动、删除旧链接或停用仍有效的旧商品。活动到期、商品明确失效、佣金不再合格等自身资格变化仍按原规则处理。未知活动不阻止下一轮正常更新，不改变已有有效商品的发送授权。
8. **边界：** 本决定只处理申请加入新活动及该原申请结果未知，不改变已加入活动的正常刷新周期、商品资格或平台成员关系。“放弃”只是停止主动追查，不是退出 Campaign。账号认证失效、全局读取异常的恢复由账号模块另行确认；不能把整账号故障伪装成“所有活动都没有资格”。其他写入场景不自动套用“3 次补查/5 分钟后放弃”。

**处理结果与后续动作：**

| 结果 | 系统动作 | 对其他活动及旧活动的影响 |
| --- | --- | --- |
| 明确加入成功或精确回读确认 | 结束该申请的核验，采集其商品并进入既有后续流程 | 继续正常处理，不重跑其他已完成活动 |
| 平台明确拒绝或有效证据明确未加入 | 记录证据和原因，结束本次申请 | 其他活动继续，已有货盘正常更新 |
| 次数/预算耗尽仍未知 | 保留原意图与未知结果，标明已停止主动跟进；不重复申请、不建立人工待办 | 未确认的新材料暂不使用，其他活动和旧有效材料继续 |
| 正常刷新顺带发现此前未知申请已成功 | 按原活动证据自动确认，并纳入正常商品采集 | 不新增专项追查任务，不重跑其他活动 |

**5 分钟预算依据与取舍：** 当前 `campaign_join.py:184–222、264–267、481–504` 每轮读取可加入/已加入两份列表，每页 100 条、每份最多 20 页；`vendor/bdhub/send/taplink/transport.py:43–67` 请求间隔至少 1 秒，连接/读取超时为 5/25 秒；`global_source_transport.py:58–78` 账号锁可等 15 秒。首次加 3 次补查不是 4 个 HTTP 请求，60 秒可能过早耗尽。5 分钟为本轮讨论选定的初始总上限，不是生产实测耗时，也不保证一定完成 4 轮。核验仍消耗请求和账号/平台资源；本方案接受有限额外成本和漏掉未确认活动机会，不声称零开销或全部申请都能查清。

**执行与发布要求：** 新加入、已确认活动更新和未知项核验不能继续共用“一个未知就提前返回”的串行成功条件。专项核验不得排在已确认活动的正常商品准备之前独占账号/平台槽；不提高已有平台并发容量来掩盖竞争。已确认范围的商品仍需完整采集、去重与资格核对后发布，未知申请单独列缺口；旧活动一次读取失败不能用空快照覆盖旧 head，也不能触发有效绑定退役。实施时须明确阶段拆分或范围发布方式、generation 归属及断点，保证下游消费已核实范围，而不是只修改页面状态。相关配置保存为本模块参数，不复用为全系统 unknown 默认值。

### 9.2 全托 PID 发现、候选累积与建链前检查（用户 2026-09-25 确认）

**目标：尽可能多地发现全托商品 PID。** 采集只判断商品在采集当时是否符合入池条件，保存符合条件的候选；不以持续刷新旧商品信息为目的。商品后来下架或商业条件变化，由选入的实际平台结果、TapLink 准备及链接有效性维护处理。

**适用范围与节奏：**

- 支持且已接通全托能力的市场，首次接入做一次完整的按类目探查，以获取尽可能广的商品范围；之后每 **15 天**再做一轮按类目探查。不增加每日扫描，也不再以普通每周查询更新旧商品为常规采集路径。
- 此方向适用于 IT、UK 及后续具备全托能力的市场，替代原 IT 普通周更/不再新建类目采集、UK 每 30 天类目采集的业务方向。BR/MY 等尚无全托能力的市场不因统一配置自动开启。
- 首次指新市场接入的首轮，不是服务重启或每次部署都重跑首轮。原轮未完成就续原类目/页码断点，不开启同市场重叠扫描；跨日或到下个周期也不能丢弃原断点重头开始。周期与来源绑定持久化，沿用既有调度、锁和租约。
- 新规则上线不自动恢复历史上被用户停止的 IT 类目任务，也不修改已有 worker、授权或生产开关；既有候选及在途任务的迁移/切换在实施前明确，保留原证据。

**候选入池与去重：**

1. 沿用采集时的条件：高机会商品中的“仅全球销售商品”；累计销量 ≥300；有评分时 ≥4.0、无评分允许，未核实的 0 不解释成无评分；总佣金－公开佣金 ≥2 个百分点；无库存数量门槛，但明确下架/治理/失效排除。
2. 满足条件即记录候选资格事实：market、PID、来源、采集时间、来源 run/类目/页或证据引用、当时销量/评分/佣金及规则版本。证据合格只表示取得后续候选资格，不表示已经选入、建链或获得发送许可。
3. 以 **market×PID** 累积去重，跨类目、跨轮出现同一 PID 不重复创建候选或后续任务。商品在上轮未达标、本轮首次达标时可以新增；不能把“曾见过 PID”误当作“已经取得候选资格”。不同市场相同 PID 分开处理。
4. 新一轮只增加新合格候选，不用新采集结果覆盖或删除历史候选；旧商品未出现、之后销量/评分变化均不抹去当时的入池依据。重复读取可追加必要来源证据，但不是重新刷新全部旧商品、重复选入/建链的理由。
5. 已完成的 PID 不重复入队；在途 PID 续原任务；结果未知的选入/建链只能沿原意图处理，不因重新发现而新建请求。**明确失败的旧 PID 后来再次符合条件是否重新入队，尚未确定**，本次不新增自动重试授权。
6. 候选历史与当前可用材料分开：候选可以长期保留，其下游任务可以处于待处理、处理中、已完成或本次不可继续；保留候选不等于永久保持可发。复用现有来源证据与台账，不引入第二套平行候选事实源。

**各环节的资格职责：**

| 环节 | 判断与动作 | 失败处理 |
| --- | --- | --- |
| 采集入候选池 | 按当时销量、评分、佣金等规则取得候选资格并保存证据 | 当时不合格不入池；不定期回头重查所有已入池商品 |
| 选入机构商品池 | 按当前平台接口合同执行选入；先落原意图，不省略必要请求校验 | 明确拒绝跳过该商品；结果未知保留原意图，不重复选入；不把单项拒绝扩大为整批失败 |
| TapLink 准备/建链前 | 读取当前推广事实：商品/对应活动是否有效、是否允许推广、当前佣金是否满足合作和建链要求 | 明确下架、失效或佣金不合格，记“本次不可建链”并移出当前待建队列，其他商品继续；候选及证据保留 |
| 已有 TapLink 后续使用 | 由链接有效性维护及发送前既有材料门禁判断当前材料 | 明确失效停用对应材料，不删除历史 PID；不回到采集模块建立旧商品刷新任务 |

- 建链前核对的是“现在能否推广及当前商业条件”，不以重新达到历史销量/评分阈值作为常规二次入池条件。全托资格不能误套 Campaign 的普通库存规则；当前佣金必须用于生成实际卡片，不沿用过期佣金。
- **读取失败不是商品失效。** 超时、登录异常、平台验证或未完整读取不能写成“下架”或永久淘汰；保留候选，按后续 TapLink 环节的有限读取重试规则处理。该重试次数/预算尚待 TapLink 讨论，不套用 §9.1 的 3 次/5 分钟。
- 仅未提交的新建意图可以因事实变化安全结束/退役；已提交或结果未知的意图继续受原意图核验合同约束，不能借“商品失效”删除证据或重建请求。
- 已建链接的刷新节奏、暂时不可建链商品何时再给机会，属于后续 TapLink 决策；本次没有把全托卡每周核验改为每 15 天，也未关闭现有链接维护。

**覆盖、发布与增量的含义：**

- “增量”指候选集合取并集、新候选只入队一次，不代表平台提供增量 API。每 15 天通常仍需遍历各类目列表；不能因当前页全部是旧 PID 就停止翻页，后续页可能出现新商品。
- 保留类目分页、数量核对、动态列表差额、repair page 和覆盖证据，不能把平台窗口截断/读取失败称为完整发现。新类目也应从当轮平台类目范围发现，不只固定遍历首次缓存的类目。
- 来源扫描快照/head 与累积候选是不同用途：前者描述本轮覆盖，后者保留历次合格 PID。原有 sourceRun/head/overlay 与下游绑定须逐项适配，不能继续把“本次 head 没出现”作为删除候选或退役有效材料的条件。
- 单 PID 合格证据可先保存；扫描未完整不能冒充完整 generation。首版保持完整范围发布与原断点恢复合同；是否允许部分已完成类目提前发布到下游，若后续需要另行确认，不自动将 Campaign 的范围例外扩到全托。
- 候选引用的资格证据、在途意图与恢复来源应受 retention 保护；不会因旧扫描快照轮换而丢失累计候选的依据。迁移采用增量、幂等方式，保留旧候选、身份、选入/建链回执和授权，不删库重建。

**已接受的取舍与关注指标：** 15 天节奏可能延迟发现新商品、漏掉短暂上架的商品；类目全量读取仍有请求成本，且平台接口限制不等于全站绝对完整。累积候选会增长，建链前还会淘汰部分已失效商品。主要观察本轮新增合格 PID、累计唯一候选、类目覆盖/未完成范围，以及新增候选走到选入和有效 TapLink 的数量，不把扫描返回总行数当新增商品数。

**实施验收：**

- 首次完整类目探查及后续 15 天到期规则按能力配置生效；重启不重置首轮/到期时间，未完成时不启动同市场重复轮次，IT 历史停掉的任务不自动复活。
- 首轮入池 A/B，次轮读到 B/C，则累积候选为 A/B/C，只新增 C 的任务；A 本轮没出现不被删除。跨类目重复不增加候选，跨市场同 PID 互不覆盖。
- 上轮见到但不合格的 D，本轮首次合格可入池；已有 PID 的正常重见不重置处理中、成功、明确失败或未知状态。
- 同一输入重放、入池后未入队崩溃、入队后未回执崩溃均幂等；原选入/建链未知不重复提交。来源 run、分页、规则版本及资格事实可追溯。
- 采集时合格、建链时已下架或佣金不合格，只停止该商品本次建链；其他商品继续，历史候选不丢；不因销量/评分后来变化重复做常规入池筛选。
- 建链读取超时/认证失效不写成商品下架；已有链接后来明确失效由材料维护停用，不触发全候选池重新采集。
- 中断保存原类目/页码并可恢复；旧页全是已知 PID 时仍继续到实际末页/受限终点，缺口如实记录。来源版本轮换不丢累积候选及被引用证据。

**实施状态：** 2026-09-25 已实现并加载首次/15 天类目发现、历史候选累计、原选入任务引用、推广检查分工和增量幂等回填；没有主动开启新扫描或恢复历史停止任务。数据、验证及运行边界见 [全托增量发现交付](fullmanaged-incremental-discovery-20260925.md)。


### 9.3 TapLink 两条路线、全托选入及单项异常（用户 2026-09-25 确认）

**两条来源路线，不是所有商品都必须依次经过的两个阶段：**

| 来源 | 流程 |
| --- | --- |
| Campaign | 已确认加入活动 → 采集、筛选活动商品 → 准备该活动商品 TapLink → 回读确认 → 后续达人线索 |
| 全托 | 按类目发现合格 PID → 累积候选 → 选入机构已选商品池并确认 → 准备对应实际商品方案 TapLink → 回读确认 → 后续达人线索 |

Campaign 路线不调用全托选入；全托单项选入失败或未知不阻塞 Campaign 建链。共用的是当前推广条件检查、本地化名称、佣金计算、完全匹配的已有链接复用、创建及回读。market/PID/来源/Campaign/商业条件必须精确匹配，不能以相同 PID 为由跨路线复用错误链接。

**分佣继续沿用：** 机构至少 1、优先 2 个百分点，达人至少比公开佣金高 1 个百分点；机构收益取 `min(2, 总佣金－公开佣金－1)`。公开 10%、总佣金 12% 时机构 1、达人 11%；总佣金 13% 时机构 2、达人 11%；总佣金 15% 时机构 2、达人 13%。按当前核实的佣金建链；空间不足停止该商品本次建链，保留历史候选，不发送旧佣金承诺。

**全托选入处理：**

- 已在选品池中且当前可用商品方案已经核实：复用，不重复选入，进入对应方案的建链准备。
- 新选入回执/回读精确确认：进入建链。
- 平台明确拒绝：记录原因并跳过该商品，其他商品继续。
- 请求已经发出但结果未知：保留原账号、原请求、目标 PID/Campaign 与证据，只做有限只读核验；仍查不清就跳过本次使用，不交给用户，不让该项卡住其他商品或市场路线。不换号、不改意图、不重复选入。
- 池里只看到同 PID 的其他 Campaign，不等于原申请已经成功。未提交前复用已核实方案，与已提交后核验原目标是不同路径；后者不得偷偷换活动确认成功。现有活动失配隔离证据和状态予以保留，不因这次讨论放宽为任意同 PID 即成功。

**建链处理，两条来源共用：**

- 已有完全匹配当前方案且经核验的有效链接直接复用，不额外创建。
- 商品明确下架、当前佣金不合格或平台明确拒绝，结束该商品本次建链，继续其他商品；不删除候选历史。
- 创建结果未知时先继续其他商品，批后统一有限回读。仍未知就保留原创建意图、本次不使用，不拖住其他已确认链接，不建立需用户逐个处理的待办；“没查到”不能当作“没创建”重新 POST。
- 读取超时、认证异常、未完整分页不是商品失效；不能用失败读取把原有效链接批量停用。账号级故障需按账号合同处理，不以跳过所有商品伪装正常完成。

**边界及尚待细化：** 这次确定的是自动处理、有限核验及单项不阻塞的业务方向。选入核验、建链前读取失败、新建链接未知分别评估接口成本并确定次数/总预算；§9.1 的 3 次/5 分钟只适用于 Campaign 加入。旧失败/隔离商品是否在未来重新处理和新增平台删除权限仍未扩展；已建链接刷新频率见 §9.4；本次不新增自动重发、旧任务恢复或删除授权。有限核验耗尽后原结果仍未知，不改判成功/明确失败，重复发现与 worker 重启也不能产生新写入意图。

**实施验收：**

- 同批含 Campaign 和全托商品时，Campaign 不调用全托选入接口；一个全托选入始终未知，其他可用商品仍能完成建链，不让 catalog/stage 屏障把所有路线一起挡住。
- 新选入未确认不建链；已核实的已有选入可复用；同 PID 错 Campaign 的回读不能确认原申请成功；不同市场同 PID 不串用回执或链接。
- 两条来源都按相同已确认分佣规则处理边界；资格/商业事实变化仅影响相关商品，精确匹配的旧链接不重复创建。
- 原意图核验、批后回读、有限核验后的跳过均保留请求与证据；未知期间及进程恢复后没有重复 POST，没有用户待办，其他已确认材料可继续推进。
- 分别统计选入成功/拒绝/未知跳过、链接复用/新建确认/不可建链/未知跳过；跳过不是成功，不把不完整商品范围称为全部完成。

**实施状态：** 仅记录确认结果，代码与生产行为尚未调整；后续明确核验参数并在独立 worktree 实现和验证，不因文档更新启停 worker 或执行平台写入。


### 9.4 已建 TapLink 维护（用户 2026-09-25 确认）

本次确认不等于全市场平台删卡授权：内部佣金/期限不合格、暂缺货、混合有效卡、未知状态均不构成删除依据。非 IT 清理扫描/本地停用尚未接通的实现缺口继续按方案补齐，平台删除保留原 canary/能力与授权边界。

### 9.5 Kalodata A/B 线索范围（用户 2026-09-25 确认）

| 类型 | 已确认范围与筛选 |
| --- | --- |
| A 类 | 四市场每个精确 PID，近 14 天有正销量的达人，按该商品关联 GMV 降序，每 PID 最多 50 位；替代原上限 20 |
| B 类 | IT、BR、MY、UK 均接入；近 30 天精确关联该 PID、单条视频累计播放 ≥1,000 的达人，不要求出单 |

**口径保持：**

- A 类保留数值 GMV、币种和来源排序；少于 50 位合格达人就保留实际数量，不用零销量、缺销量或非法 handle 凑数。50 是每 market×PID 的达人上限，不是每页上限、总请求数或全市场人数上限；不能外层写 50、内层仍截到 20。
- B 类同达人同 PID 多条视频只取最高播放的一条，并列取较新发布；不把多条不足 1,000 的视频相加越过门槛。保留视频 ID、作者、播放量、发布时间、市场及商品关联证据。
- 同市场同达人×PID 同时命中 A/B 时合并为 A 并保留视频证据，不能由两条来源各触达一次。不同 PID 可以保留不同位置，但仍由后续身份、关系、冷却和发送去重控制是否联系，不以线索数直接当可发人数。
- 仅对已有可用 TapLink 的合格商品范围读取达人线索。全托候选累积、15 天商品发现和 Kalodata 线索刷新是不同任务，不能将所有历史候选无条件送入 Kalodata。
- B 类四市场接入需覆盖 market/区域/币种、视频扫描与作者缓存作用域、generation/head/投影、额度及身份衔接。接入资格不等于可以直接取消现有 IT 分支；先修未完成换代清空投影、跨市场主键冲突等 §8 指出的合同缺口。

**取舍：** A 类提高到 50 可扩大每个商品的正销量达人覆盖；若商品有足够合格达人，上限是原来的 2.5 倍，但实际新增量和请求耗时不能据此直接乘 2.5。B 类增加视频潜在合作对象，会增加视频读取及作者解析需求，播放达标不代表有带货转化。各市场真实额度仍按平台规则计算，不因方案扩围而增加配额或绕过限制。

**验收：** 正销量不足 50、恰好 50、多于 50、分页重复与无效 handle 均覆盖，排序和去重后数量准确；B 类 999/1,000 播放、窗口内外、同作者多视频和 A/B 重合均验证；四市场同 PID/handle/videoId 不串数据；未完成扫描不冒充完整结果；新配置/schema 迁移不抹去原来源证据或重复触达。已有每 PID 20 位的已发布结果如需扩充，须建立明确新查询范围/版本，不复用旧“已完成”回执冒充已读取 50 位。

**后续确认：** A/B 每 7 天刷新、首次/到期任务公平排序、A/B 读取轮转及额度恢复已在 §9.6 确认；B 作者进入 OECID 队列的具体合同后续继续核对。

**实施状态：** 2026-09-25 已上线 A50、B 四市场隔离和持续读取，保留原自动运营开关；MY 当前关闭时不会自动开始。旧范围、新范围与验证证据见 [滚动队列交付](rolling-market-leads-20260925.md)。


### 9.6 Kalodata 滚动队列、排序与额度恢复（用户 2026-09-25 确认）

**目标：每天推进同一个持久队列，A/B 每 7 天重查；不是每天从头生成并重扫一份商品清单。** 任务加入、完成、等待额度、退出和恢复都保留原状态，不能由一次货盘工作流是否启动决定次日能否续查。

**任务与入队：**

- 按 market×PID×A/B 分开保存查询状态；一个 PID 可以 A 完成、B 仍在途。跨 Campaign/全托发现同市场同 PID 时，只要该 PID 有合格可用材料，不为同一类型重复查询；来源与实际材料绑定仍单独保留。
- 新商品可用 TapLink 就绪后，分别产生 A/B 首次查询资格；某类型有效刷新到期（7 天）时，再产生该类型刷新资格。重复发现、每日调度和进程重启不能重复入队。
- 同一 market×PID×类型只保留一个活动查询意图，冻结窗口、规则版本和稳定查询 ID；新一日不能覆盖旧任务的分页归属。任务同时保留首次就绪/刷新到期时间、最近有效完成时间、原窗口、页/游标、重试到期时间及必要 lease/fence。

**排序与 A/B 轮转：**

1. 各市场独立排队；同市场 A/B 轮流获得有界读取机会，不再要求先清空全部 A 才开始 B。一类没有可运行任务时，另一类可使用空闲机会；不为了形式对半保留而浪费额度，也不承诺 A/B 消耗相同数量的实际平台配额。
2. 在各类型可运行队列内，优先续未完成断点；随后按有效等待起点升序排列：首次任务取可用链接就绪时刻，刷新任务取满 7 天的到期时刻。新入队不永久压过旧到期任务。
3. 等待起点相同时，按已有商品销量降序、PID 固定顺序；未知销量按 0。这里的商品销量不是达人 GMV，不增加旧商品刷新请求来获得排序数据。达人候选内部的 A/B 排名规则不因读取队列轮转而变化。
4. 断点优先不等于让一个巨大视频任务独占全天：按有界页/请求片段保存进度、释放执行机会并轮转；同等可续任务公平轮转，不能每个片段都无条件重新领取同一项。让出不等于完成，不截断最终窗口覆盖，也不清空已保存页面。片段大小在实现验证时确定，不新增未经确认的每日视频读取上限。
5. 退避未到、账号不可用、材料明确失效的任务不占可运行队头；零任务或全部未到期时结束本轮，不靠重查未到期 PID 凑数。

**额度耗尽与第二天续跑：**

- 平台明确提示市场额度耗尽后，停止该市场新的 Kalodata 请求并记录等待额度状态；保留原任务、窗口、分页、已完成范围和队列等待时间，不把额度不足计作单商品失败，也不消耗商品技术重试次数。
- 已完整成功的 market×PID×类型结果可发布并进入后续身份流程；当前 PID 的未完整新结果不发布，已有上一完整投影继续按资格/有效窗口供消费。不能让永远有新任务的滚动队列成为必须全部清空的下游屏障。
- 调度器按平台实际额度周期安排恢复检查；额度恢复后自动续原未完成部分，不重读已完成商品，不要求人工操作，不等待新一轮 Campaign/全托采集到期才唤醒。不能假设北京时间零点必然重置；仍被明确拒绝时退避，不高频空查。
- 其他有额度且账号可用的市场继续，保持已有全局并发和账号锁。共享 Kalodata 登录失效与某市场额度耗尽分别处理，不能把认证失败误当所有市场额度已用完。
- 跨日仍续同一冻结查询窗口，不把不同日期范围的页面拼接。长时间中断导致窗口陈旧时，记录真实覆盖日期，恢复完成也不能称为当天最新结果；新窗口查询使用独立任务版本。具体陈旧阈值/到期锚点需在实现说明中明确，不能因每次失败/恢复而将 7 天刷新无限后移。

**退出、等待与重新进入：**

| 结果/条件 | 队列动作 |
| --- | --- |
| 完整成功，包含有效证据证明 0 位合格达人 | 结束当前任务，记录有效完成及窗口；等待下一次 7 天到期，不把 0 当技术失败连续重试 |
| 明确下架或不再有任何可用商品材料 | 暂停该 PID 的活跃查询，保留历史与断点；材料恢复后重新评估窗口和入队资格，不盲目复活陈旧任务 |
| 单商品暂时读取失败 | 保留原查询并退避，其他任务继续；失败不推进刷新成功时间、不重置原排队年龄 |
| 单商品持续失败 | 移出活跃队列、保留错误和证据，不反复消耗全天额度；自动再进入条件/尝试上限另行明确，不默认为删除或已完成 |
| 市场额度耗尽 | 市场等待额度，任务保留；恢复后自动续跑 |
| 用户暂停或账号故障 | 遵守已有授权/账号恢复合同，不以日常调度绕过暂停，也不将全部 PID 判失败 |

**产品显示与容量：** 每市场分别展示 A/B 待首次查询数、到期刷新数、断点数、技术失败隔离数、材料暂停数、最久等待/逾期和等待额度状态。每 7 天是到期目标，平台额度不足时不保证全部按时完成；必须让积压可见，不通过改时间或减少范围伪造完成。配额恢复时刻、A/B 真实请求成本、单轮处理量在实现验证中记录，不凭 PID 数假定消耗相同。

**与当前代码的差异：** `leads_queue.queue_items` 当前先全部 firstTime 再 due；`leads-run.py` 每次调用按当天重新计算窗口，只能在同 query/window 内复用页面；scheduler 先 A 后 IT B，且依附来源阶段推进。实施需补持久查询窗口、独立日常续跑、类型轮转、断点让出和局部完成发布；不是只修改列表排序。新规则仍复用既有台账/队列、claim 与证据，不另建平行事实源或重置旧任务。

**验收：**

- 新 PID 的 A/B 各只入队一次；A 完成后仅续 B，重启不重复；第 7 天到期前不重复查，到期后只产生一份刷新任务。
- 持续加入新商品时，等待更久的旧刷新不会被所有新商品插队；同等待时间按销量/PID 稳定排序。A/B 都有积压时，两类均获得读取机会，大 B 任务按片段让出后仍可续完整窗口。
- 查到第 100 个 PID 第 3 页遇额度耗尽：前 99 个完整结果可供后续消费，第 100 个未完整结果不发布；额度恢复后继续原窗口未完成部分，不重做前 99 个，排队年龄及尝试次数不因额度耗尽被重置。
- 一市场额度用完不阻塞其他有额度市场；仍未恢复时不密集请求；用户暂停时不自动恢复执行。没有新的货盘工作流时，已有队列也能按已授权日常调度续跑。
- 跨日/重启不混窗口、不重复导入、不清空上一完整结果；旧窗口过期不能伪装最新刷新。空结果记成功，技术失败/配额不足不记成功，单商品失败不占死队头。
- 商品无有效材料后不继续烧查询额度；新材料恢复按规定重新评估；库存变更/平台超时不删除历史线索。新迁移在旧库副本上幂等，保留已用额度证据、查询回执与原任务。

**实施状态：** 2026-09-25 已实施并加载。每片段最多 3 个请求、每阶段最多 8 片段，类型与断点/新到期项轮转持久化；7 天锚定原窗口开始，三次技术失败后隔离，7 天后或材料实质变化重新评估；额度按小时沿原任务检查而非假设零点。具体实现、旧数据迁移及运行验证见 [交付报告](rolling-market-leads-20260925.md)。


### 9.7 OECID 搜索不到后不再自动查询（用户 2026-09-25 确认）

**用户选择首次获得有效“搜索不到”结论后不再查询，否定了“隔 7 天补查一次”的建议。** 此决定针对平台正常返回但无精确 handle 匹配的 unresolved，不包括没有取得有效结果的技术失败。

- 保存 market、规范化 handle、原查询及其有效否定证据，作为可复用的已判定结果。相同市场同 handle 关联多个 PID、同时来自 A/B 或在新一轮 Kalodata 查询中再次出现，都复用原结论，不重复调用 Find。
- 不安排定时重查、不因服务重启/队列重建而重置状态、不把搜索不到变成人工待办。跨市场相同 handle 不能共用否定判定；更换 PID/来源也不能制造同市场新身份查询意图。
- 未取得 OECID 的线索不进入可发层，保留来源和未解析原因，不算解析成功。已成功解析的其他达人继续正常资格处理。
- 超时、验证码、签名、登录、接口错误等属于查询未完成，不得误记 unresolved。有限重试耗尽后自动跳过、不转人工已由 §9.8 确认；具体尝试/退避参数另行评估，不从本条推导为无限重试。

### 9.9 二发 A/B 份额（用户 2026-09-25 确认）

**每个市场的主动推品队列采用 A 类 80%、B 类 20% 的安排份额，替代 A 整体优先。** 按每 4 位 A 类后安排 1 位 B 类交替推进，不将 B 类留到当天最后。此比例独立于 Kalodata A/B 查询轮转，不是平台配额分配，也不改变机构新联系额度的计费/预留合同。

- 按实际领取并持久冻结的去重达人计一次安排，不按 PID、卡片/文字组件或回查次数计数。只扫描候选但未成功领取不消耗安排位置；恢复同一 delivery、补回读或重启不重复计数。安排数与真实确认触达数分开，不通过凑成功比例重发失败/未知意图。
- 根据领取时符合资格的候选判断 A/B；同达人当前同时有 A/B 合格位置时归 A 并选其最优 A 位置，不能将其 B 位置重复领取以占用 B 份额。仅有合格 B 位置时可进入 B 队列。原来源视频/销量证据保持，份额分类随冻结投递保存，回查不因后续分类变化改账。
- A 类内部按商品关联 GMV、销量及既有稳定排序择优；B 类按代表视频播放量、发布时间及既有稳定排序择优。只从通过身份、材料、关系、冷却、模板、窗口与平台容量门禁的候选中领取，不为比例降低资格。
- 一类没有可发达人时，另一类补位，避免空闲；记录实际类别和补位原因。补位不累积跨日必须偿还的发送欠额，不能为了“补足 B”突发发送或突破额度；两类恢复都有候选后按正常 4:1 轮转。
- 各市场持久保存安排类别、轮转进度及对应投递引用；同一天进程重启、控制页刷新或 worker 切换不重置为连续 4 位 A。领取与份额记账需幂等，多个执行入口不能并发各自发出一份“20% B”。实现时明确日界与在途任务归属，跨日核验不得重复占份额。
- 小样本、窗口关闭、额度耗尽或一类不足时，实际比例不一定精确为 80/20；这不是失败，不新增发送来强行凑满。两类都有稳定供给时按领取序列验收 4:1，同时另报各类确认、部分送达、拒绝及未知结果。

**取舍与观察：** A 充足时将一部分安排机会留给 B，优先级最高的 A 可能晚些被联系，换取 B 类稳定机会。分别统计 A/B 去重安排、确认触达、回复及加橱窗表现；效果归因须遵守同范围与事件去重口径，不能直接用消息条数评价两类效果。

### 9.10 同达人主动推品冷却（用户 2026-09-25 确认）

**继续保持同市场同达人主动推品至少间隔 72 小时，一次只推最优一个商品。** 同一达人关联多个 PID 时其余位置等待，不能按商品分别计算冷却，不能通过 A/B 份额分配、换商品或重新入队连续推送。

- 已回复或已加橱窗不缩短主动推品冷却；人工客服和针对新来信的正常回复不套用主动推品的 72 小时限制，但仍遵守各自授权、窗口、事实与写入门禁。
- 冷却到期仅恢复被检查的资格，不直接放行。拒联、人工接管、待处理来信、未结发送 unknown、无有效商品材料或消息额度不足等仍阻断；事项解决后重新计算。
- 已有确定性冷却口径在池投影、领取前复检、逐次平台写门禁中保持一致；保留部分送达及平台已观测外发参与冷却的既有规则，不因新排队方案重置最后联系时间。已提交未知独立处理，不靠过 72 小时变成可重发。
- 示例：周一联系达人推广甲商品，即使还有乙/丙候选，也不能当天连续推送；最早满 72 小时后再检查是否可选其他合格商品。此规则不是每 72 小时必须联系一次，也不授权重复发送同一已处理商品。

**验收：** 多 PID、A/B 交叉、重启或来源刷新均不能绕过同一市场/OECID 的冷却；不足 72 小时拒绝主动推品，满 72 小时仍执行全部其他门禁；回复/加橱窗不提前放行主动推品，新来信服务不因该冷却被阻止。池展示、候选领取和最终写门禁使用同一计算方式。

**实施状态：** 确认保留既有业务规则，只更新文档，不修改生产授权或启动发送。发送窗口、额度及发送 unknown 的后续确认见 §9.11–9.12。

### 9.12 二发未知有限核验后自动隔离（用户 2026-09-25 确认）

**二发中建会话、商品卡或文字结果未知，有限核验后仍不明则自动隔离该次投递，不转人工，其他合格达人继续。** 用户接受可能只送达部分邀请或错过一次联系机会，以避免重复发送、长期阻塞整个市场及逐条人工核查。

| 未知位置 | 保留与禁止动作 |
| --- | --- |
| 建会话无回执 | 保留原申请与账号/目标达人，不能重新建会话，也不能猜 CID 继续发卡文 |
| 商品卡已提交但未知 | 保留原卡意图；不重复发卡，不假定卡已收到后继续发配套文字 |
| 卡已确认、文字提交后未知 | 保留卡的成功证据和文字未知；不重发整套邀请，不重复提交文字 |

- 核验只使用原 market、账号、达人身份、会话和请求引用；已知回执精确匹配才确认。历史读取失败、列表截断或暂时没有找到消息不能证明未送达，不能改判 failed_known。
- 先完成有限只读核验，仍未知时把原投递置于有记录的隔离处理状态，组件结果继续保持真实的 confirmed/unknown/未提交；隔离是队列处置，不是平台结果结论。记录隔离原因、核验次数/时间及证据缺口。
- 隔离后不建立必须由用户完成的人工待办；暂停该达人的后续主动推品，不能换 PID、账号、文案或等待冷却结束后绕过。其他合格达人继续按窗口、额度及份额发送，收信仍正常运行。
- 已隔离原投递释放的是其对其他达人的队列阻断，不放宽账号写入互斥、lease/fence 或未停止执行器的并发要求；本地原提交尝试结束后才可释放对应执行资源，不让迟到旧 worker 再次提交。
- 以后正常收信若获得与原意图精确匹配的可靠证据，可以幂等结算原组件。仅凭达人回复、存在同 CID 或相似文字不能认定卡文都成功；结算不自动补发原来未提交的组件，也不自行解除拒联、人工接管等其他限制。
- 收信继续不等于本次同时授权 AI 对该隔离达人回复；新入站如何处理、何时允许解除隔离后再次主动联系，需在会话/AI 模块明确。既有人工案件保留，不批量结案，不将业务投诉等人工事项改成技术隔离。
- 参数分三类评估：建会话、卡片、文字分别定义有限核验次数、时限、可用证据和停止条件；不照搬 Campaign 的 3 次/5 分钟。已有卡片两次成功读历史且间隔 ≥5 分钟的缺失证据保留，不把读取失败凑成缺失次数；新的耗尽隔离政策不需要谎称已确认未送达。
- 重启、下一窗口或跨日不得重置核验进度、重复创建隔离记录或重新提交原消息。隔离后不以“还有 unknown”继续要求用户处理；汇总可展示技术隔离数，但不能变成阻塞其他发送的人工工单。
- 明确拒绝、额度耗尽与结果未知分别处理；业务码 201 等有明确拒绝事实的情形保留原分类，不因统一隔离入口丢失平台回执。AI 回复自身未知按后来独立确认的 §9.18 处理，不与二发意图混用。

**实施验收：** 分别注入建会话无回执、卡未知、卡已确认文字未知；有限核验无结论后自动隔离，无重复 POST，无人工必办任务，其他达人可继续。原达人换商品/跨日/满 72 小时仍不能绕过阻断。历史不可读保持未知，精确迟到回执只结算原组件，达人普通回复不能确认全套成功；收信不停止，其他人工接管不被解除；崩溃重启与并发核验不重复隔离/发送；窗口、额度、账号互斥和 frozen 意图合同不因隔离放宽。

**实施状态（2026-09-25）：** 本批已接入四市场正式二发的有限只读核验与营销隔离、共享执行锁、迟到组件确认不重开投递、发送池/状态接口区分技术隔离。沿用既有表追加核验记录，无需重建或迁移业务行；原人工案件与关系不清理。建会话 2 轮、每轮 180 秒/最多 101 页；卡/文各 3 轮、每轮 90 秒；轮间至少 300 秒，首次专项核验起总期限 900 秒。计数在读取前持久化，首次正常发送的即时回读不计专项次数。卡片两次成功历史缺失的旧标准仍可提前隔离；预算耗尽是停止跟进，不是“不存在”证明。新非 IT 投递补充冻结发送账号和 IM 身份，旧投递按原固定账号兼容并拒绝换号。原卡文邀请遇入站的例外仍按 §9.13 单独实施，不能由本批推断已完成。验收与真实 UK 原意图收口见[交付报告](delivery-isolation-20260925.md)。


### 9.13 收信与当前卡文邀请的衔接（用户 2026-09-25 确认）

**用户选择：卡片已发送并确认、配套文字尚未发送时，即使收到达人来信，也允许把这一套原卡＋原文字发完。** 不选择“任意新来信就取消剩余邀请文字”。这只改变当前投递的来信打断规则，不开放后续商品连续推送。

**收信方案参考依据（只读核实，非迁移完成）：** 用户要求基于旧版 BDHub 成熟收信机制叠加业务规则。旧项目 `bdhub/monitor/__main__.py` 的 SDK 实时回调（671–703）、会话变化补读（1020–1152）、独立限量深层历史恢复（1155 起）及 resident（1997 起）构成主路径：先挂回调、成功落库再 ACK，按活动变化/未读补读，历史缺口保留断点和退避。它不是把全部旧会话持续重查。默认 5 秒处理实时缓冲、30 秒变化检查、20 分钟重载会话元数据；非未读补读受限，历史深拉每轮最多一个。以上为源码默认机制，不是本次生产实测延迟保证。

应复用其消息不丢、精确去重、断点与有界补读的设计，再适配本项目市场身份和台账。旧版常驻浏览器 SDK 与当前 HTTP 收信/发送的账号租约方式不同，不能直接启动旧监听器或让其写旧 PostgreSQL 接管四市场。账号所有权、接收传输、我方消息/橱窗识别、本地待回复状态及消息覆盖验证需单独设计；旧版外部联系方式/自动回复业务规则不随收信机制一起复制。

**业务衔接：**

1. 收信持续保存新消息，与“是否现在调用 AI 回复”分开。正常新来信进入该达人的待回复队列，不启动一轮即时 AI 回复来抢占二发时段；沿用已经保存的独立回复窗口与二发缓冲，不在本次改具体时间。
2. 对尚未开始的后续推品，该达人所有 PID 暂停领取，直到来信处理后重新判断；其他达人继续发送，不能把该达人的 pending 当成全市场暂停条件，也不能在队头反复领取同一个被阻断的人。
3. 对当前已确认卡片、尚未提交文字的冻结投递，允许发送原文字完成邀请。market、账号、达人、CID、PID、Offer、原正文与 requestRef 不变，不换文、不加新商品、不重新发卡。
4. 这个例外仅忽略“本次新来信”造成的当前邀请打断；显式 stop、窗口结束、投递过期、已确定的拒联/人工接管、材料失效、消息容量不足或发送 unknown 等仍按原合同处理。卡片未知时不发配套文字，文字已提交未知时只核验，已取消/已隔离投递不因此恢复提交。
5. 配套邀请文字发完不等于已经回答新来信。原 pending/入站 turn 保留，到回复窗口读取最新上下文集中处理；收信或重启不能因最后一条变成我方配套文字就把达人问题自动结案或永远跳过。
6. 我方人员在机构后台实际回复过该入站时，AI 避免重复回答，沿用真实我方消息识别；必须区分“当前二发的配套邀请正文”与“对这次入站的人工/客服回答”。不能仅以我方消息时间晚于入站就一概判断已回复。
7. 待回复处理完也不直接恢复主动推品，仍需核对 72 小时冷却、关系、有效材料及原未知/拒联等限制。新来信对已隔离投递的后续 AI 服务资格仍需单独确定，不从当前邀请例外推导全面解除隔离。

**实施前问题与改造要求：** 原 `cycle_delivery.interrupted_by_inquiry` 会在卡确认、文字未开始且存在 inbox_pending 时取消文字；`cycle_inbox` 入站会更新关系 revision/inbox_until，逐写资格也会检查这些字段。实现不能只删取消分支，也不能无条件忽略关系 revision：须证明变化仅来自该入站，并对同一冻结投递给予狭窄例外，其他控制变化仍阻断。IT/其他市场两条执行路径都要覆盖。同时检查 `observed_messages`/`pending_rows`/会话 unread 与 Agent 上下文的“机构已回复”判定，防止原配套文字误抑制未回答来信。

**验收：**

- 卡确认→达人来信→原文字仍可在既有门禁允许下提交并核验；整套只发一次，随后不再向该达人领取另一 PID，其他达人继续。
- 原文字发送后，达人待回复状态仍在；回复窗口能看到真实卡、原文字与插入的达人问题，不把配套邀请当成客服回复。
- 若人工实际回答过该入站，AI 不重复答；新一条达人来信仍可进入判断。多条来信、同时到达的消息和重启不丢 turn、不重复发送。
- 卡未知、文字未知、窗口关闭、stop、过期、显式拒联/接管、材料变化及容量不足均不能借该例外放行；改变冻结正文/账号/requestRef 被拒绝。
- 单达人 pending 不阻塞其他发送；当前文字不因任意历史已处理 pending 行而误取消；领取/预检/逐写对上述例外一致。

**取舍：** 允许当前邀请完整发送，接受达人来信之后仍可能收到已经准备好的邀请文字；真正针对来信的回复留到独立窗口。并非承诺即时响应，也不以此扩大用户已确认的窗口或发送次数。

**实施状态（2026-09-25）：** 已在四市场正式发送路径实现“卡已确认→实时入站→原文字”的窄范围继续规则并加载。复用原核验台账保存入站版本链，逐写校验原账号/会话/冻结内容；手工控制变化、unknown 和原其他门禁不放宽。首次收信基线改为同会话已确认卡的开始时间，待回复/未读不被邀请文字清除；真实 Agent 上下文仅增加同套已确认邀请，默认 replay 保持时间截断。schema v24 只确保原表和查询索引，不改旧消息/冻结意图。

凭证只在摄取实时入站时原卡已确认的顺序下产生；入站先入库、卡后确认未放宽，旧取消/隔离不复活。该批发布时 HTTP 收信使用原热点与有界补读；2026-09-26 SDK 接收适配已按 §9.22 上线，见[四市场上线报告](sdk-http-rollout-20260926.md)。§9.14 集中回复、完整 live/replay 上下文、隔离达人服务资格仍属后续，不宣称整个 AI 优化完成。测试、生产加载及自然案例观察边界见[交付报告](invitation-inbound-20260925.md)。


### 9.14 集中回复队列排序与多条消息合并（用户 2026-09-25 确认）

**在独立回复窗口集中处理，按达人最早一条尚未处理来信排序；同一达人多条消息合并理解。** 接收和保存消息持续进行，回复窗口不开时只积累待办，不插入二发时段调用发送。

- 各市场以稳定达人身份维护一个当前待回复事项，保存未处理入站范围及最早等待时间；同一达人连续发消息不生成多个相互竞争的回复，也不刷新其排队年龄。排序相同用稳定身份/消息顺序确定，不以不断发新消息获得插队优先。
- 轮到该达人时读取最新真实对话，将该轮尚未解决的问题一起交给模型判断，按实际问题合并回复；不是逐条消息逐条生成，也不能只看最后一句而遗漏前面的问题。
- 人工或已确认的客服回复已经处理的入站不重复回答；其后的新问题仍保留并进入判断。只按已处理范围推进水位，不能一次清空此达人全部 pending。按 §9.13 继续发送的二发配套文字不算对入站问题的回答。
- 已开始生成但尚未提交期间若有新来信、人工出手或关系变动，发送前复核入站水位/pending/control revision；旧草稿不盲发，回到最新上下文重判。已提交的正文与请求保持冻结，后来的新问题另留待办，原回复结果未知先按原意图核验，不换文重复发送。
- 回复窗口结束停止新的回复提交，剩余未处理事项连同等待时间保留到下个窗口，不清零、不挤占二发时段。已提交在途结果按既有收口/只读核验合同处理，不把窗口结束解释成失败后重发。
- 排序针对当前可自动处理的事项；人工接管、等待达人补资料、技术退避或未知核验等不能一直占住队头，使其他可处理达人空等。保持各自状态，不把这些等待误当已回复。
- 当前一轮处理完后，如果后来又有新来信，从新一轮最早未处理入站重新计算等待时间。保留历史处理与回执，不把很久以前已处理消息拿来抬高新问题的优先级。

**实现关注：** 当前 `run-agent-replies.pending_rows` 按 inbox_pending.due_at 排序，收信会更新 due_at；需验证并保留独立的最早未处理入站依据，不能直接用每次更新的 due_at 代替等待年龄。复用 turn、pending revision、真实外发与服务处理水位，不另建平行对话真相。合并回复需保存覆盖的入站范围，确认时只结算该范围，生成/提交期间的新消息不得被吞掉。

**验收：** 达人甲较早发问、之后不断补充，仍按甲最早未处理时间排队；其他达人不因重复消息重复排队。一次回应覆盖同一轮多个未解决问题，人工已答旧问题不再答、新问题保留；配套邀请文字不误结案；生成期间新消息触发发送前复核，已提交意图不改文；窗口结束后翌日原等待年龄与断点保留；并发收信/确认及重启不丢消息、不重复回答、不解除不相关人工/拒联状态。

**实施状态（2026-09-25）：** 四市场集中队列已按原始未处理来信时间排序，连续补充不刷新年龄；同达人当前未处理消息全部进入一次决策输入，冻结精确 CID/messageId/contentHash 范围。生成应用与逐写复核；确认/no_reply 只记录覆盖版本并推进连续已处理水位，新增/编辑消息保留，已答版本不重复入队，人工控制不被收口覆盖。新本地 input_blocked 不调用模型，保留过长问题并让其他人继续，未实现自动分段。schema v25 增量回填既有 cursor 已处理证据，旧回复意图/人工案件不重写；同批补齐查询索引改善会话读取。详见[交付报告](reply-scope-queue-20260925.md)。

真实 worker 使用当前本地上下文，默认目标时刻回放保持原兼容；长期提醒记忆、完整历史状态回放、技术错误分型/通道退避和 AI unknown 有限核验仍按后续推进，不把本批称为全部 AI 方案完成。窗口、商业回复内容和全量授权不变；§9.17–9.19 的后续范围继续保留。

### 9.15 继承此前已确认的 AI 回复场景（2026-09-25 回查确认）

- 四市场使用各自固定语言，基于真实前后文自然组织回复，参考答案约束业务含义，不要求机械逐字发送。

**本轮新方案的边界：** §9.1/9.3/9.8/9.12 中的“不转人工”是对应技术失败或未知处置规则，不取消固定报价、真实联系方式、卡异常等已确认的商业人工交接。§9.13–9.14 调整当前邀请收口及集中回复调度，也不改变上述场景权限。这些运行衔接随后已在 §9.17–9.21 确认，不能据此重新打开全部内容政策。

### 9.17 AI 模型调用失败：有限尝试后自动跳过（用户 2026-09-25 确认）

**适用范围：模型没有成功生成可用回复，尚未因本次生成向达人发送消息。** 同一明确输入最多尝试 3 次，包含首次调用；不是首次再加 3 次，也不是平台回复发送重试。

- 模型超时、临时网络等可恢复故障退避后自动重试，其他可处理达人先继续；单项不占死队头。重试服从独立回复窗口，具体间隔按错误类型在实现时明确。
- 输入过长、缺字段等可确定的本地问题先按上下文/结构合同处理，不原样反复提交必定失败的请求。必要上下文不能完整容纳时记录真实技术缺口，不能删掉未答问题后宣称处理完成。
- 尝试耗尽后退出活跃回复队列，不转人工、不建立用户必办任务；记录“AI 处理失败”，保留未回答消息范围、等待时间、输入版本和尝试证据。不能伪装为 no_reply 或 answered，也不解除该达人的待回复主动推品限制。
- 第二天、worker 重启、模型服务恢复及无关时间字段变化不自动给相同失败输入重新分配 3 次。输入身份由真实待处理消息范围、有效上下文/规则版本等定义，不用每次运行时刻制造新 hash 绕过预算。
- 后来该达人发来新消息，形成新的真实上下文时可以连同原来未回答的问题重新判断；原失败与成本保留，新事项不遗漏旧问题。不因收到同一 messageId 的重复事件重置状态。
- 多位达人连续发生同一种模型服务故障时，暂停该服务调用并退避，避免依次耗尽每位达人的预算；已发生的真实调用如实记录，暂停期间未调用不计作每人的失败。服务恢复后继续尚有尝试资格的事项，不复活全部耗尽项。
- 平台已提交回复的 unknown 按原意图核验，不能套本条再生成/发送另一份回复。商业 handoff 也不能因模型故障或技术跳过自动撤销原案件。

**接受的取舍：** 个别来信可能暂时没有得到回复；用有限自动处理避免少数异常反复消耗调用或拖住其他达人。界面保留技术失败数量和原因，不把它们包装成已经处理的业务结果或必须用户接手的商业待办。

**验收：** 同输入最多 3 次实际模型调用；重启/跨日/重复事件不增加预算；等待窗口和服务级暂停不消耗未执行尝试；本地确定性无效输入不反复外调；耗尽项退出活跃队列且保持未答事实与推品阻断，其他达人可继续；新入站形成新上下文时能携带旧未答问题，原平台送达未知不因新输入重发。

**实施状态（09-26）：** 同输入三次限制、持久退避、未答范围和超长输入零调用已具备；错误分型、服务级退避、耗尽展示仍待实施。平台 AI 回复 unknown 的隔离仍见 §9.18，不能把模型生成失败与平台未知共用预算。


### 9.18 AI 回复送达未知：有限核验后隔离（用户 2026-09-25 确认）

**适用范围：AI 回复已向平台提交，但尚不能确认是否送达。** 这不是模型生成失败，不能重新生成一句近似回复或使用新 requestRef 再发。

- 只沿原 market、账号、达人、CID、正文和 requestRef 做有限只读核验；具体次数、间隔、总预算与回复接口能力一并评估，不直接继承 §9.17 的 3 次模型调用或 Campaign 的 5 分钟。
- 有可靠且精确匹配原意图的消息证据则正常结算。核验耗尽仍不明，自动技术隔离该次回复，保留真实 unknown 及核验记录，不改判成功/明确失败，不产生新的用户必办任务。
- 隔离后该达人的自动回复与主动推品暂缓，新的来信照常接收、保存，不把它们标记已答；其他合格达人继续，不能由隔离后的单个回复占住整个市场队头或模型前门禁。
- 未来正常收信获得精确原消息证据时，幂等结算原结果；达人说“谢谢”、存在同一会话或相似文字都不足以确认送达。只有消息归属和原意图匹配才推进原覆盖范围；新问题及其他拒联/人工状态不被顺带清除。
- 如果未知的是商业转人工确认消息，原 case 与人工接管继续有效；技术“不转人工”只是不新增技术故障工单，不能撤销已经需要人工处理的报价、联系方式、卡异常等业务事项。
- 重启、跨日、窗口重开或又有新来信，都不自动重新发送原消息，不给已隔离意图重置有限核验预算。该达人待处理新入站保留，不能套用“模型失败后新输入可重试”绕过已有外发 unknown。
- 当前正在执行的本地写操作仍按账号串行与 lease/fence 收口；只有历史未知的队列阻断可按已确认隔离状态释放。不能在原执行器尚可能继续提交时并发新写。

**接受的取舍：** 某位达人可能未收到答复且其后续自动服务暂缓，但其他达人可继续；以避免近似回复重复发送和全市场长期堵塞。原始来信、冻结正文、人工事项及证据均保留，技术隔离不计为业务已解决。

**验收：** 原回复超时/无回执只触发原意图读取，无新增正文/请求；有限核验耗尽后无技术人工待办且其他达人继续；该达人新入站仍入库但不绕过隔离自动发送；精确迟到证据仅结算原范围，普通“谢谢”不能确认；商业 handoff 案件与其他接管状态保留；重启/并发核验/跨日均不重发或重置预算；窗口外核验不能顺带开始新回复。

**实施状态：** 仅文档确认。当前 service_reply 和 reply_blocker 的隔离状态/范围需增量适配和迁移兼容验证；尚未修改生产代码、数据库、窗口或进程。仅被二发技术隔离的达人主动提问，按随后确认的 §9.19 提供受限 AI 服务。


### 9.19 二发技术隔离后允许服务新来信（用户 2026-09-25 确认）

**仅因二发邀请结果未知而被技术隔离的达人，后来主动提出新问题，可以由 AI 在回复窗口提供服务；主动推品继续禁止。** 这不是解除原投递隔离，也不是把原未知结果改成成功。

- 收信保存新消息后，按集中回复队列处理其真实问题，使用原有市场、身份、已确认指南和授权；不因隔离例外即刻在二发窗口回复，也不绕过原 pilot/full 持久控制。
- 模型输入明确区分已确认和未知的原卡/文字证据；不能假定达人看过某卡/正文，不能以“你已经收到”作为回答前提。问题信息不足按既有澄清规则，不通过补发原卡或生成另一份邀请解决。
- 原二发意图、requestRef、组件结果及营销阻断保留；服务一条新问题不自动放行该达人其他 PID，不重置冷却，不重新排入主动发送队列。
- 若同时存在明确拒联、商业人工接管，或 AI 回复本身仍有送达 unknown，继续受相应限制，不适用本例外。原商业人工 case 不因技术隔离标记而清除；服务过程新遇付费、联系方式、卡异常等人工事项，照既有场景政策交接。
- AI 服务产生的回复按正常唯一意图、发送前复检及回执核验执行；如果该回复又送达未知，按 §9.18 处理，不以不断出现新来信绕过它。
- 实现中区分 outreach 技术隔离与商业 human/rejected、reply unknown，派生当前允许的动作，不另建一套相互矛盾的关系状态。不能简单把 human 改回 auto 来放行，也不能忽略真实人工案件。既有历史隔离/case 的兼容需逐类核对，不批量解锁或结案。

**验收：** 仅二发技术隔离＋新问题时，回复窗口内可生成并发送服务回复，原营销阻断和未知证据不变；无新入站不主动回复；窗外/无授权不外发；拒联、商业人工接管、AI 回复 unknown 任一存在时拒绝本例外。上下文不把未知卡文当已送达，服务不会补发旧邀请，新的商业交接和服务 unknown 均按各自规则执行。

**实施状态（09-26）：** §9.17 已有三次上限/输入预算等基础，完整失败策略仍未实现；§9.18–9.19 的 AI unknown 隔离和新来信服务许可仍待实现。核验参数与迁移切换须单独验证，不能因为四市场 AI 已全量授权就视为这些策略已经上线。


### 9.20 账号维护与掉线恢复（用户 2026-09-25 确认）

**统一恢复、保留断点与授权，只暂停依赖故障账号的新操作。** 账号正常时沿用现有定期维护，不因偶发请求错误反复重登，不新增各业务各自运行的恢复循环。

| 触发/状态 | 系统动作 |
| --- | --- |
| 正常使用或定期维护到期 | 沿既有维护任务与账号锁执行，不让频繁健康探测抢占业务资源 |
| 业务请求明确返回登录失效 | 自动尝试刷新；刷新失败再尝试本账号有界重登 |
| 多条业务同时发现同账号同代次失效 | 合并为同一恢复意图，其他调用读取该任务进度，不各自重登 |
| 正在恢复 | 暂停该账号新的请求，保存业务断点/意图；其他可用账号和不依赖该账号的工作继续 |
| 恢复成功 | 发布经验证的新身份代次，重新核对原授权、暂停、窗口、能力和任务状态后继续原工作 |
| 平台必须人工验证且自动流程不能完成 | 停止重复尝试，账号页明确显示需要验证；不批量把商品或达人写成失败 |

- 超时、网络异常、签名或普通业务拒绝不能一律当登录失效。失败证据保留脱敏错误分类和平台码，恢复必须针对原市场/账号/角色，不错误刷新成另一个通讯账号，也不换号重放未知写入。
- 沿用现有维护意图、身份代次、lease/fence 与 profile/写入锁。当前原子操作按既有合同收口，明确正在提交的请求不能因为登录恢复而强制换身份后重新发。
- 多业务共享去重应同时覆盖主动定期维护和故障恢复入口；同代次已存在恢复任务时复用，不因换调用方、请求名称或 worker 重启重复登记。失败/需验证状态不能在每个 tick 被无限重新执行。
- 恢复成功不自动开启暂停市场、二发或 AI，不将未验收能力直接设为 verified；原外部结果未知继续只读核验原意图，已完成任务不重做，未完成任务续原断点。
- 恢复失败保留上个身份代次与证据用于诊断/恢复，不把已明确失效的旧身份继续当健康可写使用；其他可用账号可继续其原职责，不以替换账号规避原意图绑定。
- 账号需要人工验证是平台无法自动完成的必要动作提示，不等于把所有受影响业务对象变成用户待办。暂缓对象、恢复原因与恢复后下一步在账号状态中汇总。
- 本次确认不涉及迁移密码存放方式、复制旧凭据、启停旧项目生命周期任务、修改账号分工或移除 IT 旧写门禁；这些仍保持项目边界，实施只在本项目内完成。

**验收：** 收信/OECID/发送/回复同时报同账号同代次失效，只出现一份恢复意图；定期维护与故障恢复不重叠操作同一身份；刷新失败能转到有界重登，必须人工验证后不会每轮再尝试；普通网络/业务拒绝不触发无意义重登；其他可用账号继续。成功恢复不改授权、不重发 unknown、不复活停止任务；失败不清除断点或把所有商品/达人判失败，市场、账号角色及能力状态不串用。

**实施状态（09-26）：** 原定期维护、项目自有代次、通讯账号同代次一次恢复和供给 OECID 恢复已接入；`login_recovery` 仍固定 communications，OECID 从 scheduler 选择角色，所有模块统一请求键与认证分型尚未完成。SDK owner 在维护前排空借用客户端，真实维护/写入交错仍需验证。


### 9.21 整体调度与首页反馈（用户 2026-09-25 确认）

**调度持续领取条件满足的工作，失败/等待按真实影响范围处理；首页优先呈现已处理、正在等待、真正需人工三类。** 有真实上游依赖仍须等待，不用“不断运行”掩盖材料缺失或未完成输入。

| 情况 | 调度行为 |
| --- | --- |
| 单商品/单达人失败或未知 | 按对应已确认策略有限处理、跳过或隔离；其他合格对象继续，不误将跳过计为成功 |
| 某账号维护/恢复中 | 等待依赖该账号的任务；其他可用账号按原职责继续，不换号重放原未知写入 |
| 某市场 Kalodata 额度耗尽 | 该市场查询等待额度；已完成范围及其他可运行市场/模块继续 |
| 来源发现尚未到期 | 不重复采集；已有线索查询、身份、发送、收信和到期维护按自身条件推进 |
| 滚动队列持续有新增工作 | 已完整发布的范围可以进入下游，不要求整个市场所有滚动任务清空 |
| 上游身份/材料/范围尚不完整 | 对应对象等待，不强行生成完整 generation 或越过资格发送 |
| 用户明确暂停 | 保持授权和暂停边界，不因其他任务结束、跨日或部署而自动恢复 |

- 去除 scheduler 按领取批次等待最慢任务才再次调度的限制；已完成任务及时结算，符合上游和资源条件的新任务及时领取。保留同市场/账号互斥、平台全局槽、Kalodata 并发上限、短事务 claim、lease/fence、真实子 PID 及父死子活合同，不以增加并发掩盖调度缺陷。
- 各模块到期时刻、队列、范围发布和断点独立持久化，scheduler 负责连接依赖。一个模块空队列/未到期不阻止其他模块；但不能重复启动存活 worker，不能重复发布同一完成范围或用新 run 掩盖旧未知。
- 旧 needs_human 不能仅靠改状态整体放行。先辨认其原因和领域范围，按已确认策略完成隔离/恢复，再判断无关任务是否可运行；旧 head、来源和未结写入继续精确绑定。全托尚未完整的类目扫描仍按 §9.2 的覆盖合同处理，不因滚动队列策略自动获得部分类目发布权限。

**首页三类反馈：**

1. **已处理：** 新增合格 PID、当前有效链接、可发达人、确认触达、已回复等；标明统计时点/范围，当前库存与每日事件分开，不把平台写入次数或 worker 存活当业务完成。
2. **正在等待：** 下次刷新、真实额度、发送/回复窗口、账号恢复、缺材料、用户暂停等；说明受影响市场/对象、已知下次动作和等待年龄，未知恢复时间不猜。
3. **真正需人工：** 平台必须人工验证，以及既有商业场景明确需人工决定的事项。自动技术隔离、重试耗尽等展示数量/原因并可展开，不混入必须由用户处理的待办，不掩盖真正商业人工案件。

保持现有页面告警条渠道，不新增飞书/系统通知。自动处置后的历史 unknown 行不能让首页永远显示全市场堵塞；仍有真实共享账号故障、未知在途写、数据不完整等约束时如实显示影响范围，不能宣称已恢复。一个市场读取失败只标该市场不可用，不把缺失显示为 0。

**验收：** 一个长阶段运行时，另一满足上游/资源条件的任务可以进入，不等待整批；有真实槽位占用时不超并发。有失败对象/额度暂停市场时，其余完整可用范围继续下游；新来源未到期时既有队列仍能日常续跑。重启、迟到结果、重复 tick 不重复领任务/发布结果/写平台。页面的已处理、等待及人工分类均可追到原台账，与真实阻断范围一致；技术自动处置不变成人工工单，人工案件不被统计隐藏。当前投影、每日事件和转化归因不混算。

**实施状态（09-26）：** 只读三类概览、scheduler 在长任务期间补领、B 投影逐 PID 发布已实施；所有领域统一恢复、完整等待解释与历史问题分类仍未完成。当前实现见本页实施表和 TECHNICAL，不把初次确认时的“尚未改造”作为当前结论。

### 9.22 双账号通讯与供给分工（用户 2026-09-26 确认并要求四市场上线）

通讯账号同时负责 SDK 收信与原 HTTP 发信；供给账号负责 Campaign、商品、TapLink、OECID。固定账号 IT acc6/acc9、BR acc1/acc2、MY acc8/acc5、UK acc11/acc4，不使用 SDK 替代 HTTP 发送，不换号重放未知消息。原窗口和持久授权继续，MY 主链原开关不变。

一个通讯会话负责人持原 ProfileLease，接收独立运行，原发送/AI 通过私有 IPC 借用同身份；SDK 通知先落持久唤醒，再由原 HTTP 合同验证消息身份与正文。初始化回放去重，断线期间保留原发现/有界补读，维护先收口原 HTTP 请求再释放身份。供给 OECID 必须先有该账号真实 Find 验收，旧报告按原账号恢复，技术预算与成功身份保留。

验收区分代码与自然业务：四市场身份/会话匹配、无重复 owner、SDK 成功状态与续期、并行 HTTP 回查、原授权/消息请求不变；Find 四账号逐一核对；真实发送和新来信延迟只按实际观察记录，不用初始化回放或测试通过代替业务送达。上线与保留消息的回退见[交付报告](sdk-http-rollout-20260926.md)。
