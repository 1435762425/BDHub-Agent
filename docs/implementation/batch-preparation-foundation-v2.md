# B.17 全量批次准备基础与TapLink门槛

实施日期：2026-09-14。用户已确认TapLink纳入并要求开始实施。当前设计基线为[PRD](../PRD.md)和[批次架构](../architecture/batch-outreach-v2.md)。历史研发文档归档，AGENTS/README改为精简的当前入口；手动暂停AI回复明确保留。

## 本轮交付

- `scripts/lib/batch_tasks.py`：固定整数目标、约10%候补、商品范围、北京时间/开始日期、跨午夜窗口、任务确认哈希/幂等、准备成员与修订审计、全量材料门槛、显式部分放行、同机构市场排队判定、人工回复暂停优先。
- TapLink检查是每名正式/候补成员准备条件之一；同一材料可服务多个OEC，不能用一张卡的成功代替所有材料成功。同OEC不能重复填目标。补齐材料时需版本匹配；冻结后不能直接改成员。
- 该基础模块不调用平台，`can_start`仅给阶段资格，始终返回`platformDispatchAuthorized=false`；还没有新的真实任务执行器、目标发送名额预留或回执结算适配。不得将其当作上线验收。
- `scripts/inspect-batch-preparation.py`及`lib/batch_preparation.py`读取新项目真实IT库，按当前本地商品/身份/关系来源去重，检查本次目标＋候补的名单、短名与具体TapLink记录缺口。不会创建任务、建卡、发送、调用模型或修改旧系统。
- `/api/batch-preparation`仅本机同源POST `{target:整数}`，不接受执行命令、账号或路径。外部来源、模糊目标、伪装可发送的子进程结果均拒绝。
- 工作台新增只读批次准备预检，一发/二发分栏，一发V2状态明确；既有实测批次保留独立区域。商品明细折叠，速度改为完整卡文确认曲线，区分速度目标达成与批次目标数量。
- 修正二发页面仍显示“真实发送尚未开放”的历史文字，以及回复已暂停时仍显示“正在自动回复”的误导文案。

## 验证与事实

- 新任务与预检12项Python测试、接口3项Node测试通过。覆盖3000/5000、候补全量门槛、缺TapLink、同人去重、材料版本补齐、确认重放、跨午夜开始日期、scope排队、暂停回复优先及本地读取不授予外部动作权限。
- Next.js构建通过；仅更新5198本机Web，旧BDHub服务和数据库未改。
- 真实CLI预检3000人目标计算3300要求，单轮本地候选9人、8个材料方案；随后浏览器读取到13人/11个方案、候补300、名单缺口3287、1个短名和1个TapLink记录待补。不同时间数据变化来自原有供给Worker继续运行，不是假样本。
- 浏览器实际点击“检查准备条件”，返回TapLink明细与“尚未放行发送”，且明确未创建任务。无外部发送或建卡由预检触发。
- 页面截图核对了准备面板、折叠材料明细和速度折线，未发现该桌面视口的溢出；未进行移动端验收。
- AI回复配置仍为0；原意大利试验批次有真实回执，但不代表新的全量批次系统完成。
