# B.13 提速、速度监控与每日额度实测

2026-09-13。用户明确要求继续发送直到每日新触达上限，取得平台限制标志；同时要求提速与速度监控。当前it-bulk-20260913已从100扩到500目标，授权变更保存在cycle_bulk_scope_event。此目标不是已发送人数，也不是平台额度剩余量。

## 提速方案与证据

新系统单发写入间隔从5秒设为2秒，不修改旧BDHub配置，旧写入gate仍遵守旧间隔。同一组卡文共享一次鉴权和会话runtime；商品核验只在同组10秒内复用，跨收件人、超时或恢复必须重新核对。卡片回查、正文前新消息核对、身份、控制和未知结果门禁保留。

初始13组优化样本的卡→文字间隔中位数约4.09秒，原来通常约8秒。2秒是发送器最小写入间隔，实际仍包含读取/回查，不能当成每2秒触达一人。整体吞吐还受身份解析、库存供给和账号竞争影响。提速生效时点保存在cycle_speed_policy。

## 监控口径

- 近5分钟已确认卡片对应触达人数/分钟、已确认消息/分钟。
- 最近1分钟、15分钟触达；15个一分钟柱状点。
- 同组卡→文字中位耗时；提速后样本数与中位数。
- 材料准备/发送执行的成功平均耗时、未成功操作次数；账号忙不是平台拒绝。
- 未确认尝试比例包括在途与未知，不标成失败率；平台明确拒绝另计。
- batch worker阶段和最近更新时间。速度按已确认组件的实际派发时间统计，不用历史总量除运行时长。

数据来自cycle_delivery_part、cycle_bulk_timing、cycle_bulk_runtime与cycle_platform_signal。工作台自动刷新。

## 限额信号与停止

已核实官方SDK SendMessageResponseBody：field3=status，field5=check_code，field6=check_message。发生原生拒绝/异常时保留这些字段及响应SHA引用；不保存new_ticket等凭证。cycle_platform_signal追加保存，后续回查不能覆盖掉首次限额/拒绝证据。

明确native rejection与result_unknown分开：明确拒绝不作已送达，批量新触达停止等待识别拒绝范围；自动回复不因已证实未发送的拒绝被误当未知卡长期锁住。未知结果仍只核验，不重复发送。

本地保守滚动24小时500位预留上限与平台真实额度分开。达到本地计数但未收到平台限额时记录local_capacity_reached，不能声称已经取得平台限制标志；需要进一步只读核对当前平台提示/额度语义。当前尚未观测到每日新触达上限返回，不能提前编造错误码或认定所有拒绝都是日额度。

## 持续执行交接

保持本批500目标、收信、自动回复、供给与身份解析运行。若平台拒绝出现，先读取cycle_platform_signal及对应执行，区分每日新触达、单达人5条、账号限制与其他错误，形成有证据的下次停止规则。不得换号绕过机构市场额度，不重发已确认组件。

同一达人如果收到卡片后立即发来咨询，未提交的固定推广文字取消，转入咨询处理，保留已确认卡片；商品事实可使用这张已确认卡，不要求固定宣传文字必须补发。

2026-09-13后续用户明确20位/分钟目标。最新运行已改用B.15的4通道短批次、0.75秒新系统写间隔和更高供给频率，详见[吞吐改造](second-cycle-throughput-20-v1.md)。本文2秒单组runtime方案保留为阶段实测历史，当前效果以运行库为准；持续20位/分钟仍未通过真实验收。
