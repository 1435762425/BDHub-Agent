## 问题与修复

素材 Worker 的实际失败原因是 `current_offer_changed`，不是账号争用：PID 1729480033890900437 当前库存不满足 >100。建卡前检查正确地阻止了平台提交，但本地意图一直停留在 prepared，每轮又选中它并退出，后面的合格商品因此无法继续准备。

新增 `invalidated` 终态只用于**尚未提交**的建卡意图：要求 state=prepared、receipt为空、当前精确 PID/Offer/Campaign/来源身份一致、60秒内的新响应证据，以及不合格商业条件或佣金变化。started/response_saved/unknown 不允许失效处理，也不允许创建新意图替代未知动作。原始 offer_json 与当前核验依据均保留。

同一货盘版本增加独立 executionHold 投影，选品、准备容量与最终发送资格都排除该版本；不篡改原始库存或不可变货盘。新完整货盘版本到来后会重新判断，不能把本次库存不足当永久拒绝该 PID。当前仍沿既有货盘刷新周期；尚未新增针对这些 hold 的更短补货轮询。

材料推进器区分“无提交的商品失效”与“提交结果未知”：前者继续准备本轮其他商品；后者只核验、停止新建卡。

实测 `var/material-unstall-20260913.json`：

- 原阻塞商品 1 次当前读取，0 次建卡提交，记录 invalidated。
- PID 1729480050548447690 和 1729480054732331671 各建卡 1 次、读取 4 次，均已验证。
- 三个动作均确认身份文件未变；素材调度恢复 idle，连续失败归零。

## 身份关键路径

实际属于 active IT 二发 plan 的 cycle_identity_outbox 批次写入 identityOnly=true。普通用户手动导入和 OEC 画像刷新保持原完整流程；不能凭输入标签或 Kalodata ID 开启身份绑定。

明确精确 handle、数值 OEC 和 IT 市场的 Find 成功后即可完成该二发身份任务。仍使用已有 HTTP、签名、验证与重放流程。Find 不含明确 IT 市场时继续原 Profile 核验；没有精确 handle 就保留未匹配。旧 handle/OEC 不猜测合并，旧已核验 OEC 不因名字变化丢弃。

导入器验证目标关联、HTTP/code/验证状态、精确身份与未变的账号身份文件。intentional identity-only 记录 completed / identity_only，保存 Find 事实，不伪造 Profile 成功或失败。UI 已有“已取得OEC，画像尚未补齐”的状态。完整画像仍可通过既有按 OEC 刷新入口补齐；本轮未新增自动后台画像补齐任务，不声称已完成完整画像更新。

身份 Worker 在当前读取结束后的空闲点换版，使用 --interval 1，业务请求 QPS 与验证重试规则未改。新的身份与线索桥接继续按持久证据自动回填。

实测新模式连续17个完成的输入：17次业务请求，12个明确身份、5个无精确匹配，Profile调用0。其中首批2个明确身份已核对在cycle_identity_resolution中自动绑定。报告留在各discovery item既有attempt目录，未制造模拟入站或修改旧BDHub。
