# 货盘页 UI 重组（2026-09-14）

全托货盘功能基本完善后，用户要求重组前端：原来 10 张卡片从标题一路平铺到「达人线索查询」，没有任何分区或组织。

## 原来的三个问题

1. **页面顺序和真实流水顺序不一致**：真实流水是 `采集 → 筛 → 入池 → 建链 → 查线索`，但「已发现商品」（1 万条明细）夹在入池与建链之间打断数字阅读；「达人线索查询」在最底部，而它依赖的「Kalodata 身份」在它上面隔着几屏。
2. **汇总与明细混层**：表格虽已折叠，但"这个阶段有多少"和"具体是哪些"没有视觉分层，10 张卡看起来同等重要。
3. **运维配置混在业务流里**：命名模板、Kalodata 身份、作业与定时属于跨业务配置，却排在业务末尾。

## 新结构（用户确认三项）

```
货盘    [全托商品] [非全托商品]          ← Tab 分区

┌ 漏斗条（常驻一行，可点击跳段）──────────────────────────┐
│ 采集 10,000 → 筛出 2,291 → 已备链 1,410 → 待查线索 255 │
└──────────────────────────────────────────────────┘

① 采集与筛选    来源（主动采集）· 入池门槛（可调+试算）· 商品明细〔折叠〕
② 入池与建链    批量选入 · 已选商品链接准备〔明细折叠〕
③ 达人线索      Kalodata 抓取身份 · 达人线索查询队列（立即运行）
```

后续调整（同日）：**系统与运维独立成子页面 `/ops`**，货盘页只剩三段业务流水。

```
系统与运维页（/ops）    Kalodata 抓取身份 · 作业与定时 · 新建链接命名
```

- 三样都是**跨业务**配置：抓取身份影响线索查询，作业面板决定各步骤手动还是定时，命名模板影响之后新建的链接。它们不属于某一个流水阶段，放在货盘页只会拉长阅读路径。
- 货盘页③「达人线索」保留查询队列，并留一行指向 `/ops` 的说明（身份失效时查询会停下并保留断点）。
- 导航新增「系统与运维」（`ops` 视图，与既有「系统设置」= 市场账号页并存不冲突）。

- **Tab 分区**：`全托商品` / `非全托商品`。非全托页如实标注「尚未建成」，只写已确认的设计，不提供任何入口。
- **漏斗条常驻**：4 个数字实时反映状态，点击滚到对应卡片。这是用户要的"采集→筛出→入池→建链"一眼可见。
- ~~运维单独成段并默认折叠~~ → 后改为独立子页面 `/ops`（见下）。
- Kalodata 身份曾移到③（线索查询的依赖），随后与作业、命名一起移出到 `/ops`。

## 实现要点

- `Section` 组件（`features/bdhub/ui.tsx`）：段序号 + 标题 + 段内摘要。
- `buildFunnel`（`features/catalog/funnel.ts`）：漏斗四个数字在一处推导。
  **缺失来源显示 `null` 而不是 0**——"还没读到"和"确实是 0"是不同事实，用 0 表示未读数是撒谎。有 3 项测试钉住这一点（含"真实的 0 保留为 0"）。
- `useLeadsQueue`（`features/catalog/useLeadsQueue.ts`）：队列数据由页面持有，漏斗条与队列面板共用一次请求，不重复轮询。
- 页面按流水重排，业务逻辑（采集/筛分/命名/链接的状态与处理函数）一行未改。

## 验证

- 构建产物含全部新结构与文案；`tsc` 干净；Web 测试 **313 项通过**（新增 3）。
- 漏斗数字与三个 API 逐一核对：采集 10,000 / 筛出 2,291 / 已备链 1,410 / 待查线索 255。
- 已备链 = `verifiedPidCount + reusePidCount` = 219 + 1,191 = 1,410，与查询队列的 `linked` 一致。

## 二次精简（2026-09-15，按用户要求）

用户指出卡片太多是**浪费空间和时间**。这次是合并与删除，不是重排：

| 原 | 现 |
| --- | --- |
| ② 入池与建链 段 + 「全托商品批量选入」独立卡片 | 删除段落；**「一键选入」按钮直接放在「待入池」小卡上** |
| 「已发现商品」独立卡片 | **合并进「意大利·全托主力来源」**，商品明细折叠区放在该卡最下面 |
| 「TapLink 准备」放在② | 移到①，作为入池门槛卡的下一张 |
| 「商品短名」一大段说明 | 只留**缺 N 个 + 「一键补全」**；模型/端点/Prompt 收进「模型与提示词」折叠区 |
| 「本次选入上限」输入 + 「点一次跑一批」说明 | 删除；选入默认上限就是脚本上限 600，一次点完 |

现在的结构：

```
① 采集与筛选
   意大利·全托主力来源      〔商品明细（可搜索）〕
   采集即筛：入池门槛        [待入池 + 一键选入]
   TapLink 准备            短名：缺 N 个 〔一键补全〕〔模型与提示词〕
② 达人线索
   达人线索查询队列
```

Prompt 提取为 `cycle_materials.NAMES_SYSTEM_PROMPT` 常量，经 `/api/catalog-names` 暴露给前端——
**展示的是代码里真正发出去的那一句**，不是另写一份可能走样的说明。

## 三次精简：去明细、加进度、队列卡片化（2026-09-15）

用户四条要求，都是「少铺数据、多给状态」：

1. **TapLink 准备加准备进展**，去掉「商品链接明细」表。
   进度怎么算、文件在哪、为什么 `start()` 要先清空上一次的，见[建链进度](catalog-actions-and-incident-20260915.md#建链进度一次读取-19-秒一轮却要几分钟2026-09-15-追加)。卡片里现在只有一行进度条 + 一行「第 N 步 · 在读什么 · 已判定 · 待建链 · 本批已建 · 更新时间」。
2. **达人线索查询队列不再展示明细**（原「首次查询队列（按销量降序）」5 行表已删）。
3. **发送池不再展示明细**（原「可发前 20 行」表和「池中等待与冷却明细」折叠区已删）。
4. **查询队列改成和发送池同一种队列卡片**：

```
达人线索查询队列
 ┌ 队列 PID（总数） ┐┌ 今日可查 ┐┌ 冷却中 ┐┌ 本次将跑 ┐   ← 四个数字，本次将跑高亮
 │ 合格 ∩ 有链接    ││ 首次+到期 ││ 周期内 ││ 上限内的 │
 └─────────────────┘└──────────┘└────────┘└──────────┘
 线索覆盖（已查过 / 队列总数）  ▓▓▓▓▓▓░░░░  1,501 / 2,287
 ┌首次待查┐┌到期待刷新┐┌冷却中┐┌连续失败暂停┐        ← 四层，合计＝队列总数
 └───────┘└─────────┘└─────┘└───────────┘
 四层合计就是队列总数……另有 521 个查过的 PID 已出队列，不占额度
```

- 「已出范围」（查过但链接不再合格 / 商品不再合格）**故意不做成第五层**：它不在队列里，混进去会让四层之和不等于总数。用一句话如实报数。
- 「已查过」必须同时扣掉**从没问过**和**连续失败被移出**的，否则覆盖条会把从没到过平台的工作算成已完成。
- 冷却按 **PID** 算（不是达人），和发送池按达人算是两套不同口径，两张卡片各自的副标题都写明了。

三张卡片现在都是「四到六个数字 + 一层层拆开」的同一形状，扫一眼就知道卡在哪一层，不需要读表。

## 四张卡片：补上发送前的 OECID 闸门（2026-09-15）

用户指出：发送前要先拿到达人的 **OECID**，这一步在页面上既没数字也没入口。确认后新增独立一张卡，放在②达人线索 里、**查询队列与发送池之间**：

```
② 达人线索
   达人线索查询队列        ← Kalodata 查 handle
   达人身份（OECID）       ← 新增：handle → 平台身份，查不到的进不了池
   发送池                 ← 只有已拿到 OECID 的达人才能出现在这里
```

- 卡片四个数字：**已就位（可进发送池）／待补 OECID／搜索不到（不进池）／本次将补**，加上一条补身份进度和手动按钮「开始补 OECID」。
- 状态、边界与实测见[达人身份（OECID）阶段](creator-identity-oecid-stage-20260915.md)。
- 发送池卡片补一句「池里只有已经拿到 OECID 的达人」，因为**这不是池子的一层，而是进池的前提**——把它画成第五层反而会让人以为池子里有「缺身份」的位置。
- `StatTile` 提到 `features/bdhub/ui.tsx`：队列卡片的数字块形状从此只写一次，查询队列与新卡共用。

## 五轮精简：把说明文字清掉（2026-09-15）

用户逐条点名删掉 16 处**解释性文案**，原则是：**页面只留数字、状态和动作，不留自我介绍**。

删掉的包括：采集卡的「只在你点按钮时采集，一次约 15 页…」、入池门槛卡的副标题「门槛只决定新商品能不能进池…」、三个输入框的 hint（「含等于。」等）、TapLink 卡的副标题与「链接不授予发送权限…」、查询队列的副标题与该段长说明、身份卡的「身份单位是达人…」与通道说明段、发送池卡的副标题与暂停提示、页脚的「平台展示总佣金不等于…」和「抓取身份的检测与刷新在系统与运维页」。

留下的：

- **筛分那段不合格原因**保留，但改成**斜体**，并把标点重写成中文习惯：`合格率 22.9%；筛除 7,709 个（累计销量不足 300，7,484 个；评分低于 4，1,390 个；佣金字段缺失，17 个；两档佣金差不足 2 个点，13 个）；另有暂无评分的 421 个（评分为 0 的语义未核实）。`
- 身份卡的**等式**（`线索 ＝ 已就位 ＋ 待补 ＋ 搜索不到`）保留：它是自校验，不是说明。
- 两张卡的**运行说明**：用户点名的第 10 条是身份卡的「上一批：领了 N 个达人…」，已删；**查询队列那张卡里同类的一句保留**（未被点名），要一起删需再确认。

**唯一保留的例外是「异常停止原因」**：`账号不可用`／`维护中`／`验证未完成`／`超时` 这类必须在页面上说，否则出问题时页面什么都不讲。日常叙述（「正常结束」「达到上限」）随该条一起删掉。

⚠️ 副作用：`发送仍为暂停` 的三处提示都被点名删除，**货盘页现在不再声明发送已暂停**。代码层面池子卡依旧不提供发送入口、`service_reply_config.enabled` 也仍是 0，但"页面上看得出暂停"这件事没有了——需要的话让用户决定是否留一处。
