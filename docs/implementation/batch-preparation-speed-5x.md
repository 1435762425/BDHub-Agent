## 主要卡点

- 首先是身份解析：当时已有1400多条排队，每个达人都重启Python/签名SDK/HTTP会话，再串行等待响应。重复首请求初始化和串行网络等待占据主要时间。
- 单纯20人共享会话的第一轮仍不足以稳定达到5倍；改为3条同账号通道、总请求级限速后达到目标。
- 热更新时一个旧准备进程仍加载单活跃身份索引定义，与新分组状态发生冲突；已同步重启准备与身份进程。该中间失败保留日志，不计成成功。
- 账号已有其他读取任务时，旧的零等待抢锁会反复产生空批次；分组查询改为最多15秒有界等待同一账号锁。
- 后续素材执行原有固定30秒间隔：整批名单齐备且材料仍有正常可执行工作时改为2秒续接；异常/未知仍按较低频率核验。这部分尚未有本批完整实测。

## 实现与边界

- `discovery_cohort`保存同组成员、尝试编号与归属；一次事务认领最多20人。同一时刻仍只有一个执行拥有者，组内最多3个HTTP请求通道。普通手动画像任务默认保持原单人流程。
- 同账号同一机构身份，不跨账号复制Cookie或签名状态；共享签名器内部锁与总请求节拍，每个通道保留各自HTTP会话。所有业务重试/回放仍经过3 QPS总节拍。
- 每个目标独立按精确handle、IT市场、OEC、HTTP业务回执核验。完整组响应保存在cohort目录，每人的证据带父响应摘要并按原有身份入库规则落库。
- 其他目标后续失败不抹掉已核验的只读结果；无请求/未完成者不标成功。重启优先回放已保存组证据，无有效结果只重排只读查询，不推测身份。
- 准备页面增加最近约5分钟净新增候选/分钟。时间窗口以当前时钟推进，即使没有新事件，速度也会衰减为零。
