# 采集即筛：全托商品入池门槛前置到采集

2026-09-14，用户确认将全托商品的三条入池条件从"选入时判断"提前到"采集完成即判断"，并要求门槛像命名模板一样可以在货盘页面上调整。同日确认门槛**只管进不管出**：不清理已在选中池、但达不到新门槛的存量商品。

## 为什么可行

采集结果里三个指标本来就有，不需要额外请求：

| 指标 | 字段 | 例子 |
| --- | --- | --- |
| 累计销量 | `sales` | `2.349 已售` → 2349 件 |
| 评分 | `product_rating` | `4.3` |
| 两档佣金 | `commission_rate` / `open_collab_rate` | 1400 / 900，差 5 个百分点 |

采集快照还自带 `fs_is_selected`（平台是否已入池），所以"筛出多少、其中多少已入池、多少待入池"在采集完成那一刻就能算出来。对 `it-global-20260914`（10000 条）实算：

```
采集 10000
├ 筛出（合格） 2291 (22.9%)
│  ├ 已入池 1692
│  └ 未入池 599        ← 与上一轮实际选入的 599 完全一致
└ 筛除 7709
   累计销量不足 7484 · 评分低于门槛 1390 · 佣金字段缺失 17 · 两档佣金差不足 13
```

筛分结果与实际选出的 599 一字不差，说明这不是新逻辑，只是把已在跑的判断提前。用当前门槛重跑 10000 条耗时 **0.41 秒**。

## 门槛只决定进入

反查平台已选池 2819 条，其中 **1127 条达不到这三条门槛**（销量不足 843、评分不足 144、两者都不足 134、佣金问题 6）。这些是早期按别的口径选入的存量商品，其中可能正在出单、已有 TapLink 和达人。用户据此确认：**门槛只决定新商品能不能进池，不移出已在池中的商品**。要清理存量另走清洗流程并由用户看清单确认。

## 配置与记账

- 配置：`config/catalog-screen.json`，字段 `minSales`（0–1000000）、`minRating`（0–5）、`minCommissionGapPoints`（0–100）、`allowUnrated`。默认 300 / 4.0 / 2 / 允许。页面上可改，改动先生效校验再原子写盘；被拒绝的取值不会碰到文件。
- 筛分记录：`var/global-source.sqlite` 的 `global_source_screen_run` 与 `global_source_screen`，逐条记 `合格/不合格 + 原因码 + 当时的三个指标值 + 当时生效的门槛`。
- 筛分批号：`screen-<digest(采集批次, 门槛指纹)[:24]>`。**门槛不同就是不同批次**，改门槛不会覆盖旧筛分结果，所以可以对比"改之前"和"改之后"。
- 原因码：`sales_missing`、`sales_below_min`、`rating_unrated`、`rating_below_min`、`commission_missing`、`commission_gap_below_min`。码不带数字，阈值从配置读，改门槛不会让原因码过期。

## 接入位置

采集作业在采集回合停止读页后再做筛分（`collect-global-opportunity.py`）。筛分是纯本地算术，不发平台请求；筛分失败不回滚或否定已经成功的采集，只把错误记进运行报告。筛选与选入共用同一份配置（`lib/global_selection.assess` 委托 `lib/global_screen.evaluate`），不会出现"页面门槛"和"实际入池门槛"不一致。选入批次号已纳入门槛指纹。

## 页面上的一条修正

已确认口径写的是"有评分须≥4.0、暂无评分允许"，但旧实现把评分 0 一律判不合格，与口径不符。现按口径实现为 `allowUnrated` 开关（默认允许）；评分 0 只作为事实记录，不当好评也不当差评。本批受影响的 421 条本来也因销量不足被筛除，**翻盘 0 条**，但下次采集不会再错杀。评分为 0 的平台语义仍未核实。

## 边界

- 筛分不写平台、不发消息、不授予发送权限；发送与自动回复仍为暂停。
- 进入选中池仍需平台写入，走已验证的选入路径（单次提交、逐条回查、未知按原意图核验）。
- 采集即筛只产出候选并记账，**尚未把"合格且未入池"自动接到选入执行**；该串联与每日 03:00 定时任务一起决定。

## 漏斗要读「池子现在是什么样」，不是「采集时是什么样」

用户发现页面数字过时：筛分卡显示「已在池中 1,692 / 待入池 599」，但这 599 个其实**早就入池了**。

原因：`selection_split` 只读采集快照的 `fs_is_selected`。快照拍在选入**之前**，所以它永远说这 599 没入池——即使它们已经被确认选中。

修法：实际入池 = **快照标记已选 ∪ 选入账本里已结的商品**。账本口径 `state IN ('confirmed','already_selected')`。

| | 修之前 | 修之后（真实） |
| --- | ---: | ---: |
| 已在池中 | 1,692 | **2,291** |
| 待入池 | 599 | **0** |

**只有「证明在池中」才算已结**：`pending`（还没提交）、`filtered`（只是没达门槛）、`needs_review`、`result_unknown` 都**不算**——尤其 `filtered`，门槛放宽后它应当重新有资格。有测试逐条钉住这一点。

同时修正选入卡的措辞：`本批待选总数` 其实不是"待选"，它是**批次商品数**；改为 `本批商品数` / `本次新选入` / `已在池中（跳过）` / `尚未提交`，且 `尚未提交 = 0` 时卡片右上角标 `本批已全部在池中`。
