# 自主运行模式与经营工作台改进

2026-10-24。延续用户已确认的现有业务规则和持久授权；本批针对完整经营路径重新检查，不能将上一轮运行恢复等同于整体设计最优。当前合同见 [PROJECT](../PROJECT.md) 与 [TECHNICAL](../TECHNICAL.md)，发布结果另见[本批交接](../handoff/autonomous-design-20261024.md)。

## 执行模式

复用原任务、台账和控制，把执行条件分清楚，不增加第二套调度或授权状态：

| 工作 | 何时执行 | 停止与完成标准 |
| --- | --- | --- |
| 新的模型生成、发送和平台写入 | 原授权、计划、窗口、资格和额度均允许 | 暂停立即阻止新动作；平台结果按原意图入账 |
| 已提交回复的核验 | 原 `inflight/accepted/unknown` 台账存在 | 只读原账号/请求，沿原次数和期限；耗尽隔离，绝不发送 ready 草稿 |
| 本地匹配续段 | 同原 generation/游标确有前进，仍有下一页，且没有更优先的停止/核验等待 | 保留每片段的边界和停止检查，有进度短延续；无进度、账号、额度和 unknown 仍按原节奏等待 |
| 人工事项 | 用户确实需要作决定 | 使用会话人工队列人数；未回来信、技术等待与人工案件不相加 |

## 本批实现

### 读取成本与真实迁移

- 达人概览的 `identity_market_recent` 虽已写入 schema 定义，生产旧库尚未建立；旧查询按市场扫描排序。先做 3.2 GB online backup，校验 SHA256 和完整 `quick_check=ok`，再幂等创建同一索引。事务前后四张业务表数量不变，未调用平台；原身份事实没有重写。
- 同一 BR 计数结果保持：旧子查询 9.9347 秒，补索引后的冷读样本 1.892 秒，原生产 HTTP 概览随后为 0.9678 秒。查询计划不再出现最后观测时间的全量排序。缓存和当时负载影响耗时，不将样本当成长期吞吐承诺。
- 互动统计先过滤回复/橱窗种类，再按达人去重；同一只读快照结果相同，样本 0.198→0.0217 秒。
- 会话详情只读取所选达人的 handle，画像指标绑定当前 market/creator/OEC，利用原 `identity_history_lookup`。旧指标查询在只读 30 秒期限内未完成，新的同一 OEC 查询约 0.00014 秒；新完整人工会话详情在原真实库只读样本为 0.2365 秒。旧查询超时，不能声称这一实测已经逐值比较；字段、最新观测、当前 no_value、零值及身份隔离另有合同测试。

### 匹配续跑

500 人原 OEC 页由逐人两次查询改为一次关联读取，单人 fresh 校验和批量路径共用画像过滤、排序及绑定解码。保持 observed_us、完整 Profile 优先级、rowid tie、market/creator/current_handle/conflict、JSON 资格与扫描计数。缺画像仍占原游标位置，最新 creator 错配不回退旧画像；发送前仍读取原 fresh 事实。

同一只读快照的 500 人完整对象与顺序逐项相同，SQL 从 1,000 条降为 1 条。两组冷/热样本分别为 84.7→11.0 ms、44.53→21.72 ms。原每 2,000 人片段固定等待 5 秒，586,436 人一轮仅固定等待下限约 24 分钟；现在仅有实质游标/scanned 前进、明确有下一页的本地匹配用 0.25 秒续段，保留原任务、页大小和资源交接。无进度、暂停、账号/额度等待及 unknown 不快转。

### 原回复恢复与启动互斥

本地 fixture 复现：原未知回复已超过核验期限，关闭 AI 并退出 worker 后，旧 scheduler 不再恢复核验，原 unknown 继续阻断市场派发。现在用只读台账判断原已提交回复，必要时以 `--reconcile-only` 恢复；计划暂停、窗口外或人工停止不授予模型、新会话或新回复权限。原 started、requestRef、sender、文本及检查预算保持，超期只隔离。

IT 同时存在 `job-inbox.stop` 时保留该标记，也不强行恢复 SDK owner；没有原本地精确证据时，可能借用失败后按原期限隔离，不能承诺平台回查一定成功。关闭新工作与保留已提交事实是不同合同。

IT 发送器的并发 fixture 复现两次 spawn 与 `.tmp` 竞争。现在复用已有 `runtime_files.launch_guard/atomic_json`，父启动与子心跳/退出共用稳定 guard，运行 flock 已被占用时不重复 spawn，也不拿未经证明的 PID 覆盖原记录。重复 child 先取得运行锁，再打开业务库。启动和观察记录不改停止状态或授权，只有原页面显式 start 事务能清除对应业务停止位。

## 工作台体验

本轮先截图走首页→提醒分组→人工队列→选中会话。原页面把跨市场分组数显示成待处理任务数；同一首页还有未回人数、人工队列人数和 service_case 行数，不能相加。首页“暂无等待”也不能表达独立发送/回复通道的窗口等待。

首页新增原会话分类器的 `humanQueue`，不再用 service_case 行数冒充需处理人数；读取失败为 null。全局提醒明确分组/市场的计数单位，区分人工事项、来信积压和系统/维护提示；结果未知、真实故障和旧数据不隐藏。工作流与独立通道的等待说明应解释系统能否按原授权继续，时间只取现有配置和状态。

会话详情原来没有独立加载/失败状态，30 秒轮询还会取消同 CID 的未完成详情请求。现在同一选择复用在途读取，切换 market/CID 仍取消旧请求、拒绝迟到结果；详情加载、失败、保留旧详情时的陈旧提示分别呈现，并可重试。人工原因及处理结果入口放到事项主视区，原写入 revision 与草稿合同不变。

普通轮询复用与写后刷新分开：草稿保存、原回复核验和结清事项成功后强制新读取代次，提交前的迟到详情或旧队列不能覆盖新 revision、重新选中已经结清的事项。持续二发的恢复说明沿原 stop 否决与全局设置/automaticEnabled/runRequested 的 OR 合同；缺少持久控制、窗口或 fresh 证据时不推测自动恢复时间。

本次备份/完整性检查与部分浏览器审计重叠，额外磁盘负载影响实际等待时间；不能将这一轮详情长等待全部归因于日常负载。取消循环、无加载反馈及未绑定 OEC 的查询则有独立源码/测试/查询计划证据。

上线后另一只读样本中，完整人工会话详情 HTTP 为 0.1457 秒；最终四 API 并发样本为详情 0.1341、达人概览 3.9689、首页 5.4886、六分区总览 5.8652 秒，全部 200。首页人工队列 36 与会话列表一致，浏览器原人工会话已能正常加载并看到处理入口；没有为截图执行业务写入。

全量覆盖时效另有真实限制：检查当时 BR 有 5,149 个 checkpoint，每分钟约完成 50 个 HTTP 核验，理想全轮也需约 86 分钟；`min(checked_at)>300` 的固定提示不能当作新来信处理全局故障。成功空读同样更新 checked_at，138 分钟是全量核验陈旧而非“无消息时间”。页面仍保留数量、最旧时间、可见性和链接，明确为“全量会话复查较慢”，说明新来信优先、全量按队列推进；未隐藏或清空事实。检查时未完成 SDK 信号为 0、七市场 gap/backfilling 为 0，旧 checkpoint 持续更新。MY/TH 此前长时间旧覆盖仍是技术限制，不据此称全量覆盖已恢复到五分钟。
