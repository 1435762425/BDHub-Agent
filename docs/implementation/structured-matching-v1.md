# 结构化匹配与关系评审准备 v1

2026-09-11。本轮实现新设计的事实层、双向召回和模型输入准备，不沿用旧版选人算法，也没有调用真实模型或平台。

入口：`http://127.0.0.1:5198/opportunities?mode=matching`。侧栏“机会与货盘”进入新匹配工作台；原页面作为界面演示保留。默认数据为72个合成商品、360名合成达人、90个独立Offer，覆盖MX/BR/IT。

## 已实现的业务链路

1. 从商品找达人，或从达人找商品；来源显式选择合并、一发、二发，不通过是否有样品决定来源。
2. 精确PID正销量、明确需求、多类目价格适配、类目补充和冷启动分别召回；同一组合合并来源。
3. 展示同币种价格带、内容形式、类目交集、单一窗口销量证据与缺项。缺失不变成0，多个重叠窗口不累计成总销量。
4. 商品与活动报价分开。保留公开、总、达人、机构佣金与各自Offer版本，不能拼接不同活动的最优值。
5. 为一个关系整理最多5个商品、每商品最多2个完整Offer的评审包。字符预算6000；实际token未计算，`estimatedTokens=null`、`modelStatus=not_called`、`executable=false`。
6. 商业条件变化使相关候选与旧评审包失效。重新召回可以发现新符合条件者；其他市场和不相关类目的缓存保持。

有库存/活动/卡片准备缺口的商品仍可被发现并研究。营销拒联、暂停、人工控制的关系可以查阅，但不能准备自动Agent评审。评审就绪不是发送资格。

## 数据与实现

| 部分 | 位置与作用 |
| --- | --- |
| 合同 | `apps/web/src/features/matching/contracts.ts` |
| 事实与索引 | `apps/web/src/server/matching/store.ts`：商品、达人、Offer、证据、需求与多类目索引表 |
| 合成数据 | `apps/web/src/server/matching/fixtures.ts`；数字形态ID始终保持字符串 |
| 本地API | `GET/POST /api/matching`；查询分页与结果数量有界，命令仅限召回、评审准备、合成商业变化 |
| 界面 | `apps/web/src/features/matching/MatchingWorkspace.tsx`；请求编号保留在sessionStorage用于中断恢复 |
| 存储 | 新项目 `var/matching.sqlite`，与旧BDHub和已有 `runtime.sqlite` 分离；不进入Git |

事实导入按稳定ID/市场/PID/OEC核对，所有字段有来源和观测时间。较早观测不能覆盖当前事实，会拒绝该批次；历史保留与多来源仲裁属于后续导入适配，不静默回滚当前值。币种不明的来源价格应保持未解析，不能按市场猜原始币种后导入。

语义字段、商业字段、关系控制分别处理变化。`semanticBuilds` 计结构化语义字段的hash/特征版本更新，不是模型或向量调用数。单纯价格、库存与报价变化不增加该计数。

召回按相关主体、类目、精确PID和需求分区版本缓存。首次变得适配的对象也会使相关查询失效；活动跨越开始/结束时间时同样重新核对。每路最多200个不同候选，最终最多50个；界面取20个。初始排序按明确需求、精确证据、价格/形式/类目依次比较，不输出未经校准的成功概率。

## 量级基准

原始记录：[matching-benchmark-20260911.json](../research/matching-benchmark-20260911.json)。Mac/arm64、Node26.7.0，本地独立临时SQLite；每档20次商品方向＋20次达人方向查询，按MX/BR/IT分层共14/14/12次。

| 合成规模 | 导入与索引建立 | 未命中结果缓存 P95 | 结果缓存命中 P95 | 模型调用 |
| --- | ---: | ---: | ---: | ---: |
| 1,000商品 / 10,000达人 | 738 ms | 18.71 ms | 0.88 ms | 0 |
| 10,000商品 / 50,000达人 | 3.92 s | 32.44 ms | 0.69 ms | 0 |

“未命中”只指应用结果缓存，不是磁盘/OS冷缓存。大档整进程当时RSS约286MiB，不是峰值或独占内存。各查询最多返回20个候选；大档各路累计最多返回805个召回行，这不包括后续读取的Offer和证据。查询计划按市场/类目/价格或精确PID使用索引，部分有范围内临时排序；没有枚举5亿商品×达人组合。

这组基准证明本地技术路径能处理测试量级，不证明真实匹配效果、并发上线容量或平台日发送量。样本分布、来源覆盖和真实业务评审仍需另外验证。

复现：在 `apps/web` 执行 `npm run benchmark:matching -- --large`。过程使用合成数据，完成后删除自己的临时库；不访问旧库、远端或模型。

## 自动验证与浏览器验证

- 全部76项检查通过：25项匹配存储契约＋3项匹配接口边界＋原48项测试；类型和生产构建通过。
- 核心覆盖：幂等导入、长ID、未知/零、佣金不拼接、双向多类目、二发精确证据、去重、乱序观测拒绝、增量新候选、缓存隔离、时间过期、控制抑制、评审范围/上限。
- 浏览器已经验证商品方向二发、达人方向多商品、评审包、来源切换和商业更新。实际评审包曾包含5个商品/5928字符，未计费。
- 实际停止本地Web模拟请求中断，刷新并重新进入页面后恢复原请求ID；一次降价从30000到15000最小货币单位、商业版本2→3、语义版本保持1。同ID再经HTTP重放不再次改价；较早已完成命令在后来条件变化后重放，返回当前商品事实，避免界面重新显示旧价格。
- 更新商业条件后，界面将旧候选标为失效并禁用评审，重新查询取得新结果。
- 视觉证据及剩余覆盖范围见项目根 [design-qa.md](../../design-qa.md)。

## 下一实施边界

当前没有真实数据导入入口、定期自动召回、实际向量检索、学习排序或DeepSeek调用；也没有把本地评审包直接桥接成真实发送。默认示例图片只用于布局，不是模型识别商品用途的证据。

下一阶段先做少量已明确范围的真实字段适配、人工评审对照与token计量，再决定语义召回/精排和DeepSeek调用预算。原运行切片的一关系单示例商品仍需迁为多事项模型，不能把当前两个验证库合起来就宣称完整经营系统完成。
