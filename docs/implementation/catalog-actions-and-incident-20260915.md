# 入池与建链的主动按钮，以及一次误启动事故

2026-09-14/15。用户要求「全托商品批量选入」与「已选商品链接准备」都要有主动操作按钮，并去掉页面上的冗长说明，只留关键数据。

## 两个主动按钮

| 按钮 | 实际调用 | 性质 |
| --- | --- | --- |
| 开始选入 | `select-global-products.py execute --limit N` | **平台写入**（选入商品） |
| 准备链接（只查不建） | `catalog-link-batch.py --seed --creates 0` | 只读 |
| 准备链接并新建 | `catalog-link-batch.py --seed --creates N` | **平台写入**（建 TapLink） |

`scripts/lib/job_run.py` 统一负责启动与存活判断，复用链接准备与 Kalodata 登录同一套形态：请求立即返回，工作在自己的进程里跑，页面跟随一个状态文件。存活判断**问进程表**（`os.kill(pid,0)`），不看标志位。

两条纪律：

- **建链默认 `creates: 0`**，即只摸清哪些商品已有可复用链接、哪些确实缺链，不新建任何链接。新建必须显式设上限。
- `platformWrites` 如实标注：只有 `creates > 0` 的链接作业才是写入。
- 同一作业同时只跑一个（409）。
- 配置里**拼错的字段名直接拒绝**（`job_unknown_field`），否则会静默按默认值运行。

## 一次误启动事故（如实记录）

**经过**：验证「重复启动会被拦住」时，我用了一个会立刻退出的进程 pid 去伪造「正在跑」的记录。守卫按进程表判断，pid 已死 → 判定未运行 → **真的启动了一次选入作业**。

**后果**：0。平台写入 `platformWrites=0`，真实发送 0，建链 0，**带回执的条目 0 条**（即从未发出任何选入请求）。它只做了只读回查，把 200 条标记为 `already_selected` 后按 `--limit` 上限退出。

**副产品**：这次意外反而**再次确认之前那批 599 个商品全部在已选池中**——回查到的 599 条一条不漏全是 `already_selected`。

**守卫本身正确**：事后用真正存活 300 秒的进程重测 → **HTTP 409**，且未启动任何进程。错的是我的验证方法，不是代码。

**收尾**：用户选择把该重复批次跑完。再跑两次只读回查后，批次终态 `already_selected: 599`，`platformWrites=0`，回执仍为 0。第三次运行短路返回 `alreadyComplete: true`。未删除任何数据。

## 顺带修掉的根因

每次门槛变化都会生成**新的选入批次号**，而 `prepare()` 会把快照里所有「合格且未标记已选」的商品重新入队——包括在**之前批次里已确认入池**的商品。结果是每点一次「开始选入」，都会造一个 599 条的空批次，然后逐条回查只为被告知「已在池中」。

修法：`prepare()` 跳过在**任何**批次里已是 `confirmed` / `already_selected` 的商品。

注意 `filtered` **不算**已结——它只表示「当时没达门槛」，门槛放宽后应当重新有资格。两条规则各有测试。

## 提速：为什么之前只有 5 条/分钟（2026-09-15）

用户要求提到 30–50 条/分钟。拆开上一批的耗时，瓶颈**不是**读取：

| 步骤 | 次数 | 总耗时 |
| --- | ---: | ---: |
| **seed** | 1 | **161.2s** |
| read | 80 | 17.9s |
| create | 1 | 13.5s |

两个原因：

1. **建链一直在单通道上跑。** `step_create` 本来就支持 `--lanes/--qps`，但 `catalog-link-batch.py` 只把它们传给了 `read`，**没传给 `create`**。所以建链用的是默认 `lanes=1`——这正是没跑到实测速率的原因。
2. **seed 每次重付 161 秒** 读整个已选池。其实已有 2 小时 TTL 的池子缓存（`var/catalog-selected-pool-cache.json`），首次之后应当命中。

### 改动

- 驱动器把 `--lanes/--qps` 一并传给 `create` 和 `seed`。
- `job_run` 把 `lanes`（1/3/6/9）与 `qps`（3/5/8/12）纳入作业配置，默认 **9 × 12**（此前实测达到 35.4 条/分钟的那组）。
- 桥接层把这两个字段**按集合校验**而不是按范围：`lanes=5` 在 1–9 之内但不合法，必须在请求层就判 400，否则会漏到驱动器那里变成"服务不可用"。

### 实测

| 步骤 | 耗时 |
| --- | ---: |
| seed | 1.5s（缓存生效，原 161s） |
| read | 24.0s |
| **create** | **33.5s / 20 条 → 35.8 条/分钟** |

落在用户要求的 30–50 区间内。按此速率，剩余 854 条约 24 分钟。

**传输速率仍是既有验收过的上限**（9 通道 × 12 QPS 共享），没有突破任何已确认的账号 pacing；只是把已经支持的能力真正接上了。

## 更正：`commercial_facts_changed` 那 16 条并没有变化

我先前的说法是"平台改过方案，需要人工核对"。**这是错的**——我看到错误码名字就下了结论，没读平台核对。

实际读一次平台逐字段对比后：**16 条的活动 ID、总佣金、公开佣金、达人佣金全部与冻结意图一致**，没有任何字段不同。

那些错误记录于 2026-09-14 22:14，当时确实不一致，现在又一致了。最可能是平台在那一刻返回了过渡态数据（活动切换窗口或部分响应）。**结论：这 16 条不需要人工核对，重跑即会成功。**

### 因此修掉的可观测性缺陷

程序原来只记"变了"，不记"变成了什么"，错误码就是 `commercial_facts_changed` 一个名字。后果是——**连开发者都得重新读一遍平台才能判断**，而一次瞬时差异和一次真实变更在记录上完全一样。

改为记录差异明细：

```
commercial_facts_changed:totalPercent 17->14;creatorPercent 15->12
```

页面对这类带明细的错误码会显示成「分佣与已核验链接不一致（totalPercent 17->14）」。

字段用 `->` 而不是箭头字符，是为了让错误码保持可直接 grep 的 ASCII。

## 每次新建上限：从"每次运行的总量"改成真正的批大小

用户问前端那两个参数要不要改。查下来发现 `--creates` 的语义和实现对不上：

- `catalog-link-batch.py` 的循环是 `while True: created=result['create']['created']; if not created: break`
- 但 `catalog-link-prepare.py` 的 **stdout 只打印 `{action,state,summary,platformWrites}`，没有 `create` 字段**

所以 `result['create']['created']` **永远是空**，循环**第一次就退出**。真实的 `created` 一直躺在 `var/catalog-link-create-NN-*.json` 报告文件里，驱动器从没读过。

后果：`--creates N` 实际是「每次运行建 N 条」，而不是「每批 N 条、循环建完」。设 5 就 5 条，设 200 就 200 条。

**修法**：CLI 把本次新建条数打进 stdout（`'created': len(...)`），驱动器按条数判断是否继续。

### 实测：设 30 跑完了全部 879 条

| | 修前 | 修后 |
| --- | --- | --- |
| `creates=20` | 建 20 条就停 | — |
| `creates=200` | 建 200 条就停 | — |
| `creates=30` | 建 30 条就停 | **建完 879 条才停** |

速率稳定在 **38–50 条/分钟**。

## 建链进度：一次读取 19 秒，一轮却要几分钟（2026-09-15 追加）

用户要求 TapLink 准备卡加「准备进展（跑到第几个了）」。原来页面上只有一个 `running` 标记：一轮读取 15 条要 19 秒，一轮创建要几分钟，**中间没有任何数字会动**，看起来像卡死。

进度不能靠最终报告——`catalog-link-batch.py` 原来只在**收尾时**写一次 `--report`。所以：

- 驱动器新增 `--progress <var 下的路径>`，**每完成一步就原子替换一次**小 JSON：`{startedAt,updatedAt,phase,step,pass,passes,created,total,states}`。`phase` 是 `seed`/`read`/`create`/`done`，`states` 直接取该步 CLI 返回的台账状态计数。
- `lib/job_run.py` 的 `command_for` 把 `var/job-links-progress.json` 传给驱动器；`state()` 读回它并挂在 `run.progress` 上，`status()` 因此自然带上；**`start()` 会先删掉上一次的进度文件**——否则新批次刚启动时页面会显示上一批已经跑满的进度条，等于谎报本轮已完成。
- 桥接层（`server/catalog-jobs/bridge.ts`）严格校验 `progress`：非负整数、`states` 值必须是非负整数；**缺失可以是 `null`，写坏则整包拒绝**，半截文件不会被画成进度条。
- 页面只有 `links.run.running` 为真时才 5 秒轮询（沿用原逻辑），所以进度是真动，不是前端假动画。加载时 `progress` 为空且不在运行 → 不显示该区块。

进度条取哪个分子，按阶段换：

| 阶段 | 分子 / 分母 | 含义 |
| --- | --- | --- |
| seed / read / done | `已判定 = total − pending − reading` / `total` | 读了多少商品（读不完整也算已处理） |
| create | `本批已建` / `本批已建 + 当前 states.missing` | 待建链起点涨到几成；此时读进度已满，不能再拿它当分子 |

行尾另给「第 N 步 · 只读检查已有链接（第 4 / 80 遍）· 已判定 · 待建链 · 本批已建 · 更新时间」。

同时按用户要求**删掉卡片里的「商品链接明细」表**（20–40 行/次、没有实际动作）；台账状态仍由 `/api/global-source?links=1` 返回，只是不再铺在页面上。
