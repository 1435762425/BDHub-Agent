# TapLink 卡名的商品短名：一个静默失效的环节

2026-09-14/15。用户问：建 TapLink 时用到的**商品短名是不是 DeepSeek 生成的**？如果是，这一环不能忽略，必须在页面上可视化。

## 结论：是 DeepSeek 生成的，而且**一个都没用上**

- `lib/draft_provider.py`：`MODEL = "deepseek-flash"`，`ENDPOINT = https://api.deepseek.com/chat/completions`，凭据来自 `DEEPSEEK_API_KEY`，实测 `credentialReady: true`。
- `lib/cycle_materials.Materials.prepare_names` 调 `call_model` 生成 `shortNameIt` / `mentionIt` / `shortNameZh`，经 `checked_names` 校验后写入 `cycle_product_name`。缓存里已有 **367 条**（200 个作业 ready）。
- 建链时 `link_naming.short_name_for` 读这个缓存；**读不到就回退成截断的原始标题**。

按建链的实际调用方式实测 2,289 个商品：

| | 修复前 | 修复后 |
| --- | ---: | ---: |
| 命中 AI 短名 | **0** | 268 |
| 回退截断标题 | 2,289 | 2,021 |

**根因**：缓存键包含**商品标题**——`digest(['product-short-name-v1','it-IT',pid,title])`。而同一个商品从两个来源来的标题不同：

```
短名缓存来源（Kalodata）: cuscino per il collo morbido in memory f
货盘台账来源（平台列表）: Cuscino morbido per il collo in memory f
```

不只是大小写，**词序也不同**。所以缓存永远不命中，AI 短名全废。

之前看到的"漂亮卡名"（如 `Lucidalabbra effetto velluto`）其实是**恰好截断得好看的标题**，截自 `Lucidalabbra effetto velluto opaco…`。

## 修法：短名属于商品，不属于标题字符串

`short_name_for` 改为**按 `pid` 查**（`cycle_product_name` 本身有 `pid` 列），不再用标题拼键。改一个商品的标题不该丢掉它的 AI 短名。

修复后立即恢复 268 个，剩余 2,021 个需要生成。

## 页面可见化

「已选商品链接准备」改名 **「TapLink 准备」**，并新增「商品短名（卡名来源）」区块：

- 已就绪 / 共 多少，缺多少个（`缺 N 个` 黄色标记；模型未就绪则标灰）

- 模型与端点、每批上限（5）
- 缺短名样例（PID + 标题前 60 字）
- 「生成商品短名」按钮 + 本次上限输入，旁标 **「会消耗模型额度」**

`scripts/lib/catalog_names.py` 提供 `gap()` / `prepare()`；`scripts/catalog-names.py status|prepare` 是 CLI。`prepare` **复用** `Materials.prepare_names`（同一个 provider 调用、同一套校验、同一套预留与缓存），不重写。**失败的调用绝不自动重试**，失败即停并如实报告。

## 三个后续修复（用户点击后暴露）

**① 点击「生成商品短名」报"暂时无法生成短名"**
`catalog-names.py prepare` 只回 `prepare()` 的报告，缺 `scope`/`ready`/`missing`/`provider`/`batchLimit`，桥接层校验不通过判为不可用。改为**始终回完整状态**（`gap() | prepare()`）。

**② 长度口径不一致，31–60 字的名字被白白丢掉**
写入端 `checked_names` 允许 ≤60 字，读取端 `short_name_for` 却卡 ≤30 字。`Scarpe da ginnastica con luci LED`（34 字）是有效名字，却被判为不可用而回退到截断标题。长度适配本来就是 `render_full` 的职责（它按词裁到卡名上限），所以读取端放宽到 60，与写入端一致。这一改立刻恢复 17 个。

**③ 一个"占着位置但不可用"的缓存会永久阻止重新生成**
`prepare_names` 只用 `WHERE id=?` 判断是否已缓存。一行 `shortNameIt` 为空或超限的记录**满足这个条件但任何读取方都不接受**，于是该商品永远既用不上、也不会重新生成。改为 `usable_cached()`：**只有读取方会接受的名字才算已缓存**，并把写入改成 upsert（`missing` 里只会有"没有行"或"行不可用"两种，所以替换正是想要的，好行永远不会被覆盖）。

另外：历史遗留预留可能挡住个别商品。`catalog_names.prepare` 会**跳过**这些并如实报告（`blocked`），不让一行陈旧记录拖住整批。

## 「设了 100 却只跑了 20 就停」——三个原因

**① 一批失败就终止整轮。** `prepare` 在第一个错误上 `break`。改成**跳过失败批次继续**，只有**连续 3 批失败**才停（`MAX_CONSECUTIVE_FAILURES`）——连续失败说明是系统性问题，继续跑只是烧钱。

**② 真正的失败原因是模型多回了一个字段。** `checked_names` 要求字段集合**完全相等**（`set(row)=={'ref','shortNameIt','mentionIt','shortNameZh'}`），而模型有时会把输入标题原样回显成 `title`。于是名字完全有效、整批却被判 `names_invalid`。

改为**必须包含这四个键**，多余字段忽略且**不落库**（值校验一字未改，持久化内容反而更干净）。用存下来的响应重放验证：之前失败的两批现在都通过。

**③ 已经生成过、只是没落库的响应被浪费。** 新增免费恢复路径 `_recover()`：如果某个商品的预留指向一个状态为 `ready`/`response_saved` 的作业，就直接从**已付费的响应**里取值落库，绝不重新调用模型。恢复覆盖**全部**缺失项，不受本次批量上限影响。

## 「全部生成」

页面新增 **「全部生成（剩余 N）」** 按钮，API 接受 `all: true`，CLI 有 `--all`。上限从 500 放宽到 5000。

| 动作 | 结果 |

## 最后 5 个：一个字段拖垮整批

跑完全程后剩 5 个反复 `names_invalid`。查明原因：其中一个商品的 `mentionIt` 是 `questo set di strumenti per la pulizia del viso`——**9 个词**，超过 `checked_names` 的 ≤8 词限制。

关键点：**一批 5 个里，另外 4 个被它拖死**。而且**批量请求时模型才会给出超长短语**，单独请求时给出的是合规的短版本。

两层兜底：

1. **`names_invalid` 可安全重试**。这条错误意味着**响应已收到且被判定不可用**——结果已知，重新请求不可能重复一笔"结果未知"的开销。所以 `_forget()` 清掉该批的预留与作业（**只对 `names_invalid` 这样做**，传输类失败绝不重试），然后重问，最多 3 次。
2. **拆分兜底**。重试仍失败且该批多于 1 个商品时，**逐个单独请求**。于是失败的粒度从"批"变成"真正无法生成的那个商品"。

结果：这 5 个全部救回。
